# Selected npm write-route threat model — whole-package revision DELETE

Verdict: **MODELED** (design review, 2026-10-28).
Blocking findings: **none**. The approved Gate 1 and Gate 2 documents and the amended Gate 3/4 design are present. No accepted or transferred security risk is needed.
Scope: every selected `/registry/npm/<id>/` write entry point described in Gate 3, with emphasis on whole-package `DELETE /<package>/-rev/<revision>`; the canonical packument preflight and tarball reference are included where they authorize or feed those writes. This is not implementation verification.

## Entry points, boundaries, and assets

- **Actors:** admitted developer holding a unique client certificate and optional developer bearer; malicious or compromised client; selected upstream registry; registry administrator approving D41 destinations; operator approving private egress; signed-in member requesting setup; certificate issuer and status responder.
- **Entry points:** package PUT; package revision PUT; whole-package revision DELETE; named `/-/` login, package-settings, organization/team, token and stage mutations; token-bearing canonical packument GET and `?write=true` preflight; member-bound artifact-reference DELETE; direct canonical tarball DELETE; unknown catchall mutations and PATCH.
- **Trust boundaries:** TLS peer to current organization/member/registry principal; client path to disjoint named action/read/refused classifier; developer bearer to selected-upstream authorization; selected origin to outbound DNS/connected peer/TLS; selected packument URL to sealed lease; client revision JSON to outgoing upstream PUT; accepted revision PUT to one-use deletion marker; D41 administrator approval to optional extra-origin DELETE. A signed-in portal session to a certificate/private-key bundle is an adjacent identity boundary.
- **Assets:** upstream package and account state, package revisions and tarballs; developer bearer and shared read credential; certificate private key and current member/group status; selected registry identity; group-hidden metadata and artifact bytes; lease URL/query and encryption key; marker integrity; outbound network authority; firewall availability.

## Decisions and limitations

- D40/D41 apply to **version-tarball reference DELETE**. The whole-package revision DELETE is an upstream-authorized selected-origin action under C4; extending the marker to it would invent a product rule. Direct canonical tarball DELETE is locally refused because it can bypass that marker.
- STRIDE was applied across the listed entry points: spoofing (T1), tampering/repudiation of revision and marker state (T5–T6), disclosure (T4/T7), denial of service (T8), elevation (T2–T4), with destination and state boundaries checked for noninterference, capability/ambient authority, isolation, TOCTOU, unsafe parsing/deserialization and attacker-controlled complexity.
- Structural checks establish guard order only. Exact route shapes, SQL member/registry values, token bytes and destination, connected-peer/path validation, sealed data, one-use atomicity and actual upstream allow/deny remain the explicit Slice 4 runtime and independent source-review witnesses. Current or missing Slice 4 implementation does not change this design verdict.
- **Omitted threats: 0.** Eight retained threats cover the in-scope boundaries; lower-level cases are represented in their corresponding rows.
