# Threat model: active local service and npm DELETE routes

**Verdict: MODELED.** The active design distinguishes policy-server authentication, selected-registry authorization, and all three npm DELETE paths. No blocking design gap remains in the reviewed scope.

## Scope, actors, entry points, boundaries, and assets

Actors are local package-manager users/CI jobs, the local/shared Probation service, the managed policy server, configured selected registries, administrators approving D41 destinations, and local/cluster operators. Entry points are managed policy snapshot retrieval, explicit standalone TOML startup, selected npm/PyPI operations, and npm whole-package revision DELETE, direct canonical tarball DELETE, and version-reference DELETE. Assets include the service API key, package-manager credentials, policy and registry identity, hidden metadata and artifact bytes, package/account state, durable service references and revision markers, logs, and listener availability.

The service API key authenticates the firewall to the policy server only through HTTP `Authorization` on `GET /api/v1/policy/snapshot`. Package-manager credentials are separately supplied by npm/Python tools and authorize operations only at the selected registry. Local policy gates the attempt; the selected upstream decides publishing/account authorization. The shared service has no individual package-request identity. The service-store namespace is the identity scope for version references. Explicit standalone TOML is a separate selected mode; managed failure does not fall back to it.

## Decisions, limitations, and omitted threats

No risk is accepted or transferred. Managed propagation and remembered-policy outage rules retain the bounded C19/C20 exposure window; local package caches and compromise of an approved node remain outside per-user re-delivery control.

The finite model declares distinct outcomes for all three DELETE paths and `molecule-check` passes. The route sources do not yet exist; this is a design review, not implementation proof. Source controls prove only their specified call order. Exact credential bytes/destinations, route completeness, upstream decisions, marker durability/atomicity, and one-winner concurrency require the Slice 3 witnesses and source/security review. The API-key header and registry credential separation also requires the Slice 1/3 request traces.

**Omitted threats: 0.** Seven retained rows cover the in-scope identity, routing, deletion, and listener boundaries.
