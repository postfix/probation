# Organization-issued certificate revocation freshness

**ANSWERED.** The approved next-request refusal in product C24/X08 cannot be established with an ordinary cached CRL or OCSP response. CRLs are periodic, so a new revocation appears in a later update ([RFC 5280 §3.3](https://www.rfc-editor.org/rfc/rfc5280.html#section-3.3)). OCSP responses state when status was known and when newer information will be available; they may be pre-produced ([RFC 6960 §§2.4–2.5](https://www.rfc-editor.org/rfc/rfc6960.html#section-2.4)). The OCSP security analysis explicitly allows replay of a still-valid “good” response after revocation ([RFC 6960 §5](https://www.rfc-editor.org/rfc/rfc6960.html#section-5)). Its nonce prevents response replay, but does not promise prompt propagation of issuer revocations ([RFC 6960 §4.4.1](https://www.rfc-editor.org/rfc/rfc6960.html#section-4.4.1)). The current high-volume OCSP profile calls for caching and permits time-based freshness when nonce is absent ([RFC 9919 §§5, 7.1](https://www.rfc-editor.org/rfc/rfc9919.html#section-5)).

**Design inference.** Organization-issued mode needs a synchronous authoritative certificate-status check before each package read or action, against issuer state that reflects every committed revocation. A dynamic OCSP responder is usable only with an explicit issuer freshness and nonce contract; ordinary OCSP/CRL support is insufficient. Failed, unknown, unverifiable, or unavailable status refuses the request. This adds per-request latency and makes issuer-status outages deny package traffic. The chosen issuer's actual consistency and availability still need an integration witness before release.
