# Release client matrix v5 (proposed, fixed before scope reapproval)

The denominator is every **required** row below. A missing fake-registry endpoint, missing executable, changed client version, skipped row, or uncollected network trace fails the release check. Each row runs with one selected organization registry URL under three configurations: Probation-issued with self-service enabled, Probation-issued with self-service disabled, and organization-issued certificates. Every client certificate uniquely identifies a user; there is no per-user virtual host. Certificate keys and publisher tokens stay in client-local configuration or a secret manager. npm reads, login, publishing and account/package administration use that same URL; the developer token may be forwarded to the selected upstream for canonical npm packument GETs as well as named write actions; the upstream decides metadata visibility and independently authorizes writes. Only Probation is reachable from the package-client network. The fake selected upstream must implement each listed capability; an upstream denial is a positive expected outcome only where the row says so. Real public npm/PyPI canaries supplement the fake but cannot replace its negative and isolation cases.

The witness names are scenario identifiers to implement under `tests/e2e/`. Each witness records the actual client command, complete request-path trace, upstream status, client result, generated-file scan, and package-client egress log. `R` is the selected registry ID, `P` its nonsecret organization registry URL, and `S` a different origin used as a credential sentinel. Developer credentials are confined to R's canonical npm packument GETs and named upstream actions; the shared upstream read secret is absent from actions; the client certificate and private key are never forwarded upstream. Token-bearing packument GETs may reveal upstream-returned metadata despite group policy. Tokenless metadata, other reads and all artifact downloads remain group-filtered; no credential is reflected. Baseline clients: npm 11.21.1, pip 26.2.2, Twine 7.0.0, uv 0.13.5. The current E2E images pin pip and uv; dedicated npm 11.21.1 and Twine 7.0.0 clients must be built. Version changes require matrix review.

**Explicit upstream-unsupported cases:** PyPI's documented package-client API provides Simple reads and legacy upload. PyPI account sign-in, project deletion, owner management and release deletion are website workflows rather than pip/Twine registry commands, so those website operations are outside C3's package-client route and do not become silent skipped rows. [PyPI Upload API](https://docs.pypi.org/api/upload/), [PyPI Index API](https://docs.pypi.org/api/index-api/), [PyPI release deletion guidance](https://docs.pypi.org/project-management/storage-limits/). A company Python registry exposing additional documented CLI endpoints requires a versioned extension of this matrix before being claimed supported. npm CLI commands are documented by [npm 11 command reference](https://docs.npmjs.com/cli/v11/commands/npm/); exact HTTP routes must be captured by the real-client probes rather than guessed from names.

**C14 disposition:** `uv lock`/`uv sync` project mode is required in U01. Its committed lockfile can record P because the registry URL is not a bearer secret; a real scan must prove no credential is written. [uv project docs](https://docs.astral.sh/uv/guides/projects/). The prior no-host scan and npm omission setting are no longer release requirements; using npm's omission setting remains optional.
