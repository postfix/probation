## Implementation and observed behavior

The shared-service classifier now admits POST only to the exact selected `/registry/pypi/<id>/` root without a query. The existing `selected_upload` handler parses request-local Basic/Bearer credentials, spools a bounded body, rechecks policy and selected origin, then sends to the selected upstream. Unknown IDs, unrelated Python POST paths and query-bearing uploads remain locally refused. The upstream response status and body remain authoritative.

The public-route Rust test uses an exact custom target `https://pypi.invalid/legacy/`, asserts Basic/Bearer upstream allow and deny, exact forwarded destination/body/authorization, unknown-ID and unknown-path zero I/O, and declared/chunked B+1 refusal before upstream I/O. The fake transport establishes routing and value mapping only. The native service scenario uses pinned Twine 7.0.0 and a fake selected PyPI registry to exercise wheel/sdist Basic upload, Basic denial, Bearer allow/deny, selected-only refusal, no policy-key category at the registry and managed-policy refusal after service-key revocation.

## Known limits and open design questions (not fixed in this slice)

- Upload size/time: the spool cap is 2x max_artifact_bytes + max_metadata_bytes, written to disk before the upstream credential is checked; no read-idle or total timeout. OPEN, needs a user decision.
- A policy change after the upstream write returns 503 although the upload happened (retry sees "file exists"); the 30 s deadline can return 504 for a committed write. OPEN, needs a user decision (document as at-most-once-unknown, or an upload-specific response).
- Advisory: reqwest Authorization header not marked sensitive; fake PyPI accepts `Bearer e2e-owner` (real PyPI uses Basic `__token__`); case-sensitive auth scheme parsing; `fakes/main.mjs` `sig=` substring match; `admit_certificate` ignores `self.retired`; 401 vs 404 registry-ID enumeration for local peers.

## Adversarial review and upload-deadline fix (2026-11-04)

Adversarial review (independent, 40 raw-socket and service-stack probes): URL forms, Authorization variants, duplicate headers, framing, truncated bodies, concurrency and client abort held. Findings:
1. DEFECT (major, fixed): `ReqwestTransport::send_action` used the 30 s metadata total deadline for every action, so an upload that takes longer than 30 s to send or be answered returned 504, contradicting `03-program-design.md` ("30-second write-idle and 15-minute lifetime ... valid npm/Twine uploads under B must pass"). Reproduced RED through the real https transport: `publishing-python-service` gained a 2 MiB upload to a registry that answers after 33 s; it failed with 504 (`.scratch/slice4/service-red.log`). First fix attempt (artifact client with `read_timeout`) still failed, because reqwest 0.13.5 starts `read_timeout` at request creation and it covers the request-body send and the wait for headers (`.scratch/slice4/service-green.log`); the shipped fix gives action bodies above 1 MiB the 15-minute lifetime only (`UPLOAD_BODY_BYTES`, `selected_within` in `src/upstream/reqwest_transport.rs`). GREEN: same scenario passes, 6 uploads, 64.8 s (`.scratch/slice4/service-green2.log`). Limit (ponytail comment in source): there is no true write-idle timer; a stalled upstream holds its permit up to 15 minutes. Smaller actions (publish metadata, deprecate, dist-tag, unpublish) keep the 30 s bound. The e2e tally is now 6 uploads (developer-owner 200 x2).
2. OPEN (extends the post-write 503 question): in service mode `respond` checks `authorize_current_policy` after the handler, and any snapshot publication (a revision bump or an edit to an unrelated registry or layer, not only a revocation) between the pre-send recheck and the response turns a committed upload into `503`, with text "no valid blocklist is loaded", which is misleading for an upload. Reproduced with a fake transport: 1 upstream write, client sees 503. The refused-snapshot control correctly gives 503 with 0 writes. Needs the user's decision (narrow the post-handler check for non-idempotent POST, return an explicit outcome-unknown response, or document).
3. TEST GAP: the real `send_action` (header construction, Content-Length plus stream, redirects, `collect_capped`) has no in-repo unit test with https; covered only by the e2e scenario. 3xx with Location becomes 502, a reply over M becomes 502 even if upstream committed.
4. ACCEPTABLE LIMIT: one URL per registry; uploads POST to the registry's configured URL verbatim, so a registry whose upload endpoint differs from its Simple URL (pypi.org -> upload.pypi.org/legacy/) is not supported by this slice.
5. ACCEPTABLE LIMIT: Content-Type must be exactly `multipart/form-data; boundary=...`; a stalled client holds a permit and spool (known, open question 1).
