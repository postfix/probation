## Design as built
Each native runner starts everything itself (`tests/e2e/native/stack.mjs`):
- Node fake npm and fake PyPI registries (`tests/e2e/fixtures/fakes`) and a fake policy endpoint (`GET /api/v1/policy/snapshot`, Bearer `prb_` key, a `ServicePolicySnapshot` JSON matching `crates/probation-policy/src/api.rs`) on loopback https ports.
- A runner-generated CA and certificate from the existing `tests/e2e/fixtures/make-ca.sh` (SAN 127.0.0.1, localhost, pypi.org). Linux: the service reads `SSL_CERT_FILE`. In GitHub Actions only: macOS `security add-trusted-cert` into the System keychain, Windows `certutil -addstore Root`, both removed afterwards (unverified, see below). Node/pip/Twine/uv use env CA variables. This is server trust only; no client certificate or key.
- The natively built `probation serve` in `[service_policy]` mode with its own TLS listener. The registries are private destinations, so the snapshot's registry descriptors carry the operator-approved exact target and `registry_private_cidrs: ["127.0.0.1/32"]`. No product refusal was relaxed or bypassed.
- Fake PyPI as `https://pypi.org:443` on loopback. Reason (proved by a red run): a selected PyPI registry admits file URLs only on the public PyPI origins (`src/artifacts/download.rs own_origin`, `OriginSet::selected_npm_with_private`), so a private PyPI whose files sit on its own origin cannot be served; the fake uses the admitted name instead. This needs `pypi.org` mapped to loopback and a bindable port 443: `stack.mjs` appends a marked `hosts` line (sudo on Linux/macOS, direct on Windows) and removes it; the workflow opens `net.ipv4.ip_unprivileged_port_start` on Linux; macOS binds the wildcard address.
- `tests/e2e/native/publishing.mjs` then runs the real clients and 37 checks (list below). `tests/e2e/native/clients.mjs` runs first and fails on any missing or wrong pin.

Rows covered by `publishing.mjs`: npm publish (owner allow, denied 403, owner token reaches the selected upstream), install with lockfile on the local URL, view, audit (upstream audit endpoint reached), deprecate (owner allow, denied), version unpublish (denied refused, owner allowed, upstream state checked), whole-package unpublish, token-packument (policy-hidden package: tokenless 403, owner 200 with owner-only metadata, denied 403, no token reuse, noncanonical query 404, no artifact bytes from a token), unknown registry ID with zero upstream calls; Twine upload (owner, denied 403, exact upstream tally with the Basic credential), Bearer denied upload, pip install, `uv pip install`, `uv lock` + `uv sync --frozen` (lockfile on the local URL), npm ID under the PyPI path refused with zero upstream calls; boundaries (policy key only to the snapshot endpoint and never to a registry, registries see only package-manager credentials, client config files hold no certificate/key setting).
Not covered (stay in the Docker harness, now run by `linux-managed`): web-login, legacy login, outage/restart/cache cases, redirect/header/slow/size bounds, Basic/Bearer matrix breadth, SSO/issuer/10,000-client rows, `E2E-publishing-full-matrix` row accounting.

## Fix of the full-matrix certificate-admission 503 (2026-11-05)

**Proved cause.** `SyncClient` (`src/managed/client.rs`) sent every management call unmetered. The firewall's lookup budget (`Budget`, `src/managed/mod.rs ask_server`) meters only key lookups; `admit_certificate` calls `client.certificate` directly, and layer fetches and a lookup's fan-out (`ASK_CALLS` = 6) also bypass it. The management server answers 429 to a token's 201st arrival in a second (`FIREWALL_TOKEN_RATE_PER_SECOND` = 200, the only 429 source of the sync API, `crates/probation-server/src/sync.rs`), `client.rs` maps 429 to `CallError::Busy`, `admit_certificate_at` logs "the certificate admission call failed; answering busy" and the package client gets `503 LOOKUP_BUSY`. The 32-worker unpaced scale probe can exceed 200 calls in a second.
**Failing first** (`cargo test --offline --lib managed::client`): `a_burst_the_timeout_can_absorb_is_paced_below_the_servers_rate` — "the server answered 429 to 300 of 500 calls"; `a_burst_beyond_the_timeout_is_refused_busy_before_it_reaches_the_server` — 400 server 429s. A first fix attempt (a 180/s send window alone) still failed (126 and 124 429s) because requests bunch on arrival.
**Fix** (one place, all callers of `SyncClient::call`): `src/managed/client.rs` only. `pace()` takes an in-flight permit (at most 32) and a slot in a sliding one-second window (at most 150 sends/s) before each call. Bound: a request arriving in one second was sent in it (<=150) or in flight at its start (<=32), so the server sees <=182 of its 200, leaving room for the separate `changes` poll. Waiting is bounded by the request timeout; a call that cannot be sent in time answers `Busy` locally without reaching the server, so real overload still shows and the C19/C20 behavior (Busy -> stale entry / 503) is unchanged. No retry loop, no harness change, no change to any limit or to `sync.rs`, `mod.rs` or FIX-16-A files. Diff: +163 lines in `src/managed/client.rs` (constants, two fields, `pace`, one call line, two tests). Keep `MAX_CALLS_PER_SECOND + MAX_IN_FLIGHT` below the server constant.
**Results** (all under the capped scope, scratch target dir): both new tests pass, 5/5 repeated runs; `cargo test --offline --lib` managed 35/35, whole lib 198 passed 0 failed 2 ignored; `--test managed_delivery_authority --test managed_mode --test managed_sync --test service_policy_cache --test shared_service --test pypi_service_upload --test service_unpublish`: all ok (5, 10, 41, 1, 6, 4, 4); `-p probation-server --test sync_api` 6 passed. ## macOS fake PyPI on :443 and accepted residuals (batch 4)
- **Why loopback :443 is refused on macOS runners.** The service admits PyPI files only from the public PyPI origins, so the fake PyPI must answer as `pypi.org` on port 443. macOS lets an unprivileged process bind a port below 1024 only on the wildcard address (INADDR_ANY); a bind to 127.0.0.1:443 needs root, and the runner's Node process is not root. `stack.mjs` therefore (CI only, macOS only) first tries a pf redirect of 127.0.0.1:443 to a high loopback port, probes it, and only if that fails serves the fake on all interfaces with a warning. **Residual exposure of the fallback:** for the job's duration any host that can reach the runner's network interfaces can talk to a fake PyPI that serves synthetic data and accepts uploads into memory; it holds no secret (the owner and denied tokens are public test constants, the service key never reaches it) and the runner is an ephemeral VM. The pf path is unverified on macOS; its argument construction is unit-tested.
- Accepted without change: Windows ACLs of the key file and the delivery log directory are not verified by Probation (documented; `stack.mjs` restricts the key file with icacls and says so); the unpublish lease owner is shared in service mode (no privilege gain); the other compose and root images are pinned by tag only (outside Slice 5 scope); the apt packages in the test image (`native.Dockerfile`) are unpinned.

## The real policy server for macOS, Windows and Linux native jobs (tunnel design)
- **Design.** `native-clients.yml` now has two kinds of job. `real-server` (ubuntu-24.04, hard timeout 110 min) runs the real stack through the Docker harness (`E2E-publishing-native-remote`): policy server, portal, catalog with the npm registry `https://127.0.0.1:43111/` and the PyPI registry `https://pypi.org/`, each with an operator-approved private-egress entry for 127.0.0.1/32, a throwaway service key and a policy block hiding one package, all created at run time. A filtering proxy on a loopback port forwards only `GET /api/v1/policy/snapshot` with that key to the real server; a pinned, SHA-256-verified cloudflared quick tunnel exposes that proxy. The three `native-clients` matrix jobs (ubuntu, macOS, Windows) take the tunnel URL and key from the handshake and run the natively built probation, loopback Node fakes and the pinned clients against the real server. The in-process snapshot is a local-only fixture; in Actions `publishing.mjs` refuses to run without the handshake.
- **Rendezvous** (no `needs` between the jobs): `native-handshake` artifact from the server job, `native-done-<platform>` from each native job, polled through `gh api` with bounded waits; details and tests in `tests/e2e/native/rendezvous.mjs`, `rendezvous.test.mjs`, `rendezvous-cli.test.mjs`. Teardown, ensure-handshake, release and the completion records run in `always()` steps, so a failed or cancelled native job (for example Windows, which cannot yet build the service) still lets the server job finish.
- **What the tunnel exposes:** the snapshot response (policy and registry descriptors, no credentials) to a caller holding the throwaway key, for the job's lifetime. **Residual:** the handshake artifact holds the tunnel URL and the key. Artifacts of a public repository are readable by anyone who can read the repository, so for up to a day (retention 1) anyone could fetch the snapshot with that key until the server job ends; both are masked in logs, the data is synthetic and the key is useless afterwards. The handshake is never copied into `GITHUB_ENV` or logs; the downloaded copy is overwritten after the key is moved to a 0600 file.
- **Unverified until a hosted run (all of it ran on 42233412311 except the Rust platform-verifier note; see 'Hosted runs'):** cloudflared 2026.10.7 starting on a runner, printing its address and carrying traffic (quick tunnels are best-effort and rate-limited; `--protocol http2` is used so only TCP 7844 outbound is needed); that the artifact API lists and `gh run download` retrieves an artifact uploaded earlier in the same still-running run (including when the workflow is called from release.yml, where the caller grants `actions: read`); `gh` being present and authorised on all three runners; the `nohup` background harness surviving across the real-server job's steps; the macOS and Windows runners trusting the test CA and reaching a `*.trycloudflare.com` certificate; the Rust platform verifier on macOS and Windows; the Ubuntu native job's trust file (system roots appended); time budgets (image build plus stack before the handshake, 35 min bound); the Windows build, which still fails on unix-only code (that job reports failure and the server job then fails its own check, correctly). The sandbox here refused to run a downloaded cloudflared, so nothing about the tunnel program itself was run; the stub-mode run proves the real server, portal catalog, proxy filtering, handshake file, release flag and the proof-of-origin check.
- **Recommended, not added:** CODEOWNERS coverage of `check_workflow.py`, `run_tests.py`, `rendezvous.mjs` and `cloudflared.mjs`, because a change to any of them changes what judges the workflow.

### Removal of the runner-side test CA on macOS and Windows
Code (`stack.mjs`): `trust()` adds the CA (macOS `security add-trusted-cert` into the System keychain, Windows `certutil -addstore Root`) and returns an undo (`security remove-trusted-cert -d`, `certutil -delstore Root probation-e2e-ca`); the undo runs on stop, exit and SIGINT/SIGTERM, and a stale CA is deleted at the start of the next run (`removeStaleTrust`).
Proven by the hosted logs: both jobs added the CA (otherwise the service would have failed to trust the registries, and `trust()` throws on a failed add) and neither log holds a "cleanup step failed" line, so no undo step threw.
NOT proven: that the CA is gone. The undo ignores the exit status of `remove-trusted-cert` / `-delstore` (a non-zero status is not reported), the logs print nothing from them, and nothing re-queries the keychain or Root store afterwards. `remove-trusted-cert` removes the trust setting, not necessarily the certificate from the keychain. The runners are ephemeral VMs discarded after the job, which is the actual protection; the CA key is a throwaway generated per run.
