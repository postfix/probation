What problem do we have?

Developers need npm and Python installs, publishing and supported management through one selected Probation URL. npm 11 removes a version by PUTting revised metadata before its tarball DELETE; without D40's member-bound lease, the proxy loses a noncanonical or extra-origin destination. The approved D40/D41 behavior now has frozen Slice 4 source and a passing pinned npm action witness. Eight planned unsafe-mutation strings still named illustrative statements absent from that source, so their defect controls were UNKNOWN. This approval rebinds those exact strings to guarded calls without changing the caller outcome.

How will we solve it?

Each project chooses one /registry/npm/<id>/ or /registry/pypi/<id>/ URL for reads and writes; legacy /npm/... and /pypi/... stay separate, including numeric npm packages. TLS supplies a unique user certificate. Admission checks the selected organization's current roots, live status, active member, group and registry. Only named reads, login and actions proceed.

Read. Tokenless metadata, search, audit and artifact bytes use current group policy. A canonical npm packument GET with a developer token may reveal selected-upstream metadata even if no write follows; its body stays request-local. Bulk and direct quick audit responses contain only visible-version signals and safe fields. Unsupported bulk remains the selected upstream's error.
Action. Named web-login start/poll may be tokenless. Other publish and account actions require the developer credential and selected-upstream permission. The shared download credential cannot authorize a write. HTTPS, DNS, connected-peer and TLS vetting apply; action redirects refuse.

Version-unpublish decision

A token-bearing npm ?write=true packument may atomically persist a 24-hour, member- and registry-bound action lease for each exact tarball URL the selected upstream advertised. The local link has only an opaque reference; the URL, including a signed query, is encrypted at rest and absent from links and logs. A quota or storage failure refuses the packument before advertising a dead link. No developer token or packument body persists in the lease.

Before a revision PUT reaches the selected upstream, every local versions[*].dist.tarball link must resolve to that member's live lease and be restored to the exact upstream URL. A successful PUT must remove the leased version and establish its resulting revision from the accepted response or an immediate authenticated refetch. A durable marker binds member, reference and revision before PUT success. The final DELETE requires that exact revision and consumes the marker once before outbound I/O. Denied or unchanged PUTs create no marker; verification or marker failure after upstream acceptance reports uncertain partial write.

An administrator may approve an exact HTTPS origin and segment-boundary path prefix for noncanonical selected-origin paths or extra destinations. Extra-origin developer bearer forwarding is opt-in per scope, off by default; the selected origin receives the bearer. DELETE rechecks approval, certificate, member, DNS, connected peer and TLS name, rejects ambiguous encoded traversal and redirects. Removing approval makes the lease unusable.

Decisions retained

  1. Use one selected registry URL; preserve legacy numeric npm routes and upstream write authority.
  2. Keep token-bearing canonical packument bodies request-local; persist only admitted tarball action leases.
  3. Bind a sealed lease to immutable registry, admitted member, package, version, reference and filename for 24 hours.
  4. Refuse the packument before advertising a new action URL if the atomic lease batch fails its per-member, per-registry or global live-lease quota.
  5. Restore every local tarball link to its exact advertised upstream URL before revision PUT.
  6. Create a durable resulting-revision marker only after an accepted PUT removes that version; report unverifiable accepted writes as uncertain.
  7. Consume that marker once before DELETE, after current member, URL, origin/path and revision checks.
  8. Send the bearer to the selected origin; send it to an extra origin only when that exact administrator-approved scope opts in.
