What problem do we have?

Developers publish and manage npm packages through one selected Probation address. Review found a separate way to delete a whole package that was missing from the security review. The written design also used “token” for every account action, although legacy npm login uses a username and password to obtain one.

How will we solve it?

We will review every npm operation in the approved N05–N23 client matrix. Package removal remains a decision of the selected upstream registry. Removing one version follows the already approved, one-use reference path.

Whole package

Upstream decides

A package revision DELETE goes only to the selected registry with the developer credential. Its permission or denial is returned. It does not use the version-removal marker.

One version

Marker required

After the upstream accepts a revision that removes a leased version, its reference DELETE consumes one matching marker. A direct canonical tarball DELETE is refused locally.

Login

Web login may start and poll without a token on named routes. Legacy login sends the developer’s Basic username and password only to the selected registry to obtain a token. Later write and account actions need a developer token and the upstream’s permission.

Three deletion routes: Whole-package revision DELETE → selected registry decides. Version-reference DELETE → accepted marker, then one vetted attempt. Direct canonical tarball DELETE → local refusal.
