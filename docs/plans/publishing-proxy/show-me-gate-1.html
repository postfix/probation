What problem do we have?

Developers need one deliberately selected Probation registry address for installs, publishing, and supported package actions. The current install route refuses npm login and publishing and has no Python upload. The selected-registry address must leave existing npm package reads unambiguous, including numeric package names and versions. Audit results must flag vulnerabilities without exposing packages or versions a group cannot read.

How will we solve it?

Project selects a registry → its npm and Python package clients use that selected Probation address for installs, publishing, and supported actions. The selected-registry address occupies a distinct URL path; existing npm package paths remain reachable.

Member runs audit → Probation forwards the request to that registry and returns a reduced vulnerability signal only for versions visible under the member’s current group policy. Hidden names and versions, and arbitrary upstream advisory text, links, and metadata, stay out.

Selected registry cannot answer npm 11 bulk audit → npm reports that registry’s error. A client that sends a valid quick audit request directly still uses the guarded quick route. Probation supplies no advisory service or invented bulk-to-quick request.

Member reads or writes a package → a unique client certificate identifies the member and their group policy; the selected upstream separately authorizes each write. A developer token may reveal canonical npm package metadata that group read policy hides, but does not grant artifact bytes or firewall access without a valid certificate.

Scope decisions:

  1. One project-selected registry address serves package-client installs and publishing; overlapping names never cause a silent switch to another registry.
  2. Selected-registry URLs move to a distinct namespace so numeric legacy npm package names and versions continue to work. Gate 2 chooses the exact path.
  3. Bulk and quick audit output contains reduced, policy-safe advisories for currently visible package versions only.
  4. Probation remains a proxy: npm 11 receives an error only when the selected upstream cannot answer its bulk audit request; direct quick clients retain guarded quick access.
  5. Previously approved certificate, member/group, token-bearing npm metadata, and upstream-only write-permission rules continue to apply.
  6. npm web login may open an upstream browser page; Python package-client scope covers install, upload, and only actions its selected upstream exposes.

Previously approved registry administration, certificate settings, setup, and Users screens remain the product views; audit is a package-client operation. The separate Users panel handles membership, groups, disabling users, and targeted Probation-issued certificate revocation.
