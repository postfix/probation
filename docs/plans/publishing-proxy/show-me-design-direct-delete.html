What problem do we have?

Developers use one selected Probation address for npm packages and publishing. Independent review found two ways version removal could break that promise: a direct tarball deletion address could skip the one-use removal check, and a metadata update could change a listed version’s tarball address before sending it upstream.

How will we solve it?

The approved setup, guarded reads, and upstream-controlled publishing stay in place. This revision makes the deletion route and metadata rule explicit before Slice 4 implementation resumes.

Rule 1 · deletion

One checked path

A version’s tarball can be deleted only through its member-bound reference after the upstream accepted a revision that removed that version. A direct canonical tarball DELETE is refused locally, even with a valid developer token.

Rule 2 · metadata

Keep the listed destination

For a version with a write-preflight lease, the submitted tarball address must be its exact local link or exact original upstream address. The proxy sends the original address upstream. An ordinary upstream address for a version without a lease still works.

Version removal: Write preflight lists and leases versions → revision PUT checks exact leased URLs → an accepted removal records one marker → reference DELETE consumes it and sends once. A changed leased URL or direct canonical tarball DELETE is refused before any upstream request.
