# Package-client authentication compatibility

Research date: 2026-11-02. Evidence is documentation/source review only; no client, TLS, metadata, artifact, redirect, or publishing runtime tests were run. No product policy is selected here.

## Question and decision

Question: Can each standard package client authenticate to an HTTPS firewall using native API-key/header, Basic, Bearer/challenge, or client-certificate TLS mechanisms, and which protocol-specific authentication changes are required?

Decision: Whether Probation can preserve a unique-user-client-certificate requirement on registry reads **and writes** while expanding to every Nora format, or needs an adapter or a different client-identity transport for some clients. Publisher credentials for the upstream registry remain a separate input.

Stopping condition: Every Nora format has primary-source authentication evidence, an explicit mTLS yes/no/unknown result, a CA trust mechanism or documented evidence limit, endpoint/credential-scope considerations, and a likely architecture implication. Unsupported and unknown are retained rather than extrapolated from HTTPS support.

Verdict: **UNKNOWN for a complete interoperable design; the universal native-client mTLS assumption is falsified.** Current Cargo and Go upstream evidence does not provide native registry mTLS. Other rows have unresolved version/endpoint coverage. Documented settings establish configuration capability, not that a complete install/publish workflow passes the existing admission contract.

## Scope and terms

The [Nora README](https://github.com/getnora-io/nora/blob/main/README.md), fetched on the research date (file blob `196b566c2c2b6b0f124c77fe29d727a9982af6e1`), lists exactly these 17 formats. It does not promise hosted/publishing support for all 17. Its [COMPAT](https://github.com/getnora-io/nora/blob/main/COMPAT.md), blob `6a4768210efe593c5435f41d3783f51ec5cbc45b`, distinguishes proxy-only formats and opt-in RPM, APT, and Hugging Face proxying. Nora compatibility claims are maintainer documentation, not measurements made for this report.

- **CA trust** authenticates the HTTPS server to the client. It does not identify a user to Probation.
- **mTLS** presents a client certificate and proves possession of its private key during the TLS handshake. A Bearer/API token or a certificate carried in an HTTP header does not provide that same proof.
- **HTTP auth** means a credential encoded as Basic, Bearer, a protocol token scheme, or another header. An API key can sometimes be placed in the password/token slot, but the firewall must explicitly accept that mapping.
- **Inbound** is package client → Probation. **Outbound** is Probation → upstream registry/token service/CDN. Inbound certificate possession cannot be transparently forwarded as outbound TLS possession. Each leg needs its own transport and credential configuration.

The main agent/local-auth worker supplies the repository contract above. This report does not independently establish or modify repository behavior.

## Consequence for the architecture decision

1. **Preserving the present unique-user-certificate contract is not universally compatible with direct, unmodified standard clients.** Cargo and Go are enough to disprove that assumption. An HTTPS URL or custom CA distribution does not resolve it. Their HTTP credential helpers cannot supply a TLS private-key proof. [C3][C4][G1][G2]
2. The smallest grounded architecture direction is to keep the policy/admission core separate from protocol handling and make the unsupported-client boundary explicit. If the certificate contract is mandatory, investigate a **local transport adapter** that owns the user certificate and keeps publisher credentials separate, or restrict the initial ecosystem set. This is a direction for design, not a verified adapter implementation. An opaque token accepted directly by the firewall would be a deliberate change to the identity/security contract and needs a product decision.
3. A separate protocol adapter must control **both metadata and artifact routes**, writes as well as reads. A universal `Authorization` gate cannot cover Terraform mirror archives as specified. Signed, short-lived download URLs are a documented Terraform option but would add a capability-admission path rather than preserve an unchanged certificate-only path. [T2]
4. Keep outbound registry authentication independent from inbound identity. Docker token realms, Conan login, Galaxy token schemes, NuGet publishing keys, and HF Hub/Xet/CDN flows are protocol behavior, not interchangeable spellings of one API-key header. Do not forward a user's firewall credential or client key to arbitrary registries/CDNs.
5. Nora's authentication features are not a drop-in proof for Probation. Its anonymous Conan limitation and public-only HF mode, plus proxy-only format scope, materially narrow what its seventeen-format count demonstrates. [HF4]

## Gaps and smallest settling checks (not run)

- Pin supported client versions and platforms. For each client, use a fixture HTTPS firewall with a test CA and a distinct user certificate; record successful or absent certificate presentation on **metadata + artifact + authenticated publication** requests. Include a 401 retry, same-host and cross-host redirect, separate artifact host, denied/revoked identity, and upstream publisher login. This is a proposed test, not execution performed in research.
- Cargo/Go: no runtime test is needed to treat native mTLS as unsupported by the cited current public interface. The smallest next design check is whether a local adapter can cover all required URLs without changing lockfile identity, signatures, protocol credentials, or bypassing admission. A future upstream release must be rechecked rather than assumed to implement open proposals.
- Terraform: choose origin-registry versus network-mirror scope, then prove the archive admission path. Header-only authentication is explicitly insufficient for network-mirror archives. Native CLI mTLS is still unknown.
- Galaxy, Pub, CPAN: identify a supported native certificate setting in pinned released client source, or retain unknown and scope to an adapter. CPAN additionally needs a fixed HTTP backend. Do not turn missing documentation into a universal no.
- NuGet: pin a released version containing the observed client-certificate source and test all V3 resource URLs. No minimum release is claimed here.
- PyPI/Ruby/npm/Docker/Maven: documented client certificate options still need publisher and redirect coverage. The PyPI row is pip, not a proof of twine/uv/Poetry.
- HF: explicitly choose HTTP-only models, Xet, and gated/private repositories; a Python HTTP client factory alone does not establish the Xet or stock CLI path.
