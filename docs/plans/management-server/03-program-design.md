## Program behavior
Scenario (success metric 1, C32): a script signs up `ana@acme.test` with a password and confirms the email, which creates the Acme organisation with Ana as org admin. It then creates the key `prb_…` on `/keys` and writes the two `.npmrc` lines (C34). `npm install left-pad` goes to a managed firewall. The firewall hashes the key, misses its cache, asks `POST /api/v1/sync/lookup` and gets `Known` with the key id, Acme's place chain (platform -> Acme) with layer revisions and Acme's rate limit. It fetches the two layers with `POST /api/v1/sync/layers`, resolves the effective policy locally and serves the package under it. Ana then adds a block on `left-pad`. Within one sync interval, `changes` names Acme's layer, the firewall refetches it, and the next `npm install left-pad` is refused and shows in Ana's activity.

Flow (operation IDs from molecule-flow.json; molecule in brackets):
1. `authenticate` [firewall_managed]:
   - No `Authorization` header, an unparsable header, or no `prb_` prefix -> `refused` (401 `AUTHENTICATION_REQUIRED`).
   - A hash hit in a live entry -> `cached`.
   - A miss -> lookup, single-flighted per hash; places whose layers are not cached are fetched with `sync layers`. A known key -> `looked_up`, and the entry is cached with its last-use time. Unknown -> `refused`, and the hash is cached as a negative entry for 30 s (T10). Revoked or suspended -> `refused_known` (401), plus an activity row for the key's place with Layer "none" (C55, C92).
   - An expired entry -> re-lookup. If the server answers, as above. If the server is unreachable -> `stale` (C96).
   - A miss while the server is unreachable -> `refused`.
   - The canonical client IP (IPv4-mapped IPv6 folded to IPv4; behind a listed proxy, C113) is inside an approved range of org X, and the key's org is not X -> `outside_network` (403 showing only the IP, C30, C77, C92), plus an activity row for the key's place. The org's own keys work from anywhere.
   - The key's account (its organisation, or its personal account) is over its requests-per-minute limit on this firewall -> `rate_limited` (429 `TOO_MANY_REQUESTS`, C28, C66, C114). Every key of one account shares one counter.
   - The firewall is retired -> `refused` for every request (C72).
2. `decide` [firewall_policy] -> `allow` (serve), `allow_would_block` (an OSV log-only match: serve and record "would have blocked", C81) or `block_or_hold` (today's 403/hold answers, unchanged in shape). The decision names the rule and the layer it came from (C23, C92). The rendered cache is reused only for the same `PolicyFingerprint`. In managed mode the PyPI root index `/pypi/simple/` answers an empty list, because today it lists every project any client fetched (T8, evidence §6).
3. `record_activity` [firewall_managed] -> a blocked, held or "would have blocked" decision, or a revoked, suspended or network-lock refusal, is queued with its rule, layer and, for a hold, `eligible_at` (C23, C55, C56, C92). The queue is bounded by `ACTIVITY_QUEUE_CAP` (10 000) and drops the oldest event when full; one account may hold at most `ACTIVITY_ACCOUNT_CAP` (1 000) events, and its further events are counted as dropped instead (T18).
4. Policy edit. Precondition: the route first calls `tenancy::authorized_place(session, layer)`, which answers 404 for a place outside the actor's organisations or an unknown one, before any policy is loaded (C1, T9). Then `check_edit` [policy_rules]:
   - Rebuilds the proposed effective policy against the parent's effective policy. A loosening whose switch is off -> `loosens`, and the form re-renders with the blocking switch named.
   - `authorize` [server_tenancy]: the actor's role on the layer's place -> `permitted` or `denied` (403 page).
   - `save_edit` [server_policy]: one transaction, compare-and-set on the layer revision -> `committed` (layer, change_log, audit_log), or `revision_conflict` (the form shows that the layer changed meanwhile).
5. Sync, `fetch_changes` [firewall_managed] every `sync_interval`:
   - `changes` -> `apply_changes` marks changed layers stale (refetched and rebuilt with no key lookups, C111), removes the entries of changed keys (never served stale afterwards) and expires every entry whose chain contains a changed place (suspension, deletion), so it re-looks-up lazily on next use. A `network_lock` member replaces the table. 02 § Change propagation lists which state changes write which rows.
   - `reset` -> `drop_cache`.
   - `retired`, or a 401 for the firewall token -> `stop_serving`: the cache is emptied and every later request is refused (C72).
   - `unreachable` (connect error, timeout after `request_timeout_seconds` (default 2, at most `sync_margin_seconds`), 5xx, 429 or 403 `FIREWALL_SOURCE_REFUSED`) -> the cache is kept, the activity batch is re-queued, and the server is marked down until the next answered sync: while down, expired entries are served stale with no lookup, so requests never wait on a dead server. The sync interval uses `MissedTickBehavior::Delay`. The server's Postgres acquire and statement timeouts (1 s) stay below the firewall's.
   - Any other 4xx (for example 413 or 422) -> the batch is dropped and counted, the cache is kept, and the next call is sent empty (no activity, no drops); if that is rejected too it is treated as unreachable and shown on `/health/ready` and the fleet page. Each call carries at most `ACTIVITY_BATCH_MAX` (1 000) events and 1 000 `activity_dropped` entries, and `last_apply_error` is cut to 2 KiB, below the server's caps (02 § Endpoints).
   - A `settings` member whose revision differs from the applied one -> C105 overlay write and restart.
   - After every sync the caches are snapshotted to `<data_dir>/managed-cache.json`. Entries unused for one TTL are pruned only after a sync the server answered, so an outage never shrinks the cache (C96, W3). At start the snapshot is loaded, so a restart while the server is down keeps serving (C19).
6. Standalone (no `[management]`): `admit` skips step 1. `decide` uses the single `CompiledPolicy` built from `cooldown_seconds`, `osv_mode` and the blocklist file at start and on each blocklist reload, so behaviour is byte-for-byte today's (C12).

### firewall managed (proposed, `src/managed`)
Purpose: turn a request's key into its place and effective policy, keep that fresh, and ship activity.
Owns: `KeyCache` (hash -> `CachedKey { principal, expires_at, last_used }`; 16 `Mutex<HashMap>` shards bounded by `key_cache_max_entries` (default 100 000; while the server is marked down nothing is evicted and a new key that would need room answers 503 `LOOKUP_BUSY`), evicting a full shard's least recently used entry; `remove`, `retain` and iteration serve key removal, place expiry, idle pruning and the snapshot; the existing `ShardedCache` is not reused because it has none of these), the layer cache, the sync cursor, `ActivityQueue`. Unknown answers are cached as negative entries by hash for 30 s (T10); revoked and suspended answers are cached as negative entries by hash for one TTL with the answer's place chain, and a `key` row for the key or a `place` row for any place in that chain expires them, so restoring or re-activating an organisation clears its members' negative entries within one interval. The lookup budget (`lookup_budget_per_second`, default 50) keeps 10 a second for hashes that already have an entry, so a flood of unknown keys cannot starve re-lookups. The layer cache and the interner drop layers and policies no remaining key uses when keys are pruned.

#### fetch_changes / apply_changes / drop_cache (proposed, `src/managed/sync.rs`)
Declarations: `impl KeySync { pub async fn fetch_changes(&self, request: &ChangesRequest) -> Result<Synced, Unreachable> }`, `enum Synced { Applied, BatchRejected }`. The `policy_sync` task keeps the request: on `Unreachable` it re-queues the batch with `ActivityQueue::requeue`; on `BatchRejected` it adds the batch's per-account counts to the queue's drop counters for the next `activity_dropped`. It dispatches the answer `Changes(ChangesResponse) | Reset(ChangesResponse) | Retired | Rejected` to the private `apply_changes(&self, delta: &ChangesResponse)` (mark layers stale, remove keys, expire places, then `advance_cursor`), `drop_cache(&self)` (only on `Reset`, in this order: raise the invalidation floor to the reset revision, clear the key cache, the layer cache and the compiled-policy interner, then adopt the reset answer's full `network_lock`) and `stop_serving(&self)` (set the retired flag, then clear). A 429, or a 403 carrying the `x-probation-error: FIREWALL_SOURCE_REFUSED` header, returns `Unreachable` (the batch is re-queued). Effects: `apply_changes` updates the `rate_limit` of cached entries named by `changed_limits` in place (no lookups): a default row only touches entries whose `rate_limit_source` is `Default` for that account kind, an override row touches that account and sets its source, and the update records `delta.revision` like every invalidation; marks each changed layer stale, so the sync task refetches the changed layers it holds in one `sync layers` call right after the delta (the request path single-flights a refetch per place and counts it in the lookup budget) and every interned policy containing it is rebuilt. It removes exactly the entries for changed keys, so a revoked key is never served stale after the firewall learned of it. It expires every entry whose `chain` contains a changed place, so those re-look-up on next use and keep stale serving if the server goes away. ## Call stack
| Caller -> operation | Value/state passed | Why accepted | Result/failure handling |
|---|---|---|---|
| npm/pypi handler -> `http::admit` -> `managed::authenticate` (managed only) | `HeaderMap`, peer IP from the request context | `admit` already runs first on every route | `Err` -> `ApiError::Unauthenticated` (401), `NetworkNotAllowed` (403), `TooManyRequests` (429) or `LookupBusy` (503); before it, `admit` answers `NotReady` (503); no further work |
| `authenticate` -> `sync lookup` (miss or expired) | `sha256(key)` hex | server matches `keys.hash` | Known -> cache and return; Unknown -> 401; unreachable -> stale or 401 |
| handler -> npm/pypi `resolve` -> `decide` | `&principal.policy` (a `CompiledPolicy`), candidate, `osv_matched` | `authenticated(principal)`; standalone passes the one built policy | `Decision` rendered as today |
| `resolve` -> rendered cache | key incl. `policy.fingerprint` | same fingerprint = same policy | miss -> render and insert |
| artifact download single flight -> each waiter -> `decide` | own policy, verified bytes' digests | bytes verified once; decision per waiter (C104) | each waiter serves or refuses independently |
| `decide` result Deny/Hold/would-block, or an `authenticate` refusal for a known key -> `record_activity` | key id, place, result, rule, layer, coordinates | bounded queue, per-account cap | oldest dropped when full; over the account cap counted as dropped |
| `policy_sync` task -> `fetch_changes` -> `apply_changes`/`drop_cache` | cursor | firewall token | unreachable -> keep cache, retry next interval |
| portal POST `/policy/{layer}` -> `authorized_place` -> `check_edit` -> `authorize` -> `save_edit` | proposed `Layer`, session, form revision | CSRF + session; `Authorized<Place>`, `CheckedEdit` and `EditPermit` only from their constructors | 404 for a foreign place; refusal pages; conflict page |
| server `save_edit` -> firewalls | `change_log` row | next `changes` call from each firewall | reaches each firewall within one interval (C20) |

Whole-flow obligations: W1. Every request a managed firewall serves was decided under the policy of the key it carried (`managed-request`: served terminals require `decided_under(verdict, who)`). W2. A refused edit leaves the layer unchanged, and a saved edit is always change-logged and audited (`policy-edit`). W3. A server outage never shrinks the cache (`sync-changes`: kept terminal); idle pruning (C96) runs only after an answered sync. Execution assumptions are those listed in molecule-flow.json. Correspondence is checked by the source obligations in molecule-contracts.json once the source exists, and by the Test plan.

## Least confident decisions
1. C105, restart on a settings push: simple, but every push briefly drains the firewall. Live reload of the safe settings would avoid that, at much greater cost.
2. C103, fingerprint-keyed rendered cache: memory is shared across every distinct policy under one cap. A fleet with many distinct policies on hot packages will see more misses.
3. Lazy lookup (C2) gives one extra round-trip for a key's first request, and a cold firewall restart re-looks-up every active key.
4. One firewall token per firewall, with every firewall able to look up any key and fetch any layer (shared fleet, C3). A stolen token is limited by its source ranges and rate (T31), but a token stolen from inside an allowed range can read every tenant's layers until the operator retires and re-registers that firewall.
5. Keeping the firewall as the root package rather than moving it to `crates/probation` keeps the diff small but makes the workspace slightly uneven.
