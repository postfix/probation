Slice 3: a managed firewall syncs and keeps serving

What now works. The firewall syncs with the server. A revoked key answers 401 after one sync interval. A network lock refuses requests from outside an organisation's IP ranges (403). /health/ready is 503 until the first sync, then 200. When the server is down, known keys are served from the cache (stale serving). Blocked, held and would-block decisions go to the server as activity rows. Settings pushes are applied, and a failed push is rolled back.

Review findings fixed: late answers are not cached after a key, place or reset change (B1); a pushed log file is checked and a start failure rolls back (B2); IPv4-mapped ranges are read at full width (M1); layers calls are single-flight and inside the budget (M2); activity keeps its time across an outage (M3); no API key in SIEM output (T2); after a database restore, the firewall resets to the lower revision (C126); verification fixes: refused metadata and version requests now record activity, and a pushed log_file_path cannot point at the firewall's own files (S3-8).

Deviations that matter to you:

  • A refused metadata or version request records one activity row. A listing that only hides some versions records nothing (S3-8). A refused PyPI project records one row on every request, cached or not (S3-9).
  • In managed mode, blocklist_file is optional and ignored (S3-5).
  • Product code came before its tests; each red line comes from a named mutant (S3-4).

Slice 4: probation-server on Postgres

What now works. The real sync API answers a real firewall. Policy edits are atomic: the edit, the audit row and the change-log row commit together. The audit log is append-only for the app role. Tenancy keeps organisations apart. The bootstrap CLI creates the first admin, org, key and firewall token.

Review findings fixed: a permit for one place cannot save another place (R1, N3); the role table for keys and fleet is tested (R2); only the firewall that is ahead resets, never all firewalls (C126); the bootstrap audit row names the host operator, not the new admin (F7); activity time is kept and clamped to retention (S4-11); i64::MAX cursor accepted, u64::MAX answers 422.

Deviations that matter to you:

  • The server listens on plain HTTP. TLS ends at a proxy in front ([server] trusted_proxies). Operator docs come in slice 8 (S4-1).
  • Tests were written after the code; reds come from named mutants (S4-10).

Slice 5: sign-up and sign-in in the portal

What now works. People sign up (organisation or personal account), confirm the email, and sign in with a password, Google, GitHub, Microsoft or company SSO. They link and unlink sign-in methods, change and reset the password, turn on an authenticator app (TOTP) with backup codes, and delete or restore the login.

Review findings fixed: TOTP comes before the deleted-login choice (R1); sign-in and TOTP throttles hold under concurrent attempts (R2); mail and sign-up rate limits (R3); an SSO session cannot change the account (R4); a waiting session ends after a password reset (R5); state, nonce and tenant checks are tested (R6); N1-N5 (hash permits, mail-cap keys, pool use, pending-session ends, sign-up cap order); an SSO callback must match the flow's organisation (F4).

Deviations that matter to you:

  • Sign-up refuses a taken organisation name, so it shows that the organisation exists (C127, accepted like A3).
  • SSO adds a user at sign-in; a removed member is not added back by SSO (C128).
  • OIDC uses jsonwebtoken with hand-written checks, not openidconnect. TOTP throttle: 5 failures in 15 minutes (S5-5).
  • The org-admin TOTP reset moved to slice 6 (S5-7). It is delivered there.

Slice 6: organisations, keys and policy in the portal

What now works. Org admins, group admins and users manage members, groups, invitations, API keys, service keys, policy, IP ranges, activity, audit and organisation deletion. Admin roles need a second factor (C24). A key, member or group change reaches the firewall within one sync interval.

Review findings fixed: the second factor is checked on every admin action (B1); removal is remembered by SSO identity (B2); last-admin and invitation races have deterministic tests (B3, M1); the SSO secret is kept only for the same issuer and client (M2); purge and restore do not race (M3); an org admin cannot demote, reset the authenticator and promote back (M4, S6-4); the place switcher posts real values (M5); an invitation needs a live admin sender (S6-SEC-4).

Deviations that matter to you:

  • Activity and audit have no filters; each lists the newest 500 rows. No separate confirmation before revoking a key. No organisation rename (S6-11).
  • The .npmrc and pip.conf lines use a FIREWALL placeholder; the portal has no setting for the firewall address yet (S6-10, open).
  • An org admin cannot reset the authenticator of someone who was an org admin there in the last 30 days; a global admin can (S6-4).
