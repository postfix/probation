## Program behavior
Purpose: let many people and organisations use one shared probation firewall fleet, each under their own policy, and manage that policy, their keys and the fleet themselves from a web portal, instead of editing config files on every firewall.
Capabilities:
- A person signs up (email+password, Google, GitHub, Microsoft, or company OIDC SSO) -> they get an organisation or a personal account, and a login that can hold several places (C5, C6, C29, C75).
- A user, org admin or group admin creates an API key -> the key is shown once; `npm`/`pip`/`uv` requests that carry it are served by any managed firewall under that key's place's effective policy (C13–C15, C34, C99).
- An admin edits a layer's policy (blocks, exceptions, freeze, OSV, the three switches) -> the edit is accepted only if it is stricter, or looser where the layer above allows it; it is audited and reaches every firewall within one sync interval (C8–C11, C16–C18, C20, C25).
- An org admin or an automation token imports, exports or pushes a blocklist in today's JSON format (C80, C86).
- A global admin manages organisations, personal accounts, global admins, the platform policy, network-lock IP ranges and the fleet (registration, settings, retirement, status) (C4, C22, C30, C77, C79).
- Users see blocked and held requests for their place, and admins see the audit log (C23, C25, C26).
- A firewall without `[management]` behaves exactly as today (C12).
Failures:
- A missing, unknown, revoked or suspended key -> the firewall answers 401 with an authentication error naming no account (C13).
- The management server is unreachable -> firewalls keep serving cached keys and policies, including expired entries; new keys get 401 until it returns (C19, C96).
- A looser edit the layer above does not allow -> the portal refuses it and names the switch that blocks it; nothing is saved (C8).
- A request from inside an organisation's approved IP ranges carrying a key that does not belong to that organisation -> 403 showing only the client IP (C30, C77, C92). The organisation's own keys work anywhere.
- An invalid settings push to a firewall -> the firewall keeps its current config and reports the error on the fleet page (C22, C71); a config that fails at the next start is rolled back to the previous file.
- A retired firewall, or one whose token the server rejects -> it stops serving every request at that check-in (C72); this is not treated as "server unreachable".
Programming entry point: none for applications. Supported interfaces are the firewall's registry endpoints, the portal (HTML), the automation blocklist API and the firewall sync API (JSON).

## Endpoints
Firewall (existing routes, changed): every npm and PyPI route under `/npm/` and `/pypi/` requires a key in managed mode — `Authorization: Bearer <key>` (npm) or `Authorization: Basic` with the key as password (pip, uv, Poetry). Health routes stay unauthenticated, and so do `GET /npm/-/ping` and the local `GET /pypi/simple/{project}` redirect to the trailing-slash form: neither touches package data or policy.

Server, firewall sync API (firewall token, JSON):
- `POST /api/v1/sync/lookup` — body `{key_hash}` -> `Known{key_id, org, account, place_chain: [(place, layer_revision)], rate_limit, rate_limit_source[default|override], revision}` (`rate_limit` is the account's requests-per-minute limit: the organisation's, or the personal account's, C28, C67) | `Revoked{key_id, place, place_chain, revision}` | `Suspended{key_id, place, place_chain, revision}` | `Unknown{revision}`, where `revision` is the change-log revision the answer was read at; the firewall drops an answer older than its last invalidation of that key or place, or than the reset floor, or from an ask started before the last reset (C126). The answer is derived at read time: a key whose owner is no longer a member of the key's organisation, or whose group no longer exists, answers `Revoked`; so does a key of a deleted login, organisation or personal account (no window between a removal and a key created concurrently, CO1). Revoked and suspended are 401 on the wire, but they let the firewall record the refusal for the key's owner (C55, C92).
- `POST /api/v1/sync/layers` — body `{places}` -> each place's `Layer` and layer revision, plus the change-log `revision` the answer was read at (dropped by the firewall when older than its last invalidation of that layer or the reset floor, or from an ask started before the last reset, C126). The firewall resolves the chain itself, so a platform edit costs one layer fetch per firewall, not one lookup per key.
- `POST /api/v1/sync/changes` — body `{since, report{settings_revision, last_apply_error?, status: {upstreams: {npm, pypi, osv: ok|unreachable}}, effective_period_seconds, version}, activity[{event_id, …}], activity_dropped: [{account, count}]}` -> one `ChangesResponse{revision, changed_keys[], changed_layers[], changed_places[], changed_limits: [{scope_kind[org|personal], scope_id?, rate_per_min, source[default|override]}], network_lock?: [{cidr, org}], settings?: {revision, toml}, reset, retired}`. `network_lock` is sent in full whenever a `ranges` row is in the delta, on `since = 0` and on every `reset`; the cache snapshot keeps it, with the cursor, across restarts (C115). `settings` is this firewall's own (bound to the token's firewall id) and sent only when its revision differs from the reported one. A rejected token answers 401, which the firewall treats like `retired`. A multi-firewall settings push (C70) is released to one firewall at a time; the next gets it after the previous one reports success. `lookup`, `layers` and `changes` each run in one read-only `REPEATABLE READ` transaction that reads the change-log revision first, so an answer's revision and its data come from one snapshot. A firewall token from a source outside its `allowed_source_cidrs` gets 403 with the header `x-probation-error: FIREWALL_SOURCE_REFUSED`, which the firewall handles like an unreachable server (keeps its cache, reports on the fleet page) — only an unknown or retired token gets 401. The per-token rate is per server copy, so N copies allow N × 200 a second. The body cap is 2 MiB and 1 000 activity events (above `ACTIVITY_BATCH_MAX` × the largest encoded event, ≤ 1 KiB with field bounds, plus a report whose `last_apply_error` is cut to 2 KiB and at most 1 000 `activity_dropped` entries).

Server, automation API (automation token, JSON):
- `GET /api/v1/blocklist/{layer}` — export in today's format.
- `PUT /api/v1/blocklist/{layer}` — replace the layer's blocks.
- `POST /api/v1/blocklist/{layer}` — add blocks.

Server, portal (session cookie + CSRF, HTML; one route group per mockup):
- `GET /o/{org}` (the organisation's sign-in link, C37), `GET/POST /signin` (with an organisation-name field, C37), `/signup`, `/verify-email`, `/oauth/{provider}/start`, `/oauth/{provider}/callback`, `/sso/{org}/start`, `/sso/{org}/callback`, `/totp`, `POST /signout`
- `/account` (methods, TOTP, delete and, within 30 days, restore of the owner's personal account; create a personal account or an organisation, C40), `/keys`, `/policy/{layer}`, `/activity`, `/org/{org}` (members, groups, invitations, SSO, service keys, automation tokens, leave requests), `/audit`, `/admin` (orgs, personal accounts, global admins, platform policy, platform automation tokens (C80), IP ranges), `/fleet` (firewalls, settings, tokens)

## Data
PostgreSQL (C97). Tables with the queries that hit them:
- `logins(id, created_at, deleted_at, restore_until)`; `sign_in_methods(id, login_id, kind[password|google|github|microsoft|oidc], issuer, subject, org_id null, email, password_hash)`, unique (kind, issuer, subject, org_id) and unique email for kind=password (C91). `org_id` is set for org SSO methods, so one shared issuer (e.g. Google Workspace) can serve several orgs, and the SSO callback looks up with the org from its URL. GitHub's subject is the numeric user id; Microsoft's is (tid, oid). Sign-in looks up by (kind, issuer, subject[, org_id]) only, never by email (C75).
- `sessions(id_hash, login_id, csrf_token, expires_at, totp_ok, scope_org_id null)` (`totp_ok` is true for a Google, GitHub, Microsoft or SSO session, which rely on the provider's second factor (C38, A2), and for a password session only after its TOTP step) — every portal request by `id_hash`. A session opened through an organisation's SSO method has `scope_org_id` set: `authorized_place` admits only that organisation's places for it, so one tenant's IdP cannot act for its member in another organisation or personal account. Password reset, password change, TOTP reset and method unlink delete every other session of the login in the same transaction.
- `orgs(id, name, status[active|suspended], deleted_at null, restore_until null, activity_retention_days null, audit_retention_days null, sso_issuer, sso_client_id, sso_client_secret_enc, sso_allowed_tenant null)` (`name` is stored trimmed with each inner whitespace run collapsed to one space, unique (lower(name)), so sign-in by name (C37) finds one organisation and sign-up refuses a taken name with "name taken" and writes no row, C127; `sso_allowed_tenant`: the Google `hd` or Microsoft `tid` the SSO callback requires; mandatory when the issuer is a shared one such as `https://accounts.google.com` or Microsoft's common endpoint, T2), unique (sso_issuer, sso_client_id); `org_ip_ranges(org_id, cidr, approved_by null, refused_reason null)`, with an exclusion constraint so no two approved ranges overlap (C87); `personal_accounts(id, login_id, status[active|suspended], deleted_at null, restore_until null)`.
- `groups(id, org_id, name)`; `memberships(login_id, org_id, group_id null, role)`, unique (login_id, org_id); `invitations(token_hash, org_id null, group_id null, role, created_by, expires_at, accepted_by null)` (accepted with `UPDATE … SET accepted_by = $login WHERE token_hash = $h AND accepted_by IS NULL AND expires_at > now() RETURNING …`, so a link grants exactly once even under concurrent accepts; grant ceiling: an org admin may invite member, group admin or org admin of their own organisation only, with a `group_id` of that organisation; a group admin invites no one (C27); only a global admin, from `/admin`, may invite a global admin) — every role grant, global admin included, is a single-use hashed link accepted by one signed-in login, or an explicit login id picked from the org's member list, never an email lookup; `leave_requests`; `org_removals(org_id, login_id → logins ON DELETE CASCADE)` and `org_sso_removals(org_id, issuer, subject, login_id → logins ON DELETE CASCADE)`, primary key (org_id, issuer, subject): written only by an admin removal of a member, never by an approved leave (C85), in the removal's transaction: one `org_removals` row, and one `org_sso_removals` row per SSO identity of that organisation (`sign_in_methods` with that `org_id`) the removed login holds. The organisation's SSO callback does not auto-join (C5) a login named in `org_removals`, nor a login whose identity is in `org_sso_removals`, so unlinking the method and signing in by SSO as a new login does not re-join either. Accepting an invitation to the organisation deletes the accepting login's rows and the rows of its identities; erasing the removed login (C93 after its 30 days, C94 "Start a new login", the purge, C33) deletes its rows by cascade, after which a new login with that identity joins by SSO again (C128, C130).
- `policy_layers(place_kind[platform|org|group|user|personal], place_id, revision, freeze_seconds, osv_mode, allow_exceptions, allow_osv_off, allow_shorter_freeze)`; `policy_blocks(id, layer, ecosystem null, name null, version null, digest_algorithm[sha256|sha512] null, digest null, reason)` (a package or version block always has ecosystem and name, C31; a file block may carry only its digest, as today's format does, and is lifted by an exact-version exception for the candidate whose artifact carries that digest, C106); `policy_exceptions(layer, ecosystem, name, version null, lifts[block,freeze,osv])` — a lookup loads the chain platform -> org -> group -> user (or platform -> personal) by place.
- `keys(id, hash, last4, kind[user|service|automation|firewall], place_kind, place_id, owner_login null, name, created_at, last_used_at, revoked_at)` (`last4`: the key's last 4 characters, for display only, C99) — `lookup` by `hash` (unique index). A login that loses the role that let it create an automation token (removal, demotion, leaving, login deletion) has those tokens revoked in the same transaction, with an audit row.
- `change_counter(id = 1, value, pruned_through)`; `change_log(revision, at, kind[key|layer|place|limits|ranges|settings|firewall], subject)` — a writer takes the next revision with `UPDATE change_counter SET value = value + 1 RETURNING value` inside its own transaction, so revisions become visible in commit order and a cursor never passes an uncommitted change; `changes` reads `revision > since`; rows older than the retention window are pruned and a `since` before the oldest row gets `reset` (firewall drops its cache and re-looks-up lazily). Rows older than `change_log_retention_days` (default 7, above a snapshot's expected age) are pruned by a job that also advances `pruned_through`; `changes` answers `reset` whenever `since < pruned_through`, so an emptied log still resets a firewall that missed rows; the prune job never lowers `pruned_through`. A `since` above the current revision (a firewall ahead of a restored database) also answers `reset` at the server's current revision, and a `since` that cannot be a bigint answers 422. `changes` never writes `change_counter` or `pruned_through`, so one firewall's cursor never resets another (C126). After restoring the database from a backup, the operator runs `probation-server admin after-restore` on the server host (a CLI command, no API route, so firewall tokens cannot reach it): in one transaction with an audit row it raises `value` and `pruned_through` by 2^32, more revisions than any backup-to-restore gap issues, so both lie above every revision issued before the restore and every firewall resets once on its next sync (C129). The counter only moves up.
- `firewalls(id, name, token_key_id, allowed_source_cidrs not null, settings_toml, settings_revision, last_seen_at, last_report, retired_at)` (`allowed_source_cidrs`: set at registration; `FirewallAuth` refuses the token from any other source; the sync API also limits each token to 200 requests a second, above the firewall's lookup budget, T31; behind a load balancer the server reads the firewall's address from `X-Forwarded-For` only when the peer is in its own `[server] trusted_proxies`). `settings_rollouts(id, created_by, settings_toml, state[running|halted|done])` and `settings_rollout_steps(rollout_id, firewall_id, position, state[pending|sent|applied|failed|timed_out|skipped])`: the `changes` transaction that records a firewall's success releases the next step under a row lock on the rollout; a failure, or no success within 3 sync intervals, halts the rollout and the fleet page shows it with resume and skip actions; a firewall is unhealthy after 3 × its reported `effective_period_seconds` with no check-in (C69); retired firewalls are skipped (C70, C71).
- `audit_log(id, at, actor_login, actor_is_global_admin, org_id null, action, subject, before, after)` — append-only for the app role (INSERT and SELECT only); retention pruning runs only through the argument-less `SECURITY DEFINER` function `prune_audit()` (owned by the migration role, `search_path` pinned), which computes each organisation's cutoff from `platform_settings` and its `orgs` override, never later than `now() - 7 days` (C68), and deletes only older rows (T17, C26). Migrations run as a separate owner role (`PROBATION_SERVER_MIGRATE_DATABASE_URL`), so the app role owns nothing; listed per org or platform by time.
- `activity(event_id, at, firewall_id, place_kind, place_id, key_id, layer[platform|org|group|user|personal|network|none], ecosystem null, package null, version null, result[blocked|held|would_block|refused_revoked|refused_suspended|refused_network], rule, client_ip inet null, eligible_at null)` (`client_ip` only for `refused_network`, C92) — the server derives the place from `key_id`, not from the firewall's report; listed per place by time (C23, C55, C56, C92); pruned by retention (C26). `event_id` is generated by the firewall, and the server inserts with `ON CONFLICT (firewall_id, event_id) DO NOTHING`, so a batch re-sent after a timeout is not duplicated.
- `limits(scope_kind[org|personal], scope_id null, rate_per_min, max_keys, max_service_keys)` (C28, C51, C66, C67); `platform_settings(id = 1, activity_retention_days default 90, audit_retention_days default 365)` with per-org overrides on `orgs` (C26, C68). A fresh install seeds `limits(personal, NULL)` (1 200 requests a minute, 5 keys) and `limits(org, NULL)` (6 000 a minute, 20 keys per member, 50 service keys); `scope_id NULL` is the default for that kind, a row with an id overrides it (C28, C67).
- `email_outbox(id, to_address, template, payload, attempts, next_attempt_at, sent_at null)` — sign-up, verification, reset and invitation mail is written here in the request's transaction and sent by a job with retries; the page shown is the same whether or not the send succeeded (C91), and `/verify-email` offers "resend".

Firewall: no schema change to `firewall.db`. The key cache, layer cache and network-lock table are snapshotted to `<data_dir>/managed-cache.json` every sync and loaded at start, so a restart while the server is down keeps serving (C19); entries unused for one TTL are pruned after the next sync the server answers, so an outage never shrinks the cache (C96). The applied settings revision and the last apply error live in `<data_dir>/managed-settings.state`. `managed-cache.json`, the settings overlay and `managed-settings.state` are each written to a temporary file, fsynced and renamed over the old one (and the directory fsynced), keeping the previous good snapshot as `managed-cache.prev.json`, which start-up loads when the current one cannot be parsed. Before exiting with code 75 after a settings push, the firewall sends one final `changes` call with its queued activity.

## Flow
1. **Managed request** (F-request): `http::admit` -> `Managed::authenticate` checks the retired flag, then reads the one `Authorization` header and computes its SHA-256 hash, and the key never goes further. On a cache hit it uses the cached entry and its interned `EffectivePolicy`. On a miss it calls `sync lookup` (and `sync layers` for places it lacks). If the server is down and there is no entry, the request gets 401. A stale entry is served while the server is down (C96). Unknown keys get 401. Revoked or suspended keys get 401 and an activity row for the owner. If the peer IP (IPv4-mapped IPv6 canonicalised) is inside an approved range of org X and the key's org is not X, the request gets 403 and an activity row. The rate limit is counted per account (the organisation, or the personal account, C28) on each firewall (C114); a request over it gets 429 `TOO_MANY_REQUESTS` (C66).
2. **Policy edit** (F-edit): portal form -> `tenancy::authorized_place(session, layer)`: a place outside the actor's organisations (or unknown) answers 404 before any policy is loaded (C1, T9) -> `probation_policy::check_edit(parent_effective, stored_layer, target, proposed)` (only what the proposal adds or widens is checked, so settings kept under C47 never block a save) -> `tenancy::authorize(actor, checked)` (role, 403) -> `policy::save_edit`. The edit is refused when it loosens a rule whose switch is off, and nothing is written. On acceptance, one Postgres transaction writes the layer, bumps its revision, appends `change_log(layer)` and appends `audit_log`.
3. **Sync** (F-sync): on a fixed-rate interval of `sync_interval − sync_margin` (so a change is applied within `sync_interval` including the round trip) the firewall sends `changes(since)` with its report and activity batch. A changed key's entry is removed, so it is never served stale afterwards. A changed layer is refetched lazily and every effective policy that contains it is rebuilt, so a parent-layer edit reaches all descendants without a single key lookup (C111). A changed place (suspension, deletion) expires every entry whose chain contains it, so the next request re-looks the key up. A `network_lock` table replaces the old one. A `reset` drops the caches. A `retired` answer or a 401 stops all serving (C72). A `settings` member is validated, written to the overlay with the previous overlay kept, and the firewall drains and exits with code 75. At the next start an overlay that fails startup validation is replaced by the previous one, and the error is reported in the next `changes` call (C71).
4. **Key create/revoke** (F-key): `tenancy::authorized_place` and the role check -> `keys::create` returns the key once and stores its hash. `revoke` sets `revoked_at` and appends `change_log(key)` and the audit row.

Shared/external mutation: only the server writes Postgres. Each firewall writes only its own memory caches and three files under its `data_dir` (cache snapshot, settings overlay, settings state). Concurrency: the key cache is the dedicated sharded `KeyCache` (§ Fit), and lookups for the same hash are single-flighted so a burst triggers one server call. Several server copies (C97) share no memory, and every invariant lives in a Postgres transaction.

### Change propagation
Every state change a firewall caches is written to `change_log` in the same transaction as the change, so it reaches every firewall within one sync interval (C20). A `key` row removes that key's entry; a `layer` row marks that layer stale, so it is refetched and the effective policies containing it are rebuilt, with no key lookups; a `place` row expires every entry whose chain contains the place, and the next request re-looks it up; a `limits` row updates the rate limit of the cached entries it covers in place; `ranges` resends the full network-lock table; `settings` and `firewall` go only to the named firewall.

## Constraints
- `delivery::Decision` is 240 of 256 bytes (evidence §7). Managed mode adds `place: Option<u32>` with `skip_serializing_if = "Option::is_none"` (248 ≤ 256 bytes), so standalone NDJSON and SIEM lines are byte-identical to today (C12). The key and key hash never enter it.
- `.smtc/analyzers/client-data-reaches-delivery-sink.yaml` forbids `request.headers()`-style reads, and ADR 0001 allows exactly one `extensions` read. The `Authorization` value is read from the handler's `HeaderMap` in exactly one function, `managed::authenticate`, which no record or log reaches. The peer IP for the network lock comes from that same single `extensions` read in `logging::decide`. Today the server is built with connect-info only when `log_consumer_identification` is on (src/lib.rs:286-310), and the address stays local to `logging::decide`. Managed mode therefore always builds the server with connect-info, `logging::decide` reads the address when the opt-in is on or `[management]` is set and stores it in `RequestContext`, and `admit` reads it from there. `Decision.consumer` stays gated on the opt-in, so standalone output is unchanged (C12). ADR 0001's one approved read now also serves the network lock (an addendum in slice 2).
- The firewall has no live config reload (evidence §5), so a settings push restarts the process. That needs a supervisor restart policy: slice 8 ships `docker-compose` and systemd examples with `restart: unless-stopped` / `Restart=on-failure`. The image's `/etc/probation` is root-owned, so pushes are written only under `data_dir`.
- C83: the cached path adds one SHA-256 of about 36 bytes and one map lookup per request. OSV keeps today's order: it is asked only after an OSV-blind Allow and never when the policy's OSV is off, so managed mode adds no OSV traffic.
- Single crate today: moving to a workspace keeps every existing path and test. The root `Dockerfile` gains `COPY crates ./crates` so `cargo build --locked` still builds the release image, and CI (`.github/workflows/rust.yml`) runs `cargo test --workspace` and `cargo clippy --workspace`; the existing `cargo llvm-cov --fail-under-lines 98` gate keeps covering the root package only, so new firewall code (src/managed, src/policy/effective.rs) must keep the root package at 98% lines, while `probation-policy` and `probation-server` are not under that gate; from slice 4 CI also starts a Postgres service for `cargo test -p probation-server`.
- Deployment: behind a reverse proxy, the proxy's addresses go in `[management] trusted_proxies`, or the network lock sees the proxy's IP (C113, T23). Direct termination needs nothing.
- The four existing analyzers keep their documented roots and pass conditions (`client-data-reaches-delivery-sink` and `consumer-identity-extension-read` on src/http/logging.rs as today; `outbound-timeout-guard` and `enqueue-timeout-guard` at their documented counts on src/osv). New code gets its own runs with zero breach findings (an info-severity "obligation vacuous" record is not a breach): `--root src/managed`, `--root src/tasks/policy_sync.rs` and `--root crates/probation-server`. So the server reads inbound data only through axum extractors (`HeaderMap`, `Json`, `Form`, `Path`, a cookie jar) and never calls `headers`, `body`, `into_body`, `to_bytes`, `extensions` or `from_request*` on a receiver expression containing `request`, `req` or `parts` (which includes `reqwest` paths); the SSRF-guarded OIDC adapter binds its builder to a neutral name before `.headers(..)`/`.body(..)`. Every outbound `send` (reqwest, lettre, channels, test code included) sits in a function that also calls `timeout`. The reference shapes for src/managed were run this way on a synthetic snapshot: zero findings (evidence/analyzer-roots.md).
- A managed firewall with a broken `[management]` section or an unreadable token file refuses to start. It never falls back to standalone (T20).
