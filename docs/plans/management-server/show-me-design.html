Plan management-server. You decide only on what changed since the last approval (git diff 60f007c~1 09d5f4a). Everything approved earlier stays approved.

What problem do we have?

During delivery you answered five questions that change the approved design. These are C126–C128 (slices 3–5) and ABQ1/ABQ2 from Design QA, recorded as C129 and C130. The router refused to complete slice 3 (SOURCE_CONTRACT_REQUIRED) until the design is approved again. Without these changes:

  • After a database restore, a firewall whose cursor is at or below the server's revision gets no reset. It silently skips the post-restore changes that reuse its revision numbers, so it could miss a revocation (C129).
  • When SSO is on, a member that an admin removed is added back at their next SSO sign-in (C5, C128).

How will we solve it?

Purpose. After a restore, every firewall resets once and misses nothing, and no firewall can move the shared revision. A member that an admin removed stays out until they accept an invitation created after the removal, or until the removed login is erased.

Flow: database restore and firewall reset (C126, C129)

Recommendation: Approve. Design QA is READY with no blocking findings. The counter only moves up, a firewall token still cannot reset other firewalls, and the SSO block applies only to an admin removal while the removed login exists.

Limits:

  • C129 rests on two premises that are not checked: the clock is not rolled back, and changes are written at fewer than one per microsecond. A restore is safe only after the operator runs the command.
  • N2 (QA, non-blocking): 02–04 do not name which clock after-restore reads. An NTP step backwards matters like a rollback, up to the size of the step. You were told that slice 8 will use the database clock, Postgres clock_timestamp(). That is not yet written in 02–04, and any edit to 02–04 needs a fresh QA review.
  • All new checks are planned and none has run. The slice 4–7 implementations are on worktree branches, so QA relied on their evidence files.
