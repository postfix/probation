## Program behavior

Purpose: the firewall promises it does not lose decision records below its rated load, but no
number anywhere says what that load is, and an operator has no lever when their traffic exceeds
it. This feature measures the number, publishes it with the outage tolerance it implies, asserts
a floor automatically so a collapse cannot ship unnoticed, and turns the fixed queue capacity
into two configurable per-sink memory budgets.

Capabilities:

- An operator reads a rated figure and a default outage tolerance in the operator documentation.
  The rated figure is produced by a benchmark in the repository they can re-run on their own
  hardware; the tolerance is computed from the stated 200 requests-per-second reference load and
  the bench's bytes-per-record constant (C39).
- An operator raises either sink's delivery queue budget by configuration and buys headroom,
  trading host memory for records held.
- An operator alerts on `GET /health/delivery` returning non-`200` and learns that records are
  being shed without reading log records.
- A contributor running `cargo test` fails the run if the delivery pipeline collapses below the
  published floor.

Failures:

- Offered load above the queue's capacity: records are dropped and counted exactly as today
  (`src/delivery/mod.rs:113-118`), package serving is neither slowed nor failed, `/health/ready`
  stays green, and `/health/delivery` reports `503`.
- A budget set too small to hold a single record: rejected at configuration load as `Invalid`
  (`src/config.rs:385`), the same shape as every other bad value, so the process refuses to start
  rather than running with a zero-capacity queue.
- A budget key set while its sink is off: rejected at load, matching `log_file_max_bytes`'s
  existing rule (`src/config.rs:239-244`).
- The benchmark run on a busy machine: it reports a lower figure; it does not fail. Only the
  `cargo test` floor fails a run, and it asserts zero drops rather than achieved throughput
  (C11).

Programming entry point: none. `mod delivery` stays `pub(crate)` (`src/lib.rs:13`) and this
feature adds no public Rust API. The load driver reaches the sinks through the existing
default-off `test-support` feature (C17), which is how `set_summary_window`
(`src/http/logging.rs:461`) and `set_response_timeouts` (`src/http/limits.rs:98`) already work.

## Flow

Main path, unchanged except where noted:

1. `Config::load` (`src/main.rs:122`) parses the two new optional budgets and applies their
   defaults inside `RawConfig::validate`, the mechanism `log_file_max_bytes` already uses
   (`src/config.rs:245-250`).
2. `App::start` → `delivery::build` (`src/lib.rs:161`) converts each budget to a record count by
   dividing by the `BYTES_PER_RECORD` constant (C15) and passes it to `mpsc::channel`
   (`src/delivery/mod.rs:214`, `:250`) in place of `QUEUE_CAPACITY`.
3. A request is served; `http::logging::decide` (`src/http/logging.rs:150`) builds a `Decision`
   and calls `Sinks::offer` (`src/http/logging.rs:243`), exactly as today.
4. **Every site that loses a record increments the window counter, increments the monotonic
   total, and marks the shedding state** — all three, not the marker alone (C21, C33, C34), and
   not only `Sink::push` (C21) or only the sites that increment a counter today (C27). The
   monotonic total is what the measurement path reads and what makes
   `offered − delivered == dropped` a real assertion; the marker is what makes the alarm
   truthful. Seven sites increment a
   counter now: `push` itself (`src/delivery/mod.rs:115`), the file sink's four
   (`src/delivery/file.rs:75`, `:105`, `:142`, `:181`) and the SIEM sink's two
   (`src/delivery/siem.rs:97`, `:212`). An **eighth** site loses a record with no counter at all —
   the SIEM serialize-failure branch inside `batch.drain(..)`
   (`src/delivery/siem.rs:113-135`, verified at `:120-126`) — and C27 gives it one, as the file
   sink already has at `src/delivery/file.rs:105`. The marker reaches the sink tasks the same way
   the counter already does, by widening the `Arc<AtomicU64>` cloned in at
   `src/delivery/mod.rs:221` and `:258`; that widening also carries the **monotonic
   non-resetting total** the measurement path reads (C33). Every write is a relaxed atomic: no
   lock, no allocation, no clock read on the request path, and `push` stays non-`async`,
   lock-free and infallible to its caller (`src/delivery/mod.rs:7-9`), per C24.
5. `http::health::delivery` reads the shedding state and the clock (`app.clock.now_utc_micros()`,
   as `ready` does at `src/http/health.rs:31`) and returns `200` or `503`. It never calls
   `Sinks::drops()` (C16).
6. Unchanged: `close_window` (`src/http/logging.rs:415`) still reads and resets the counters into
   `dropped_file` / `dropped_siem`, and `flush_drop_tail` (`src/http/logging.rs:399`) still
   reports the drain tail.

Measurement path (C32): the bench or the floor test starts an `App` **with at least one sink
actually configured** — an empty `Sinks` makes `offer` a no-op (`src/delivery/mod.rs:141`) and any
zero-drops assertion vacuous (C28) — then drives HTTP requests at `/health/live` at a target rate
for a stated duration. Each such request emits exactly one decision record through the full
per-request path, so the achieved figure is requests per second in the sense C2 promised. The
driver then **shuts the `App` down, so drain is cancelled and the sink tasks are joined, before
reading the tally**: the late drop sites (`src/delivery/file.rs:75`, `src/delivery/siem.rs:97`,
`:212`) fire during the drain, and a tally read earlier reports zero for a run that lost its whole
tail (C28). It reads the **monotonic non-resetting total** through the one `test-support`
accessor, never `Sinks::drops()` — the App consumes that itself on every summary window close
(`src/http/logging.rs:421`) and at shutdown (`:400`), so a driver reading it would measure only
the drops since the last window (C33). It returns offered, dropped and achieved directly, and
`delivered` as an **independent count of distinct `request_id` values among `RequestDecided`
records observed at the destination** — not raw arrivals, because the SIEM collector receives
batches of up to 256 and re-posts them on retry, and the log file also carries `RequestSummary`
lines — so that `offered − delivered == dropped` is a real assertion rather than an identity
(C34). For the file sink the harness sizes `log_file_max_bytes` for the whole run and asserts
`<path>.1` does not exist, since `Writer::roll_over` (`src/delivery/file.rs:205`) would otherwise
destroy earlier generations mid-run; a rotated run is void, not under-counted. The bench runs the
product's **ten minutes sustained**
(C30) and prints, including the `BYTES_PER_RECORD` derivation (C37). The floor test runs a short
duration and asserts both limbs (C28).

## Constraints

- **`Sinks::drops()` is read-and-reset** (`swap(0)`, `src/delivery/mod.rs:155`, `:159`) and its
  doc warns a second concurrent caller steals a window's counts. The health route must read
  separate state (C16). This is the single most likely way to implement this feature wrongly.
- **A channel's capacity is fixed at construction**, so the byte budget is converted once, at
  `build` time; there is no runtime re-sizing (C15).
- **`mod delivery` is `pub(crate)`** and a bench target is an external consumer, so the load
  driver must sit behind `test-support` (C17).
- **Adding a configuration key touches four places** and `tests/config_validation.rs` deletes
  each sample key in turn, so a key added to `RawConfig` but not to `OPTIONAL_KEYS` and
  `config.sample.toml` fails the existing suite (C20).
- **`config.sample.toml` is load-bearing**: `tests/common/mod.rs:36` `sample_config()` is the base
  configuration for all 19 integration binaries, so a new required key would change every test.
  Both new keys are therefore optional with defaults.
- **Debug-build timing is not a safe assertion target** — `tests/artifacts_concurrency.rs:991`
  is the existing scar (C11).
- **No CI exists** and this plan does not add one (C14).
- **Criterion is deliberately absent** (`Cargo.toml:77-82`); the new bench follows the existing
  `harness = false` pattern (C19).
- **Every site that loses a record must do all three things: increment the window counter,
  increment the monotonic total, and mark the shedding state** (C21, C27, C33, C34). The
  invariant covers all three, not the marker alone: the shedding signal is only truthful if the
  marker reaches every site, and `offered − delivered == dropped` only holds if the monotonic
  total does too. A site that sets the marker but misses the total makes the floor test's
  reconciliation fail on a healthy run; one that misses the marker makes the alarm lie. Not only
  the queue-full site (C21), and not only the sites that increment a drop counter today (C27). The
  queue-full case is the *least* silent failure; it is already visible as `dropped_file` /
  `dropped_siem` on the summary record. The dangerous cases drain at full speed and never fill
  the queue. There is an eighth loss site with no counter at all: in `siem::send`, a record that
  fails to serialize is discarded inside `batch.drain(..)` under
  `if let Ok(line) = serde_json::to_string(&record)` (`src/delivery/siem.rs:113-135`) while the
  surrounding `Unsent` still reports the batch delivered. The file sink counts the identical
  case (`src/delivery/file.rs:105`); the SIEM sink must too.
- **No lock, allocation, syscall or clock read may enter `Sink::push`** (C24). This rules out any
  clear-rule for `/health/delivery` that timestamps in the drop path.
- **The capacity arithmetic is validated in `config`, against the same constant**, and uses
  `usize::try_from` rather than `as usize` (C23). `mpsc::channel(0)` panics, and this config
  module exists to reject bad values rather than crash on them.
- **`Decision.method` is bounded with `loggable`** so `BYTES_PER_RECORD` is a real ceiling
  (C22). Without that, the published budget is a false guarantee.
- **The load driver and every visibility widening it requires stay inside
  `#[cfg(feature = "test-support")]`** (C25); no `src/main.rs` or non-`cfg` path references it.
- **A record dropped by a sink must remain on stdout.** `tracing::info!`
  (`src/http/logging.rs:224`) runs *before* `offer` (`:243`), and that ordering is what keeps the
  audit trail complete when the durable sinks are lossy. No change may reverse it.
- **`Sinks::drops()` has exactly one consumer, the App's own summary path.** Neither the health
  route (C16) nor the measurement driver (C33) may call it. The driver reads the monotonic
  non-resetting total instead; the health route reads the shed marker. A second caller of
  `drops()` silently steals a window's counts (`src/delivery/mod.rs:148-149`).
- **Deferred to Gate 3, as inventory rows rather than prose**: C35, the clear rule for
  `/health/delivery`, constrained by C24; and C36, whether the budget keys get a sanity ceiling
  (T8). Gate 3 imports both under those IDs.
