## Findings

### F1  Medium  confirmed (mechanism, by source trace; not measured)  src/nuget/serve.rs:787-808 `serve_registration_index`, 861-875 `allowed_for`, 887-900 `serve_search`, 940-954 `serve_vulnerability_file`, 967-984 `serve_signature_certificate`
Attacker: any caller that can reach the route (login-free common-service route, or any certificate-admitted client); no credential needed against nuget.org-like public registries.
Path: (a) `GET v3/registration/{id}/index.json` always calls `refresh_with_docs` (serve.rs:797), which bypasses the 5 s `SERVICE_SHARE_TTL` and the project TTL: every request costs 2 + up to MAX_PAGES (256) upstream fetches (4 in flight), a DB commit of 4 reference rows per version (up to max_references_per_project = 20000 rows) and an OSV evaluation of every version. (b) `GET v3/query?q=..&take=50` fans out to up to `SEARCH_TAKE_CAP*2` = 100 ids (serve.rs:894), each `current_project` + `judge`; credential-bearing reads (not cacheable by C1028) refresh every project every time, so one request is up to about 100 x 258 upstream calls plus DB writes. (c) `v3/vulnerabilities/{base,update}.json` fetch the index and the file (cap 128 MiB, `body.to_vec()` copies it again) on every request; `v3/repository-signatures/certificates/{fp}.crt` fetches every signature index until a fingerprint matches, on every request. None has a per-request deadline, a shared single-flight or a global concurrency bound beyond `max_active_requests` (1024).
Ineffective defense: caps bound one request (pages, ids, bytes) but not the work a caller can repeat; no coalescing for the uncached documents.
Effect: an anonymous client turns each request into hundreds of upstream calls and thousands of DB row upserts (egress amplification against api.nuget.org from the firewall's IP, which can get the whole deployment throttled; database and CPU exhaustion; permits held for the duration, so a 503 `Overloaded` for others). Slice 19 F4 is the same class.
Smallest correction: (1) route the registration index through the same credential-free share cell as `current_project` (serve a fetched `RegDocs` for a few seconds per (registry, origin, id)); (2) one process-wide semaphore (say 16) for project refreshes started by search/autocomplete and a hard cap of `SEARCH_TAKE_CAP` ids, with undecided ids dropped instead of waited for; (3) cache the vulnerability index and files and the signature indexes for a short TTL for credential-free reads (same cell type as `services`), and stream or cap files below 128 MiB (the real base file is a few MiB). Cost: one small cache type and one semaphore. Closure: unauthorized-action check: 1000 concurrent `registration/{id}/index.json` and 50 `v3/query?take=50` against a slow upstream fake keep upstream calls per second and permits bounded and leave `/healthz`-class requests served; legitimate check: nuget_registry and nuget_service_read tests (registration filtering, search, vulnerability, signatures) still pass.

### F2  Medium (shared class, new route)  confirmed (source)  src/http/nuget_routes.rs:211-248 `forward_write`
Attacker: anyone who reaches the common-service route (login-free) or any certificate-admitted client. Needs a registry whose service index is readable without a credential (nuget.org and public mirrors).
Path: the only pre-spool credential check is "some non-empty `X-NuGet-ApiKey` or `Authorization`" (nuget_routes.rs:213-217); the value is never validated. `publish_target` then needs only the public service index. The body is then written to an unnamed temp file in `data_dir` up to `cap = 2 x max_artifact_bytes` (default 5 GiB, so 10 GiB) before upstream is asked anything.
Effect: N concurrent requests with `X-NuGet-ApiKey: x` (N up to `max_active_requests` 1024) pin up to N x 10 GiB of disk in the same data directory as the store (every other family's reads then fail with `StorageUnusable`), and the firewall relays the bytes to www.nuget.org from its own IP. Cargo (cargo_routes.rs:272-335) and RubyGems have the same pattern, so this is a shared design defect, not specific to NuGet; it is listed here because the route is new.
Smallest correction: forward the body as a stream to the registry without spooling (the upload is not read twice), or spool only after a cheap upstream pre-check; at least bound concurrent spools (a semaphore of a few) and use the per-registry write cap, not 2 x artifact cap. Cost: a small semaphore (the minimum); streaming changes the recheck-after-body design. Closure: unauthorized: 20 parallel 1 GiB uploads with a junk key do not exceed the spool bound; legitimate: `shared_service_forwards_nuget_writes_with_the_callers_own_key_only` and an oversize write still 413.

### F3  Low (hardening)  confirmed (source), plausible exploit only with a hostile index  src/nuget/serve.rs:194-226 `registry_root`/`selected_root`/`origins_for`, src/upstream/origins.rs:145-167
Question asked: a private feed's resources may live anywhere on its own host. A selected NuGet registry's set is `selected_npm_with_private(root)` with the path reset to `/`, so every resource URL that the registry's service index names is admitted on that scheme, host and port at any path. The URLs fetched with the registry's credential are: flat, registration, search, autocomplete, vulnerability and signature URLs, and the write target (with the caller's API key and `Authorization`).
Assessment: the index is the registry operator's own document and the operator already receives the credential, so no new trust is granted to a tenant. SSRF is closed: https only (selected sets reject http), same host and port, DNS and connected-peer guards with the registry's CIDRs plus the LS-F9 denylist, no query/userinfo/fragment (`plain_url`), `.`/`..` refused (`url_below`), registration page links confined under `{registration}/{id}/` (serve.rs:438-455), redirects of credentialed reads not followed (metadata) or limited to the same origin and no credential on the hop (artifact loop, reqwest_transport.rs:375, which also closes slice 19 F2). The residual risk is a path-partitioned multi-tenant or gateway host (for example one API gateway that also fronts other internal services by path, or a provider whose index an attacker can edit): a hostile or compromised index can steer the stored/caller credential and the write key to any path of that host, including another tenant's feed. The Go slice kept the path prefix of the target; NuGet widened it to the whole host because Azure Artifacts, GitHub Packages and Artifactory name resources outside the index directory.
Correction without breaking those layouts: add an optional descriptor field (like `archive_origin`, additive, ignored by an old enforcer) that narrows the admitted path prefix, defaulting to the whole host so no layout breaks; the portal can suggest the first path segment (Azure `/org/`, GitHub `/OWNER/`, Artifactory `/artifactory/`, Nexus `/repository/`) and must not default to it, because root-hosted BaGet puts the index at `/v3/index.json` and the publish endpoint at `/api/v2/package`. Layouts of Azure and GitHub are from memory, not measured here. Cost: one nullable column and one check in `origins_for`/`selected_root`. Closure: unauthorized: with the prefix set, an index naming `https://host/other-tenant/...` is skipped; legitimate: the real layouts above and `a_selected_registry_is_read_from_its_own_layout_through_both_roots`.

### F4  Low  confirmed (source)  src/nuget/serve.rs:940-954, 967-984
Signature certificates are relayed without checking that the bytes hash to the fingerprint the index names, and vulnerability files are relayed unparsed as `application/json`. Only the registry's own documents are involved (a hostile registry is already the source of truth), so no new trust is crossed. Hardening: compute SHA-256 over the DER of the certificate (or its PEM body) and refuse a mismatch; both are one comparison. See also F1 for the buffering cost.

### F5  Low (hardening)  confirmed (source)  src/http/nuget_routes.rs:253-262
The write response relays the upstream status (any code the transport lets through) and the upstream `Content-Type` as sent, with the upstream body capped at `max_metadata_bytes`. A registry that answers `text/html` makes the firewall origin serve HTML to a browser that fetches the route. The client of this route is a NuGet client, not a browser, and no portal shares the origin in the shipped deployment, so impact is limited. Correction: force `application/json` or `text/plain` plus `X-Content-Type-Options: nosniff` for write responses. Cost: two header inserts.

### F6  Low (informational)  confirmed (source)  src/nuget/doc.rs:174-182, src/http/nuget_routes.rs `parse`
Plain-http signature resource: closed as designed. `RepositorySignatures` is not advertised when the public URL is not https (NuGet itself refuses it), and its absence fails towards the client verifying package signatures alone; the route itself still answers over http for a client that hard-codes it, which is harmless (it relays the registry's own document). The vulnerability index is advertised over http, so audit data over plain http is unauthenticated for an on-path attacker (NuGet's own http-source refusal limits this to clients that set allowInsecureConnections). Documented limit only.

### Unknown (inherited class, not new)  src/nuget/serve.rs:398-403 `publication_of`, src/nuget/doc.rs:228-246
The cooldown date is the registration leaf's `published`. nuget.org assigns it server-side; Azure Artifacts, Artifactory and GitHub Packages assign it from upload time as far as is known, but a self-hosted feed (BaGet, NuGet.Server) may take it from the package or a request. Slice 19 F1 applies to any such feed: a back-dated `published` skips the freeze. The code treats an absent, unparseable, pre-1970 or 1900 sentinel date as "no date" (first-seen), which is the safe direction, and the date is merged with `max` over duplicate leaves. No test models a publisher-chosen date. Decision for the user, as in slice 19; check needed: which feeds the organisations register.
