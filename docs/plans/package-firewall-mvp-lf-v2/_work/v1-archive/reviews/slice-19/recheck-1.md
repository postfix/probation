## New findings

N1 (Medium, availability, blocking) revision window is global per (registry, module) and per process, not per principal; trivially exhausted.
Where: serve.rs `admit_rev`, `Shared.revs`; MAX_REVS_PER_WINDOW 32, MAX_REV_MODULES 1024.
Scenario A: any holder of a read key (a hostile or merely buggy client; in the shared service, another tenant of the same registry) sends 32 distinct junk tokens for module M (`/go/M/@v/a1.info` ... `a32.info`; each counts even though upstream answers 404). Every other client's `go get M@main` is 429 for the rest of the minute and the attacker repeats once a minute (about 0.5 req/s). `go` has no fallback behind the single GOPROXY, so the resolve fails hard. The same junk for 1024 different dotted module names (admit_rev runs before any upstream call, so the module need not exist) makes `revs.len() >= 1024` with no expired entry, and then every rev query of every module returns 429 while the attacker keeps the table full (1024 req/min).
Scope: only `mod@branch/commit/short` resolution; pinned versions, @latest and lists are unaffected. Not data exposure.
Fix (small): key the count by principal (the key or client identity the admission already gives) in addition to, or instead of, the module; keep a per-module ceiling several times higher; count only tokens upstream did not answer 404 for? (a 404 token still costs one upstream call, so keep it counted but per principal). Test: two principals, one exhausts, the other still resolves `main`; and a full table of 1024 modules from one principal does not block a second principal.
Tests that exist (bounded per module) pass and would still pass after the fix if they use one principal.

N2 (Low-Medium, known, a decision exists) U-1 is not fixed on the shared-service route.
The retry loop in `selected` is real but the shared-service middleware (service_registry.rs:77-80) wraps the finished response in its own `PreparedResponse` stamped with the generation read at request start and returns 503 for ANY publication in between; a handler cannot retry. So a `go` client through `/registry/go/...` still sees the same 503 on a publication that changes nothing it needs (go does not retry a 503). Evidence "Decision 1" already states this for the other families; for Go it is the family most exposed. Not a security issue. Recommendation: either accept (documented) or let the middleware re-dispatch the request once on a gate refusal for GET/HEAD reads (one admission each, bounded at 3), which keeps SPEC §9 (the new policy decides). Needs the user's yes because it touches shared middleware.

N3 (Low, test gap) the retry test never publishes a policy that changes the answer.
`go_request_released_across_a_policy_publication_is_admitted_again` publishes `|| ()` (no change), so it proves "served after 0..2 publications, 503 after 3" but not that a block (or a stricter age/OSV) published between authorisation and release is refused by the re-admission. By reading, it is: each attempt calls `admit` again (new principal and snapshot), re-parses, and `locally_blocked`, `resolve`, OSV and `serve_artifact_in` decide under it; the refused response is dropped (permit and pin returned) before any byte is sent, and `release` uses the same `respond_order` and authority as `into_response`. So no bypass found. Add one case: the barrier publishes a blocklist containing the version, assert 403 (not 200, not 503). Cheap, closes the exact question "a block published mid-request cannot be bypassed by the retry".

N4 (Low, race) `witness` can overwrite a just-recorded date with NULL.
`witness` reads `existing`, then upserts the not-yet-present Info rows with `publication_micros: None`; the store does `INSERT OR REPLACE` and carries only first-seen, pins and content key (store/mod.rs carried_forward), not publication. Two overlapping FIRST lists of one module (the leader's fan-out `record` committing V's date between the follower's `existing` read and its commit) leave V's stored publication NULL. The in-memory table keeps the date, so serving is right until restart, eviction (MAX_DOCS 128) or a credentialed throwaway table; then `record` merges `stored = None` and the upstream date is trusted again (monotonic "only later" is lost for that version, first-seen is kept so it only matters for a re-dating upstream). Fix: `witness` should not write rows that exist (it already filters) and the store upsert should carry `publication_micros` forward when the new value is NULL (same as first_seen), which also hardens `record`.

N5 (Low) small-transfer pool: constant 64, no waiter bound, no size cap.
`small_download_permit` skips `max_download_waiters` (waiters are then bounded only by `max_active_requests`, default high) and ignores `max_artifact_downloads`: a deployment that set the large pool to 2 now allows 66 concurrent transfers. A `.info`/`.mod` is fetched with `max_bytes = max_artifact_bytes` (download.rs:241, 509), not the 256 KiB the evidence lists as the Go `.info` input, so a hostile or compromised upstream can hold small places with large "tiny" files (go itself refuses a go.mod over 16 MiB). No per-registry or per-tenant limit exists to bypass (limits are global), so there is no new cross-tenant bypass, but the pool lets one slow `.mod` stream per place starve tiny reads again. Fix: cap Go `.info` at INFO_CAP and `.mod` at 16 MiB in the transfer (`cap` by kind), and reuse the waiter bound. Evidence "LS-F7 Go inputs" text is wrong until then.

N6 (Low, behaviour/decision) a pseudo-version of a module whose list was seen is held a full cooldown from first request, order-dependent.
Fix-round decision 2 (recommended keep). Concrete cost: a project pinning an old pseudo-version (`golang.org/x/foo v0.0.0-2023...`) builds fine until anyone (a `go get -u`, `go list -m -u`) lists that module through the firewall; a fresh CI then gets 403 on that pinned pseudo-version for one cooldown (default 7 days in the tests), although go.sum pins it. The same pseudo-version asked before the first list is trusted. The behaviour depends on which request came first. It is fail closed and delay only, and listed for the user; I recommend the user is told the CI consequence (an exception entry for the version is the existing escape). Not a defect of the fix.

N7 (Low, cost) after a restart or table eviction a long list re-dates from nothing.
`judged_list` computes `missing` from the in-memory table only, though the store already holds each version's date; the 64-per-request cap then withholds old versions of a long module for ceil(n/64) requests after every restart, and with more than 128 active modules (MAX_DOCS) the cells thrash. Fail closed; no loss of data. Cheap fix: seed the table from the store's publication_micros for versions of the list (one query already made by `list_project_first_seen_in`).

N8 (Low, hardening) `witness` writes one reference row per listed version (up to max_references_per_project/3, plus the marker) for every list of any module a read key asks; a read-key holder walking many large modules grows the store by identity rows. Same class as other families (noted in the first review); mention only.

## Answers to the specific questions

1. Revision path. Token validation happens before any upstream call and before the bound (tests assert zero calls for invalid ones). The 32/minute bound is global per (registry, module) across all principals (N1), so a hostile client can deny `go get mod@branch` for everyone; plus the 1024-module table cap (N1). No cache poisoning: the rev answer is never served or cached by name (the delivered `.info` is the resolved version's own `.info` fetched through the pipeline and pinned); the resolved `Version` must be a canonical version, goes through `locally_blocked`, `record` (max of remembered, stored, upstream Time; first-seen floor after the baseline) and OSV, and is judged again by the pipeline (Q6/Q15 equivalent mutants are correctly equivalent). A held resolved version is 403 and its .mod/.zip are never fetched (tested).
2. First-list marker. Marker and first list are one transaction with one `now`; first-seen is never replaced (carried_forward), so two racing first lists keep the earlier marker and versions keep their first sight; the baseline persists in the store across restart. A hostile upstream list cannot make old versions look new (witnessed at first list, floor applies only to versions first seen after the baseline), but a hostile or flapping upstream can make versions look new by returning a truncated first list (later complete lists then hold the older versions one cooldown: availability only, same trust as the upstream). It cannot make a new version look old except through the documented first-list trust and any version asked before the first list. Remaining defects: N4 (row overwrite race). The marker row (`@list`, baseline.invalid) is never advertised, so it cannot be served.
3. Release-gate retry. Re-admission re-runs the whole decision under the new principal and snapshot (blocks, age, OSV, authority); the refused response is dropped before bytes leave; same `respond_order` as `into_response`; at most 3 admissions then 503. I found no bypass; the guarding test does not exercise a changing policy (N3). The FIX-16-A/C1028 invariants are intact (credentialed reads still use throwaway tables and request-scoped files; `release` falls back to `into_response` when there is no authority, as before). Lists and `@latest` are not gated at release in the key route, same as the other families' metadata. The shared-service route cannot use the retry (N2).
4. Small pool. See N5. No bypass of per-registry/tenant limits (none exist); not a memory problem (streams to disk); the connection bound grows by 64 and ignores config.
5. try_lock followers. They get a correct, policy-gated answer for what is dated (judged per request with the follower's own policy/OSV; dates are policy independent, and credential-bearing reads never share a cell). A follower on a cold module can return an empty or short list while the leader works (`go` then asks @latest; transient, fail closed). Staleness is bounded by the existing exists-TTL and the list's own `checked` refresh.
6. Credentialed hop and archive prefix. Correct (F2 table above). The archive redirect requires a `.zip` transfer and a URL under the configured path prefix (segment-bounded), and the registry credential is not sent past the first request.
