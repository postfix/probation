## New findings
N1 - medium - non-blocking - the certificate-mode token is valid on one process only
Location: src/oci/serve.rs `OciState.token_secret` (random per process, serve.rs:134-138), `check_local_token` (serve.rs:1532), called from `run` for every read in certificate mode (oci_routes.rs `run`).
Scenario: two firewall instances behind one L4 balancer (mTLS passthrough). A client gets a token from A, the next request lands on B: B answers 401 with the challenge, the client fetches a new token (maybe from A again) and retries (maybe on B again). With round-robin per connection, pulls fail with "unauthorized" at a rate that grows with the instance count; a restart also invalidates every token for up to 5 minutes. docs/operations.md says only "keyed by a secret that exists only in this process" and does not state the multi-instance consequence. Before the hardening a constant token worked on every instance, so this is a regression for an HA deployment.
Why it is not blocking: a single instance and sticky connections work (containers reuse one connection); the token grants nothing (admission is the client certificate), so the only effect of validating it is to refuse forged tokens, which protects nothing.
Correction options: (1) state in operations.md that the certificate-managed OCI route needs one instance or connection affinity; or (2) derive the secret from a configured value shared by the fleet (cost: a new secret to manage and rotate); or (3) do not validate (accept any `probation-pull-` bearer, since admission is by certificate). Option 3 is the smallest and loses nothing real.

N2 - low - non-blocking - upload lane eviction frees lanes that still have holders
Location: src/oci/serve.rs `upload_lane`, `map.retain(|_, lane| Arc::strong_count(lane) > 1)` (serve.rs:686-688).
Scenario: the permit returned to the caller owns the semaphore `Arc`, not the `Arc<Lane>`; the local `lane` is dropped when `upload_lane` returns, so a lane whose two layers are streaming has strong_count 1 and counts as idle. When the table holds 1,024 owners and a new owner arrives, that lane is removed; the same owner's next layer gets a fresh semaphore and the lane size (2) is exceeded, up to the per-owner spool seats (4). Needs 1,024 distinct owners (client /64s or accounts), so it is a bound that bends, not an open door; the byte reservation and seats still hold.
Correction: keep the `Arc<Lane>` inside `UploadLane` (one field), so strong_count reflects holders. Test: fill the table with idle owners, hold a lane with two permits, add one more owner, assert the held lane is still in the map.

N3 - low - non-blocking - sha512 spelling: a block by sha256 acts after the download, not at manifest time
Location: src/oci/serve.rs `judge` (children checked as the manifest's own digest texts), `read_children`.
Facts: a manifest that names a layer by sha512 is not refused for a block on that layer's sha256 (the text differs); the layer is refused at the blob request once its bytes have arrived and its sha256 is computed in the same pass (verified: test a_layer_named_by_sha512_is_served_verified_and_judged_by_its_sha256, probes U3a/b). No byte is released. Cooldown is NOT affected: `register_children` dates the sha512-named child row with the manifest's first-seen, so the cooldown holds without knowing the sha256. Cache-key confusion: the two spellings are two rows, one content (sha512 key of the store), policy identity sha256; I found no path where one spelling is served that the other would refuse after the bytes have been computed.
What full parity would need: after the first fetch the row holds both pins (`pin_computed_digests`); `judge` could look up the sha512 child rows by their pin and run `blocked_anywhere` on the stored sha256 (one store read per sha512 child; the first manifest pull still cannot know it). Cost: an index of rows by sha512 pin. Acceptable as it is; a registry that stores blobs only by sha256 answers 404 for a sha512 request anyway, so such manifests are rare.

N4 - low - non-blocking - spawned first-pull work is not cancelled when the client leaves
Location: src/http/oci_routes.rs `early_blob` (`tokio::spawn`, handle dropped with the response body).
Scenario: a client takes the headers and disconnects; the spawned `serve_artifact_in` runs on (download and hashing of up to `max_artifact_bytes`), holding download places, while its active-request permit has been released with the body. Bounded by the download gate (per-owner and per-registry places), and the ordinary path already lets a single-flight download continue for its waiters, so this is not an escalation; it lets an owner use download places without a held connection. Note only.

## Verified (the points asked)
(a) R1 lane. `big_body`: manifest never; PATCH always; PUT/POST when declared above 1 MiB, undeclared with a non-empty body; `is_end_stream` for the empty POST. Dodges tried: declared 1 MiB then more bytes: hyper h1 stops the body at the declared length, h2 resets the stream on a mismatch. Chunked with a small `Content-Length`: hyper 1.11.1 removes `Content-Length` when `Transfer-Encoding: chunked` is present (role.rs:271-280), so `declared` is None and the lane is taken. Small requests hold no lane and, while a request waits, no active-request permit (`drop(permit.take())` before the wait, `active_permit()` after; probe R1c killed); waiters capped at 6 per owner with a `Waiting` guard released on every exit; the lane permit is an owned guard held to the end of `forward_write`. A small request is therefore not starved by lane waiters. Residual, inherent and pre-existing (slice 17 seats): small slow bodies (declared 1 MiB at the rate floor) hold a spool seat each, so one owner can use its 4 seats with small requests; N2 above for the eviction edge.
(b) R2. `token_origin` additive on the wire: `#[serde(default, skip_serializing_if)]`, no `deny_unknown_fields` on `CertificateAdmission`, so an older firewall ignores it (refuses such a realm, fail closed) and a newer firewall reads an older server's answer as None. The firewall re-validates it (https, no path, query, fragment or userinfo; else the admission is refused). Realm must equal the declared origin exactly (`realm_allowed`, same scheme/host/port), realms are never taken from the request; the transport's guarded resolver (denylist first, then the registry's CIDRs, then the peer check) applies to the token host. `oci_token_url` is checked by `upstream_origin` (https, no userinfo/path, address literals checked). Credential exposure: only the caller's own Basic (shared service) or the registry's stored read credential is sent to the declared token origin; the setter is the org admin who also chooses the registry target, so a tenant can aim its own registry's credential at a host it names but gains nothing it could not do with `target_url`. Not a new primitive. A certificate principal without a target uses `oci_token_url`, not the admission's value (no server path sets one in that case).
(c) R3 foreign layers. `admits_foreign`: https, no explicit port (`:443` normalises away, other ports refused), no userinfo, no fragment, host lower-cased by the url crate (IDN is punycode and never equals a list entry), IP literals refused, trailing dot refused (no equality), `..` refused, wildcard requires a dot before the suffix and a non-empty label (`evilmcr.microsoft.com.attacker.tld` and `xmcr.microsoft.com` refused for the exact entry; `*.data.mcr.microsoft.com` does not match the bare `data.mcr.microsoft.com`). Config validation allows `*.co.uk`-style wide entries by operator choice (names with two labels or more): operator risk, documented as the operator's list. Fetch: no credential (`ambient_authorization` returns None off the registry origin; transport refuses a credential with a foreign URL, probe R3c2/R3d), redirects only when both previous and next are listed, https only. SSRF: DNS is vetted in the resolver at connect time for every host (denylist first, any non-public answer refused unless in the registry's approved CIDRs, answers dialled are the ones vetted), then the connected peer is re-checked: a listed host that resolves to a private address is refused, except inside a registry's approved private CIDR (an on-prem registry's own CIDR also admits a listed host resolving into it: needs control of that host's DNS; low, not a finding). Size cap: `max_artifact_bytes` through `capped`. Digest verified in the shared pipeline before any byte is delivered (test a_foreign_layer_whose_bytes_are_not_its_digest_is_never_released). `judge` checks every child digest (config, layers incl. foreign, nested manifests) against `blocked_outright` and `blocked_anywhere`, records the refusal, and refuses the manifest (probe R3b). Note: a manifest names a foreign URL per digest and a later manifest of the same repository may repoint that row to another listed URL (integrity still by digest); only a pusher of that repository or the registry itself can do it.
(d) U3: see N3.
(e) U1 early headers. Order in `run`: reference_for_blob (blocks, existence), then `preflight` (the same `evaluate` as the pipeline: policy validity, row, blocks, cooldown, OSV) BEFORE the registry HEAD and before any header: a blocked or held digest gets its refusal status, never 200 headers; length and `Docker-Content-Digest` are sent only after the policy allowed the digest, so the early path discloses nothing a 200 would not. Headers go out with `Content-Length` = the registry's HEAD length; the body is `once(work.await)`: the body stream yields no byte before `serve_artifact_in` has finished (download, hashing, digest compare, file on disk); a mismatch, a policy change since the preflight (`evaluate` runs again inside), a non-200 or a length different from the announced one becomes an `io::Error` item: hyper aborts the connection, and with `Content-Length` set an HTTP/1.1 client sees a truncated body, not a clean end (h2: stream reset). Because the length is checked against the announced one, a short or long file cannot end cleanly (U1b is an equivalent mutation, kept as second line, as the evidence says). HEAD, Range and sha512 are not on this path (`!head && range.is_none() && sha256`). A blob already on disk, a foreign layer and an unknown length take the ordinary path. Residual: a status code cannot be corrected after the headers (a policy flip between preflight and verification shows as a reset, not a 403): rare, stated in the evidence. N4 for client disconnect.
(f) Token. `probation-pull-<expiry>.<hmac>`: HMAC-SHA256 by hand, RFC 4231 vectors tested; message binds expiry, the principal's place kind and id, and the registry id; validation checks the prefix, expiry in `(now, now+300]`, and compares the tag without an early exit (full-length XOR fold, length checked); presented only when a request carries `Bearer probation-pull-...`, else admission is by the certificate. Replay across registries and places is refused; tokens are per place, not per certificate (all holders of one place share a token, which is harmless: the token authorises nothing). Secret from `getrandom` at start. Multi-instance: N1.
(g) Q23: one process-wide `tokio::sync::Mutex` around count, compare and raise; it is held across the single DB count only when the one-minute cache is cold; ordering with `row_gate` is row_gate then repository_gate everywhere (no cycle found). The counter is raised before the row commit, so a refused or failed new repository counts for up to one cache window (60 s): a slight overcount, fail safe. Test simultaneous_new_repositories_do_not_overshoot_the_repository_bound, probe Q23 killed.
(h) `podman image prune -f` removes every dangling image of the user, not only the implementer's: harmless (dangling images are unreferenced and rebuildable; cost is a cold rebuild), but it deviates from "remove only your own". Note only.
