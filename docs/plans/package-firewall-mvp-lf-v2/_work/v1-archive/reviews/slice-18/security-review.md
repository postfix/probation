## Findings

No critical, high or medium finding.

L1 low, resource (accepted ceiling, same as RubyGems R1). `spellings` is process-local and cleared at 4096 tracked crates, so after a restart or after an admitted client touches 4096 distinct crates the 4-spelling cap resets. Scenario: against a lenient private registry that answers every `-`/`_` spelling, a client mints up to 2^n spelling variants per crate, each one upstream fetch plus up to 20,000 reference rows (ids include the filename), never pruned. Public crates.io answers only the published spelling, so it is not reachable there. Pins and first-seen are also per spelling (R6 analog), requiring a registry that changes bytes of a version. Correction if wanted: persist a per-(registry, canonical) spelling count or key pins by lower-case filename. Record the user's acceptance in the ledger (the ponytail comment is there already). Non-blocking.

L2 low, functional/contract: the `login_url` challenge exists only on the legacy handlers (`config`, `index_*`, `download`). In shared-service mode the middleware rewrites `/cargo/...` to `/registry/cargo/{id}/...`, which is served by `selected_*` with no `challenge()`, and the 401 there is `UpstreamUnauthenticated` (upstream's 401) with no `WWW-Authenticate`. Scenario: private upstream that needs a token, Cargo with no token configured gets a bare 401 instead of the challenge that makes it run its credential provider. No confidentiality impact; test gap too (only tests/managed_mode.rs covers the challenge, in managed key mode). Correction: apply `challenge` to `UpstreamUnauthenticated` on the selected handlers (login_url = the registry's public root) and add one service-mode test. Non-blocking, but it contradicts the evidence line that says a 401 carries the challenge; either fix or narrow the claim.

L3 low, availability amplification: in shared-service mode every index read refetches the index with no validators (`refresh(..., over_age=true, None)`), and every download does two index fetches (`reference_for_download`, then `ensure_fresh_project_in`) plus, for request-scoped reads, up to three `config.json` fetches per request (no cell when not cacheable). A `cargo fetch` of 500 crates is about 1,000 index fetches to index.crates.io, each a full body up to 1.5 MB, each also followed by a store commit of all reference rows. Bounded by admission permits; admitted callers only. Same design as the other families in service mode; flag for rate-limit risk against crates.io. Correction: send validators in service mode for cache-eligible reads, or memoise per request.

L4 info, memory: one index can be 64 MiB (shipped `max_metadata_bytes`) and is held as payload plus a `Vec<Entry>` whose `line` strings duplicate the text, and `parse_entries` runs two to three times per request. Peak per request about 3x the body, times concurrent permits. Real maximum is 1.5 MB, so the shipped cap is 43x; consider a Cargo-specific lower cap (the 16 MiB floor already meets LS-F7). Not exploitable by crates.io; matters only for a hostile private registry.

I1 info, defence in depth: `own_origin` for Cargo accepts `NpmMetadata` and `CargoIndex` as artifact origins in standalone mode too, where `NpmMetadata` is registry.npmjs.org. Not reachable today because `reference_of` pins every stored `upstream_url` to the archive origin, but a corrupted or migrated reference row would be fetched from npm's host. Correction: choose the slot list by whether `origin` is Some.

I2 info: index lines pass `deps[].registry` through unchanged. Cargo resolves a dependency that names another registry URL against that URL (subject to the user's source replacement), so a hostile private registry could steer a build to an index the firewall never sees. crates.io forbids such dependencies, so not reachable on the public source. Consider dropping or refusing lines with a non-null `registry` that is not this registry, if the user wants the "nothing bypasses the firewall" property for private upstreams; this would be a deliberate byte-for-byte exception, so it needs the user's explicit yes.
