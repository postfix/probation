## Findings

### RC2-1 MEDIUM: the RELEASE-PACKAGE marker can be removed; an unmarked package installs with one status line when `gh` is absent (sh and ps1)
install-service.sh:343-352 (`verify_binary`), :365-372 (`verify_cosign`), install-service.ps1:204-208, :217-225.
The marker is the only thing that turns "missing gh, cosign or bundle" into a refusal. It is itself unauthenticated: `SHA256SUMS` lists it, but SHA256SUMS sits in the same directory. Scenario: a package modified in transit (binary replaced, SHA256SUMS regenerated, `RELEASE-PACKAGE`, bundle and old SHA256SUMS entry removed) on a host without `gh` (the normal state of a Windows server): `release=0`, the code takes the `say`/`Say` branch, prints `==> gh is not installed: ... NOT verified`, and installs the binary as a service. A dev or non-release package is not distinguished from a stripped release package, and the message is a plain status line, not the `WARNING` used for `--no-verify`. With `gh` installed the attestation check still catches a replaced binary (it is by digest), so the hole is the no-gh case. Caveat that bounds it: whoever can change the package can also change `install-service.sh` itself, which nothing verifies, so this is a defence against partial tampering and operator error only. Fix: when `$HERE/probation` is installed and the marker is absent, require an explicit `--dev-package` (or the same `--allow-unverified`) and print the WARNING line; keep the unmarked soft path only for `--binary`. Also say in operations.md that the archive itself must be verified (it is attested: `probation-*.tar.gz` and `.zip` are subjects) before the script inside is run.

### RC2-2 LOW: provenance is skipped silently when the binary path is spelled differently
install-service.sh:340 (`[ "$BINARY" = "$HERE/probation" ] || return 0`) and ps1:`$shipped`. `--binary ./probation` or `-Binary C:/pkg/probation.exe` is not string-equal to the computed path, so gh and cosign are not run and nothing is printed (the ps1 still checks the hashes). Operator-chosen, not attacker-reachable, but "verified when shipped" turns into "unverified, no message". Fix: compare resolved paths (`realpath`, `GetFullPath`), and print one line when verification is skipped for a non-shipped binary.

### RC2-3 MEDIUM (plausible, unexecuted): the Homebrew `libcrypto.a` may reference zlib; there is no `-lz`
src/managed/enterprise_certificate.rs link attributes; Cargo.lock has no libz-sys. The Linux experiment in the evidence already fails exactly this way (undefined zlib symbols from Debian's libcrypto.a). If Homebrew's openssl@3 archive is built with zlib, the macOS static link fails at the same point. The new PR job `static-link` will show it, and the failure is fail-closed (red PR, no release), so it is not an exposure. Cheap closure: add `#[cfg_attr(all(feature = "static-openssl", target_os = "macos"), link(name = "z"))]` (libz is always in the macOS SDK). The evidence correctly says the Homebrew archive case is unverified.

### RC2-4 LOW: cosign identity regexp is a prefix with unescaped dots
install-service.sh:373 and ps1 cosign call: `^https://github.com/<repo>/\.github/workflows/release\.yml@refs/tags/` has `github.com` and the repository path unescaped and no end anchor. Binding is to this repository's release.yml on any tag; the issuer is exact. Not exploitable beyond what a tag push by a maintainer already allows. Prefer `--certificate-identity` with the exact `...release.yml@refs/tags/<tag>` when the tag is known (the package name carries it), or escape the dots. `PROBATION_RELEASE_REPO` (environment) selects the pinned repository; acceptable for root-run installers, and it is not documented as a trust input.

### RC2-5 LOW: launchd `healthy()` under `pipefail`
install-service.sh:`healthy`: `launchctl print "$target" | grep -q 'state = running'` runs under `set -o pipefail`; `grep -q` exits at the first match and `launchctl` can then die of SIGPIPE, giving pipeline status 141 and a spurious "not healthy" (rollback of a good upgrade). The output is normally under the 64 KiB pipe buffer, so it is a race, not a certainty. Fix: `out=$(launchctl print ...) && case $out in *'state = running'*) ;; *) return 1;; esac`. Also the first poll follows `kickstart -k` immediately; a job in "spawn scheduled" would roll back. The Linux path has a `sleep 1` before its check; add one for launchd. Logic is tested with a stand-in only (as the evidence says).

### RC2-6 LOW: `is_shared` hard-codes the service name `Probation`; owner rule is strict for the service itself
src/key_acl.rs `is_shared` (`service_sid("Probation")`) versus install-service.ps1 `-Name` (any name). With `-Name Foo` the installer grants `NT SERVICE\Foo` on the config directory; an elevated `check-config` at upgrade (self = admin SID, allowed = admin plus the SID of "Probation") reports `NT SERVICE\Foo` as outside and rejects a configuration that sets `service_policy.service_key_file`: fail-closed, but the upgrade is refused. Also a key file owned by the administrator's user SID (made in a non-elevated shell) fails the owner rule when the service itself runs the check (self = service SID): fail-closed, the message names the owner. Fix: take the service name from the service configuration or from the service host, and say in operations.md that the key file must be owned by Administrators or SYSTEM.

### RC2-7 LOW: key_acl details
- Service SID derivation is correct: SHA-1 of the UPPER-CASED name in UTF-16LE, five little-endian DWORDs, prefix `S-1-5-80` (the test pins the documented NT SERVICE\TrustedInstaller value, 956008885-...-2271478464). The ps1 `Get-ServiceSid` is the same algorithm (`Text.Encoding.Unicode`, `ToUpperInvariant`). Note the Windows upper-casing is locale-independent invariant mapping; both sides use Unicode simple upper-casing, same for ASCII names, which the `-Name` pattern enforces.
- NULL DACL: `D:NO_ACCESS_CONTROL` (also `...PNO_ACCESS_CONTROL`, and no `D:` section) is refused; `D:NO_ACCESS_CONTROLS:` (flags run into a SACL) falls to the `None` arm and is refused too. Empty `D:P` grants nothing, tested. Deny, inherited and object/callback ACEs behave fail-closed (reported) or correctly (deny ignored).
- A process running as LocalService or NetworkService gets self `S-1-5-19` while SDDL prints `LS`; a mismatch makes it fail-closed. Not a defect for the shipped virtual account.
- Reader (`cfg(windows)`): GetNamedSecurityInfoW arguments are right (owner, group, dacl, sacl nulls, then the descriptor); every system allocation is freed. `buffer` is a `Vec<u8>` cast to `TOKEN_USER` (alignment 1 versus 8): technically undefined, works with every real allocator; use `Vec<u64>` or `read_unaligned`. Cross-compiled for gnu only; MSVC target and runtime NOT executed.

### RC2-8 LOW: ps1 trust, residual
- `Assert-Trusted` is applied to the directory being created and to its parent, but an EXISTING directory is checked only for itself and for reparse points up the chain, not for the owner of its parent; an attacker-owned `C:\ProgramData\Probation` holding an Administrators-owned `config` is not reachable without admin action, so low.
- The "private" test (`Test-DaclPrivate`) is sound for the directory's own DACL (Allow entries only, SIDs only, `Translate` failure terminates = fail-closed, deny ignored, CREATOR OWNER allowed). It does not look at children: a non-empty directory whose DACL is private but whose contents were planted while it was open is accepted. Owner must already be Administrators/SYSTEM/TrustedInstaller, so only an admin could have made it; the empty-directory takeover has a small window between `Get-ChildItem` and `icacls`.
- Order: directories and config.toml are created BEFORE the package is verified (`Install-BinaryFiles` calls `Assert-PackageHashes` after the config step); a refusal triggers `Invoke-InstallRollback`, which removes what this run created. The binary is verified before it is copied, as claimed, but "verification runs before any copy" in the evidence means "before any binary copy".
- `& gh ... *> $null` and `& cosign ... *> $null` under `$ErrorActionPreference = 'Stop'`: in Windows PowerShell 5.1 native stderr redirected with `*>` can surface as a terminating error; the effect is a refusal (fail-closed) or, for a passing `gh` that writes to stderr, a spurious refusal. Unexecuted; check on the runner.
- Paths are quoted in the service command line and passed to icacls as array elements; `Test-SafePath` bars quotes, `$ % & ; | < > ^` and backtick. No unquoted-path defect found. `-NoVerify` warns with `Write-Warning`; a DLL in the package is refused even under `-NoVerify`.

- Release asset names: the sigstore bundle is `probation-<VERSION>-<target>.sigstore.json` (the archive name without extension), while operations.md and the installers' messages say `probation-<target>.sigstore.json`. Installers look for `probation.sigstore.json` or `--cosign-bundle`, so the documented rename step is required. Cosmetic.
