## Findings

### RC1-1 HIGH, blocking, mechanism certain, unexecuted: the x86_64-apple-darwin release build links an arm64 libcrypto.a
.github/workflows/release.yml build matrix (`macos-latest` for both `aarch64-apple-darwin` and `x86_64-apple-darwin`), step `node tests/e2e/native/openssl-setup.mjs apply`, src/managed/enterprise_certificate.rs:231 (`kind = "static"` on macOS), openssl-setup.mjs:49-52 (`-L native=$(brew --prefix openssl@3)/lib`).
`macos-latest` is an arm64 runner; Homebrew there is /opt/homebrew and its libcrypto.a is arm64 only. The x86_64 target gets a static archive of the wrong architecture: link fails (undefined `_d2i_X509...` / "built for macOS-arm64"). `build` needs it, so no release is cut. The packaged-artifact smoke (service-macos) builds and tests only aarch64, so the gate does not see this. Closure: build the x86_64 archive on an Intel runner or with an x86_64 libcrypto.a (second Homebrew prefix, or vendored openssl-src), and add the x86_64 package to the smoke (`otool -L`, hidden formula).

### RC1-2 HIGH, blocking, plausible (not compiled): the static MSVC link plan mixes CRTs and omits gdi32
src/managed/enterprise_certificate.rs:231-236, openssl-setup.mjs:44-60,95-97, release.yml build-windows, native-service.yml service-windows.
- vcpkg triplet `x64-windows-static` builds OpenSSL with the static CRT (/MT). Nothing in the repo sets `+crt-static` (no .cargo/config, no RUSTFLAGS), so rustc links the dynamic CRT (/MD). A /MT libcrypto into a /MD executable gives LNK4098 (defaultlib LIBCMT conflicts) and commonly LNK2005 duplicate CRT symbols, or two CRTs in one process. This is the reason vcpkg-rs picks `x64-windows-static-md` when `crt-static` is off. Closure: `vcpkg install openssl:x64-windows-static-md` (and the matching root in `staticRoots`), or build with `-C target-feature=+crt-static` for the whole release. Verify on the runner.
- OpenSSL's documented link set for the static library is ws2_32, gdi32, advapi32, crypt32, user32. The attributes list ws2_32, crypt32, user32, advapi32 and not gdi32. Add `link(name = "gdi32")` or prove it unnecessary at link time.
- Features and Linux/macOS safety: there is no openssl-sys, no native-tls and no build.rs in the tree (Cargo.lock has `openssl-probe` and `aws-lc-sys` only). aws-lc-sys prefixes its symbols, so it does not clash with a second libcrypto. The cfg_attr split leaves Linux and the GNU Windows target unchanged (verified by the Linux test run). Consequence of the change: on macOS and MSVC a plain `cargo build` now needs `libcrypto.a` / `crypto.lib` on a `-L native=` path at the time the lib crate is compiled (a `kind = "static"` library is bundled into the rlib), where the old dynamic attribute linked the SDK's libcrypto on a Mac. A developer Mac without the openssl-setup flags can no longer build (Medium, see RC1-9). The failure here is fail-closed (the gate goes red), but the slice's Windows acceptance depends on it, and the fix is a one-word triplet change.
- The installer's refusal of a package that holds a DLL (install-service.ps1:166-168) is correct and removes the DLL planting vector; it is only as good as the link plan above.

### RC1-3 MEDIUM, blocking for the "security check" claim: key_acl accepts a NULL DACL (full access for everyone) as private; and its self-SID rule can reject the legitimate service ACE
src/key_acl.rs:37-49 (`dacl_start`), 59-66 (`is_shared`), config.rs:1029.
- Proof (compiled and run here): `trustees_outside("O:BAG:SYD:NO_ACCESS_CONTROL", sid)` returns `[]` (private). SDDL writes a NULL DACL as `D:NO_ACCESS_CONTROL`; the flag check at :43 accepts any all-uppercase-and-underscore flags text, finds no ACE, and reports nothing outside. The doc comment and tests/key_acl.rs cover "no D: section" and `D:P` (empty ACL), not this form. A key file whose DACL was set to NULL (a planting owner can do it) passes. Closure: treat `NO_ACCESS_CONTROL` as `(no DACL: everyone)` and add the test.
- The allowed set is SY, BA and the SID of the process token. The installer's installed layout grants `NT SERVICE\Probation` on the config directory (ps1:114), and that ACE is inherited by a key file in it. `check-config` run by the elevated installer at upgrade (ps1:367, :373) or by an operator has the admin's token SID, so the service SID is reported as an outside trustee and an upgrade with `service_policy.service_key_file` set is refused ("rejects config"). Install-time passes only because the ACE is added after `Test-Config`. Plausible (not run on Windows). Closure: accept the service SID `S-1-5-80-*` derived from the configured service name, or run the validation with the service SID as the "self".
- Not checked at all: the owner of the key file (an owner holds implicit WRITE_DAC, so a non-admin owner with an otherwise private DACL can re-grant itself) and the parent directory. Original brief item "owner": unmet. Deny ACEs, inherited ACEs (the `ID` flag is not special-cased, so they count), aliases (WD, BU, AU, OW, CO are all reported) and callback/object ACE types (`OA`, `XA`, `ZA`, nested parentheses in a condition, still yielding the trustee field) behave fail-closed or correctly; `is_shared` returns true on any read error (fail-closed).

### RC1-4 MEDIUM: Windows installer skips the release attestation when SHA256SUMS is absent; and it has no cosign
scripts/install-service.ps1:169 (`if (-not (Test-Path $sums)) { return }`) comes before the `gh attestation verify` block at :177-181. Deleting SHA256SUMS from a tampered package turns off both the hash check and the attestation check even where `gh` is installed. Closure: refuse a package without SHA256SUMS (or run the attestation check first). The `.ps1` also never verifies the cosign bundle the release publishes (only install-service.sh does), so the Windows binary is covered by a soft, skippable attestation check only.

### RC1-5 MEDIUM: cosign/gh verification is soft and not pinned as tightly as claimed
scripts/install-service.sh:337-359.
- Pinning that is right: `--certificate-identity-regexp '^https://github.com/<repo>/\.github/workflows/release\.yml@refs/tags/'` plus `--certificate-oidc-issuer https://token.actions.githubusercontent.com`: bound to this repository and the release.yml workflow on a tag ref, issuer fixed. Cosmetic: the dots of `github.com` and the repo string are unescaped regex. The repository comes from the environment variable `PROBATION_RELEASE_REPO` (an attacker who controls the installer's environment chooses the identity; root-equivalent, Low).
- Soft: no cosign installed, no bundle, `--binary` instead of the packaged binary, or no `gh`: the install proceeds with a message. Removing the bundle from a package disables the check. The evidence says this ("else says it was not verified"), so it is honest, but "cosign verification" is not an enforced control.
- `gh attestation verify --repo postfix/probation` (sh:341, ps1:178) is not pinned to a workflow or ref: any workflow in the repository with `attestations: write` could mint an accepted attestation. Add `--signer-workflow postfix/probation/.github/workflows/release.yml` (and a ref).
- The test stand-in `cosign` is `exit N` (tests/service_scripts.rs:391): the identity and issuer arguments are never asserted. Removing a flag would not fail a test (real cosign would refuse, so the failure mode is closed).
- Release permissions: `id-token: write` is granted at release.yml:178 (`release` job, which also has `contents: write`) and :213 (`attest`, with `attestations: write`); the workflow level is `contents: read`. Scoped as claimed, `cosign-installer` and `attest-build-provenance` are SHA-pinned, the release job compiles nothing. Unguarded: check_workflow.py has no rule on `id-token` (an added `id-token: write` on another job would pass).

### RC1-6 MEDIUM: upgrade rollback does not detect "validates but does not start" on macOS; the evidence overstates it
scripts/install-service.sh:527-532 `healthy()` returns 0 unless `PLATFORM = linux`. `launchctl kickstart -k` succeeds even if the process dies, so a macOS upgrade to a binary that passes `check-config` and exits at bind is never rolled back. The evidence row "CR25-5 sh: ... the new service must stay up five seconds" is true only for Linux (and the test uses systemd --user). The Windows script has the check (`Wait-Stays-Up`, authored). Closure: poll `launchctl print system/<label>` for a running pid for five seconds, and test with a stand-in plist as for systemd.

### RC1-7 MEDIUM: ps1 `Assert-Trusted` compares localized owner names and ignores the DACL of existing directories
scripts/install-service.ps1:89-92. The owner is matched as text (`BUILTIN\Administrators`, `NT AUTHORITY\SYSTEM`, `NT SERVICE\TrustedInstaller`, and an unanchored `\\Administrators$`). On a non-English Windows `NT AUTHORITY` and `BUILTIN` are localized, so the check on `C:\ProgramData` itself (parent walk, ps1:101) refuses every install. The CI runner is English and cannot show this. The unanchored alternative also accepts `ANYDOMAIN\Administrators`. Compare SIDs (`S-1-5-32-544`, `S-1-5-18`). Separately an existing directory owned by Administrators but still inheriting `C:\ProgramData`'s "Users may create files and folders" ACE is accepted without resetting its ACL (an operator who ran `mkdir` first): Users can then plant entries (a `data` junction) inside it. Apply the protected ACL to a pre-existing directory too, or refuse when its DACL grants Users or Everyone.

### RC1-8 LOW: install-local.sh trap can leave state user-owned
scripts/install-local.sh:57-70 (`finalize_ownership`), trap set in the SYSTEM_INSTALL branch. With `set -u`, an abort before `CERT=` is assigned (for example `useradd` failing) runs the trap; `chmod o+r "$CERT" "$CA_FILE"` then hits an unbound variable and bash exits the shell (verified: an unbound variable inside a function exits even under `|| true`). The ETC_DIR chown/chmod ran, but `chown -R $SERVICE_USER $DATA_DIR` and `chmod 700` did not. Closure: define CERT, KEY, CA_FILE before the trap, or guard with `${CERT:-}`.
The rest of the original S25-M4 is fixed: modes preserved (`file_mode`), pip `cert =` kept, the unit is installed by install-service.sh. Legacy adoption: a unit is adopted only if it has our Description and no `ExecStartPre=` (an old inline unit); a hardened unit without our manifest, or any other unit, makes the script exit 1 and change nothing; with the manifest it runs `upgrade` (keeps the hardened unit). That does not weaken a hardened unit. Residual: the old unit is moved aside before `install-service.sh install` runs, so a failing install leaves no unit (a `.legacy-<stamp>` backup exists). `--no-verify` is passed to the installer but the verify path is skipped anyway for a non-package binary.

### RC1-9 LOW
- macOS and MSVC developer builds need the OpenSSL archive on a `-L native=` path (RC1-2); say so in README and docs, or fall back to dynamic when no archive is found.
- sh `check_home_paths` (install-service.sh:326-333) does not cover `--bin-dir`: `--bin-dir /home/x/bin` with a system unit puts ExecStart under `ProtectHome=yes`.
- The system unit has `CapabilityBoundingSet=` and no ambient capabilities, so `listen` below 1024 cannot bind (EACCES, then the start limit). The old inline unit also ran as a non-root user, so it is not a regression, but nothing refuses or documents it (docs/operations.md has no mention). Either document "use 8080+ or a proxy, or `AmbientCapabilities=CAP_NET_BIND_SERVICE`", or have the installer refuse `--listen` below 1024 for a system unit.
- ps1 `-ConfigureTools` (ps1:272-277): `Save-Preserving` refuses a link at the target file but not a junction at its parent (`C:\ProgramData\pip` is user-creatable), and the fixed temp name `pip.ini.probation-new` is in that directory. Residual of the original S25-L4: a planted junction redirects a write of the pip.ini text to a file named `pip.ini` elsewhere. `npm` is resolved from the elevated PATH.
- src/service_failure.rs:50 opens `service-failure.txt` with create+truncate and follows a link at that name (Windows junctions/symlinks need write in the log directory, which only the service and admins have). The message can carry a TOML error excerpt. Bounded at 4096 bytes: verified by the test; exit codes 78/70/73 as documented.
- src/service_log.rs: bound `(backups+1) * max_bytes` holds (an oversized event is cut to the bound, `write` still reports the full length, so the cut is silent); 0600 on Unix, the log directory's ACL on Windows (installer sets it); rotation by rename works on Windows because Rust opens with FILE_SHARE_DELETE. No finding.
- `healthy()`, `rollback_upgrade` and `service_start` use `die` inside subshells and `||` lists, so "the previous service did not start either" is never printed (the `die` message is). Exit status is still nonzero.
- Systemd start limit: after ten starts in 60 s the unit stays failed until `reset-failed` (down, not looping); the rollback's `systemctl restart` would then also be refused. The unit comment documents the difference from launchd/SCM.
- The Docker lane (docker-engine.sh): root daemon through a transient unit, socket group = the runner's group at 0660 (not 666), classic image store set explicitly, archive sha256 checked before extraction (recorded from the first download, vendor publishes none: trust on first use, disclosed in the evidence). Not run as a CI job. No new finding.
