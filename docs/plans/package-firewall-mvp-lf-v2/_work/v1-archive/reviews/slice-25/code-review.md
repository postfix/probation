## Findings

### CR25-1 HIGH, blocking, CONFIRMED by code: Windows install fails on its default path
scripts/install-service.ps1:79 writes `public_url = "http://$Listen"`; src/config.rs:593 rejects any non-https public_url, so `Test-Config $BinPath` (ps1:184) dies on every fresh install that lets the script create the config. The script has no -PublicUrl/-TlsCert/-TlsKey (install-service.sh has all three), and the lane (tests/e2e/native/service-lifecycle.mjs:62) passes only -Listen. Scenario: service-windows job, step install, `check-config` exits non-zero, job red; for an operator, no Windows install without hand-writing a config first. slice-25.md "Spec changes" item 5 states the https rule, so the ps1 contradicts the evidence.
Closure: add -PublicUrl/-TlsCert/-TlsKey with the sh semantics (https default `https://localhost:<port>`, never generate TLS), and a test asserting the generated text passes check-config.

### CR25-2 HIGH, blocking, CONFIRMED mechanism (not run): the installed Windows service cannot load libcrypto
src/managed/enterprise_certificate.rs links libcrypto by name; tests/e2e/native/openssl-setup.mjs puts the import lib/DLL in a shim dir on $GITHUB_PATH. install-service.ps1:89-100 copies only probation.exe to `%ProgramFiles%\Probation`. A service started by the SCM uses the machine environment, not the step PATH, so the loader fails (0xC0000135) at start. `Test-Config` passes in the installer because it runs in a shell whose PATH has the DLL. The release zip ships libcrypto-3*.dll beside install-service.ps1 (release.yml build-windows), and the installer ignores it. Scenario: user unzips the release, runs `install`, `Start-AndWait` times out after 30 s (Die with a throw, half-installed). The CI lane has the same failure unless something else puts the DLL on the machine PATH (nothing in service-lifecycle*.mjs does).
Closure: copy `libcrypto-3*.dll` from the binary's directory into BinDir (record it in the manifest, replace it on upgrade, remove it on uninstall), or link statically.

### CR25-3 HIGH, blocking, CONFIRMED: native-service.yml hides test failures (false green gates release)
.github/workflows/native-service.yml jobs `tools-linux` and `docker-engine` run `cargo test ... 2>&1 | tee LOG` in the default shell. GitHub's default `bash -e {0}` has no pipefail (only explicit `shell: bash` adds `-eo pipefail`; the `tools` job has it, these two do not). The pipe's status is tee's. Following greps only look for SKIPPED and (docker) for the witness line, which the witness test prints whenever the daemon is 29.9.2. Scenario: docker-engine job where `a_real_podman_pull_by_digest...` fails against Docker Engine: step green, native-service green, release proceeds, and slice-25.md would count the Docker Engine 29.9.2 lane as passed. tests/e2e/native/check_workflow.py checks only native-clients.yml and release.yml, so its pipefail rule (line ~310) never sees native-service.yml.
Closure: `shell: bash` (or `set -o pipefail`) on those steps; extend check_workflow.py to run the same pipe/hide-failure rules over native-service.yml and add a mutation case in check_workflow.test.py.

### CR25-4 HIGH, PLAUSIBLE (mechanism near-certain, unexecuted): macOS release binary dynamically links Homebrew OpenSSL
openssl-setup.mjs adds only `-L $(brew --prefix openssl@3)/lib`; the resulting binary records the dylib's absolute install name (/opt/homebrew/opt/openssl@3/lib/libcrypto.3.dylib). Any Mac without that Homebrew package gets a dyld failure at launch of the whole binary (including `check-config` and the LaunchDaemon), not just the OCSP path. The macOS lanes build debug on a runner that has brew OpenSSL and test that build, never the release tarball, so CI cannot see it. Needs for parity (user's ruling: no backlog): static libcrypto (`#[link(name="crypto", kind="static")]` against libcrypto.a, or vendored openssl-src), or a runtime dlopen with a refusal that disables only enterprise OCSP, or a bundled dylib with @rpath; plus a packaged-artifact smoke job (extract the release tarball, `install-service.sh install`, with openssl@3 unlinked). ### CR25-5 MEDIUM: upgrade rollback covers only a failed `check-config`
install-service.sh:395-405 and ps1:196-207: after the old service is stopped, a failure in `install_binary`/`Copy-Item` (set -e / ErrorActionPreference Stop), or a new binary that validates but does not start (`service_start` dies "did not start", ps1 `WaitForStatus` throws), leaves the service stopped or on the new binary with no restore; the `.prev` binary exists but is never reinstated. Scenario: new binary passes check-config yet panics at bind: service down after an "upgrade". Also write_definition replaced the unit (the `.prev` unit is not restored either). Closure: trap that restores binary and unit and restarts, and restores on start failure; test with a stand-in binary that validates and exits 1. ps1 upgrade also does not re-apply the service definition (failure actions, PreshutdownTimeout) although the header says upgrade changes "the service definition".

### CR25-6 MEDIUM: ps1 partial installs and tool edits
- ps1:104-114 registers as LocalSystem (New-Service) and records `service:` only at the end of Register-Service; a failure between leaves an Automatic LocalSystem service that the next `install` refuses (not recorded) and nothing rolls back. Reorder (set account first / delete on failure) or record first.
- ps1:155 `& npm ...` with `$ErrorActionPreference='Stop'`: a missing npm throws CommandNotFoundException, so the "No npm found" branch is unreachable and -ConfigureTools aborts after the service was registered. Use Get-Command.
- ps1:131,147,84: `Get-Content`/`Set-Content` default encoding is ANSI in Windows PowerShell 5.1, so non-ASCII bytes in an existing .npmrc/pip.ini are re-encoded (credential/comment bytes not preserved, contradicting the "byte for byte" claim), and `Set-Content -Encoding utf8` writes a BOM into config.toml (unverified that toml accepts it). - ps1:57-63: ACLs cover ConfigDir/DataDir/LogDir only; a `--tls-key` or `service_key_file` outside ConfigDir is unreadable by `NT SERVICE\Probation` (start fails) or readable by whoever owns that directory (no check, see parity item 2).

### CR25-7 MEDIUM: install-local.sh overwrites the hardened unit
scripts/install-local.sh:402-424 unconditionally `install -m 644` the inline unit to /etc/systemd/system/probation.service (and writes the journald conf), replacing a unit installed by install-service.sh (drops StateDirectory, ProtectSystem, ExecStartPre, UMask directory modes) and any operator unit; not recorded in the install-service manifest, so uninstall later removes a file written by someone else. Scenario: operator runs install-local.sh --start after install-service.sh to refresh the certificate: service silently loses its sandbox. Closure: make install-local call install-service.sh (see parity item 4) or at least refuse when the unit exists.

### CR25-8 MEDIUM: Windows operator stop can restart the service
main.rs `serve` returns `Failed` when `running.shutdown()` errs; `exit_plan(Failed)` is report_stopped=false, so after an operator `Stop-Service` an unclean shutdown ends the process without `Stopped` and the SCM runs the restart action (5 s). On systemd/launchd the stop job suppresses restart. Closure: if the stop came from the SCM, report Stopped with a Win32 error code (failureflag stays 0 so no recovery action) and reserve the no-Stopped path for exit 75 and startup failure; add a lifecycle_plan case.

## Answers to the specific questions
- SCM semantics of exit 75 / failure: correct. A process that ends without reporting Stopped is a failure to the SCM and runs the failure actions regardless of failureflag; ps1:110-111 configures `sc failure reset= 86400 actions= restart/5000/restart/5000/restart/60000` and `failureflag 0` (so a reported Stopped never triggers recovery, avoiding the next-boot activation the research cites). Gaps: CR25-8, and a start failure before Running is uncertain (the docs are unclear on recovery actions for a process that dies in START_PENDING). `PreshutdownTimeout` as a registry value is unverified (the evidence says so).
- Signals: Unix SIGINT/SIGTERM unchanged (installed before `serve`, same ordering; native_lifecycle passes). Windows Ctrl-Break/Close/Shutdown in `serve`; `service` mode uses SCM controls (Shutdown not in controls_accepted, Preshutdown is: fine).
- Second owner: data-directory flock, pinned by native_lifecycle (passed) and the real systemd lane; adequate.
- src/osv/matches.rs: Unix unchanged (`owner_only` is `mode(0o600)`, `sync_directory` is open+fsync). Windows: the temp file inherits the directory ACL (real only if the installer's data-dir ACL is applied; no code check), directory fsync is a documented no-op, so the durability of the matches file is weaker on Windows (config.rs:1487 documents it). Not a Unix regression.
- install-service.sh: systemd/launchd, system/user, --root staging, manifest, no config/blocklist/cert overwrite, uninstall keeps data: behave as stated (12 tests, probe). Not idempotent by design (second install refuses). Defects: CR25-5, CR25-9.
- Workflows: all action refs SHA-pinned and the three new SHAs match their tags; permissions contents: read; native-service is called without `secrets: inherit` (no secret exposure), checkout uses persist-credentials: false; release gating via build.needs is transitive and checked by the new check_workflow.py rule; defects CR25-3, CR25-4, CR25-2.
