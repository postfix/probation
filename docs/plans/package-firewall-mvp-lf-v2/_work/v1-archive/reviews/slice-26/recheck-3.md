## Findings

**M-1 (Medium, security) The M1 fix does not cover the window between `install-firewall.sh` and the next boot.**
`deploy/kubernetes/node/install-firewall.sh:88-91`, `probation-node-firewall.service:9-11`. The installer loads the tables with `nft -f` directly and runs `systemctl enable` only (no `--now`), so the unit is INACTIVE after the install. `PartOf=` propagates a restart of `nftables.service` as a try-restart, and `ReloadPropagatedFrom=` propagates a reload as a try-reload; both are no-ops on an inactive unit. Scenario: an operator installs the firewall, later edits `/etc/nftables.conf` and runs `systemctl restart nftables` (its file starts with `flush ruleset`): both tables vanish, nothing restores them, `verify-node.sh --firewall` is not run by anything periodic. This is exactly recheck-2 M1, for every node until it reboots (and for a node whose unit failed at boot). The test (`node_scripts.rs:530`) only reads the unit text; the "tested in a network namespace" claim covers `nft -f` of the unit's own reload lines, not systemd's propagation, which no test exercises (operations.md:2118 states the systemd behaviour as fact). Fix: replace the two direct `nft -f` loads by `systemctl enable --now probation-node-firewall.service` (the unit loads both files; idempotent because each file starts with `delete table`), keep `--no-load`/`--root`, and add to operations.md that a stop of `nftables.service` also stops (removes) the node rules. Label the systemd propagation as not run.
Semantics otherwise right: `After=nftables.service` orders our start after its flush; on a restart job our unit stops first (reverse of After), then starts last; `ExecStop=-` is correct; both nft files are idempotent (`table ...; delete table ...; table ...`).

**M-2 (Medium, lane) `denied()` always returns non-zero under `set -o pipefail`.**
`tests/e2e/cluster/run-kind-lane.sh:156` (used at `:157-158` and `:211`). `kubectl ... patch ... --dry-run=server 2>&1 | grep -q 'probation-one-local-service'` runs in the main shell with `pipefail`; kubectl exits 1 when the policy denies, so the pipeline status is 1 even though grep matched. Reproduced with a stub that prints the text and exits 1: `denied` returned 1. Result: `expect "admission: externalTrafficPolicy Cluster is refused ..." denied` is always red, the 30-iteration wait burns 60 s, and `:211` never breaks early. The other `| grep -q` checks (`:146`, `:159`, `:219`, `:260`) run inside `bash -c`, which does not inherit pipefail, so they are fine. Fix: capture the output first (`out=$(kubectl ... 2>&1 || true); grep -q ... <<<"$out"`), as lane-lib.sh does for its helpers. The lib self-test does not cover `denied` because it lives in the lane script, not in lane-lib.sh.

**M-3 (Medium, lane and doc) Phase A cannot work: `default-deny` stays after `probation-ingress` is deleted.**
`run-kind-lane.sh:189`, `deploy/kubernetes/networkpolicy.yaml:14-18` (`default-deny`: `podSelector: {}`, `policyTypes: [Ingress, Egress]`), `docs/operations.md:2104`. Deleting only `probation-ingress` leaves the namespace default-deny in force, so the service pod still receives NO ingress from anyone, the approved node included. Every phase A assertion (`:192-196`, "refused BY THE SERVICE", "approved worker 2 is admitted") stays dropped/empty and goes red after the 90 s poll, and an operator following the documented procedure sees only timeouts and concludes nothing. The negative control (`:199-208`) and everything after it is unreachable in practice. Fix: lift the layer by replacing `probation-ingress` with an allow-all ingress policy for the pod (or deleting `default-deny` as well) in the lane and in the doc; restore both afterwards (`kubectl apply -k` does).
