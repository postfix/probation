## New findings from round-2 text (design gaps, none executed)

**N10 (Medium) Quick-gemspec validator and the nested Marshal stream (LS-F13 B).** `Gem::Specification` is serialised as a user-defined type (`u:`). As I recall RubyGems, its `_dump` returns a String that is itself a Marshal stream of the field array. `Gem::Specification._load` runs `Marshal.load` on it. The LS-F13 text says the validator accepts the class tag "plus their ivars" and passes the original bytes through. It does not say the inner stream is parsed. If the validator treats the `u:` payload as an opaque String, any class (`Kernel`, `Gem::Installer`-style) can sit inside it and the allow-list (and the `quick_gemspec_hostile_class_refused` fixture, if the hostile class is placed at the outer level) is bypassed. Unmarshalling clients that call `Marshal.load` then receive the payload. Fix: state that the validator recurses into the `u:` payload of Gem::Specification (and any other allowed `u:`/`U:` type) with the same class allow-list, depth, node and memory budgets, counted against the same 4 MiB / 64 MiB totals, and add the hostile case "disallowed class only inside the nested stream" to the fixture. Closure: `quick_gemspec_hostile_class_in_nested_stream_refused`. Also check the allow-list against the real fixture: Gem::Platform (`o:Gem::Platform` when `platform` is an object) and `Gem::Version` in its `U:` form are likely needed. The widen-not-refuse rule covers them, but name them up front so row 17 does not discover them mid-slice. Widening should be a recorded, reviewed addition limited to data-only classes. Regexp: refusing it by default is acceptable (no code execution on load; the cost is only a possible refusal of a valid gemspec, which the corpus rule handles).

**N11 (Low) Tuple-filter budget scope (LS-F13 A).** "Charges only retained typed values" does not say whether the Marshal symbol table and object (link) table, which must be kept for the whole stream even when tuples are streamed out, and the re-rendered output buffer count against the 512 MiB budget. They scale with node count and can dominate. State that both count, or that output is streamed with a bounded buffer. Also state that array and hash length prefixes are never used to preallocate (a declared length of 2^30 inside a small stream). Test `marshal_filter_length_prefix_no_prealloc`.

**N12 (Low-Medium) Revision digest canonical form (LS-F8).** The field set is named (version, key_id, org, place_chain, layers, revision, account), but not the canonical byte encoding the digest is computed over. If it hashes server-supplied JSON bytes or an order-dependent encoding, a server that reorders rules or map keys at an equal revision produces a permanent `RevisionRegression` rejection of valid state. Fix: hash a canonical re-serialisation of the parsed values (sorted keys, layer and rule order as authoritative, defined number and string forms). Test `digest_independent_of_json_key_order_and_whitespace`. The server obligation and the "field leaves the digest if it does not bump" fallback are fine, but that fallback is discovered only after rejection, so make `revision_moves_with_every_digest_field` a gate before row 28 ships. Also state who may run `reset-revision-floor` (local operator on the enforcer host only).

**N13 (Low-Medium) Server cache hits inside a failed batch (LS-F2).** "A whole-batch upstream failure sets `upstream_ok=false` and degrades every result." If the batch also contains keys the server already holds as matched, degrading every result drops a known match, a fail-open the server could avoid. State that results answered from the server cache (matched or fresh no-match) are returned as such even when `upstream_ok=false` for the rest, with only the uncached keys degraded. The client rule (only NoMatch from `upstream_ok == true` may be stored) already stays safe. Test `osv_cache_hits_answered_when_upstream_down`.

**N14 (Low) Denylist coverage (LS-F9).** Not named: `0.0.0.0/8` (routes to the local host on Linux; the text says only "unspecified"), NAT64 local-use `64:ff9b:1::/48`, Teredo `2001::/32` and ISATAP `...:5efe:a.b.c.d` embeddings. "Cluster control-plane ranges" is not defined here. Add these or state them as accepted. Unwrap recursion depth (mapped inside 6to4) should be one pass to a fixpoint.

**N15 (Low-Medium) Default 16 MiB cap for any other compressed input (LS-F7).** Applies to every accepted compressed input, including existing npm and PyPI metadata paths. Large packuments or simple indexes may exceed 16 MiB inflated (unmeasured). Under the product goal (no capability loss) an unmeasured default is a risk. Require each row, including the delivered npm/PyPI paths, to record its largest real fixture in evidence, and say that the cap is raised, not the input refused, where a valid input exceeds it.

**N16 (Medium, product policy) The 4 GiB per-request cap (LS-F16).** The new default refuses a credential-bearing read over 4 GiB with 503 where it streamed before. This is a loss of existing function, and it is correctly flagged to the user (decision 13). Under the standing rule that a loss is never the default, set the default to no per-request cap (disk is then the only limit and ENOSPC maps to 503) or to a high value, and keep 4 GiB as the alternative. Two wording points: `Retry-After` on a deterministic over-cap refusal invites pointless retries (use a non-retryable status or omit the header for the per-request cap), and "before more bytes are delivered" is only achievable if headers have not been sent. State that credential-bearing bodies are held in the temp file until complete, or that a known Content-Length over the cap is refused up front. Also say whether `credential_temp_max_total_bytes` is per process or per `data_dir` (the lock scheme implies several processes).
