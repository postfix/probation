## GatedCache / CacheToken
All shared inserts are gated: `GatedCache::insert` / `insert_if_current` need `&CacheToken` (src/store/cache.rs:257-260). Greps of src and tests show no ungated insert on `projects`, `rendered` or `absent` (call sites: src/npm/mod.rs:179,306,759; src/pypi/mod.rs:147,291,608; all take a token from `cache_token(app)`, which is None for a request-scoped read in service mode). `CacheToken(())` has a private field; mint points are `classify_read`, `cache_token`, and `for_test_support` (test-support feature). The inner `ShardedCache` is private to the wrapper (only a comment references it outside store/cache.rs). `references: ShardedCache<ReferenceId, ReferenceRow>` is not gated; it is filled from the database rows (identity data), never from a caller-credentialled body, so it is not a leak (N3, note). All inserts run on the request task (no tokio::spawn near them), so the task-local flag in `request_scoped()` is visible; it returns false outside a request context, which fails open (N2).

## Flake: content_store::an_open_during_eviction_is_refused_and_a_second_eviction_stands_aside
Run alone, capped scope, load average about 39: 5 runs, 4 passed, 1 failed at tests/content_store.rs:305 (`assert!(!second, "a second pass over the same key stands aside")`).
Race: the test relies on `join!` polling `evict` #1 first, which must return Pending inside `tokio::fs::remove_file` (a spawn_blocking). If the blocking-pool thread finishes the unlink before the awaiting poll of the JoinHandle (thread preemption under load), evict #1 completes in its first poll and clears `evicting`; evict #2 then finds pins=0 and no claim, claims, gets NotFound from remove_file (treated as success) and returns true. Failure at :305 (`second` true) matches exactly. src/artifacts/content.rs:185-210 (evict) and :361-420 (open_verified) are unchanged by the diff.
Cause analysis from `git diff HEAD -- src/artifacts/content.rs` (15 added, 2 deleted lines): the only changes are `_pin: Option<OpenPin>`, `_scoped`, and the new `PinnedFile::request_scoped`. They sit in the success tail of `open_verified` (after the claim and pin logic) and in the PinnedFile struct; the test never reaches a PinnedFile (open is refused with Missing). So the change cannot cause the flake; it predates and is a timing-dependent test (the evidence's "load 105 made it 5/9" fits). Fix (test only, out of scope here): make the first eviction deterministic (a test hook that holds the removal, or a Barrier/Notify in the seam) instead of relying on scheduling. Not a product defect: with a second eviction claiming after the first finished, the observable outcome (file gone) is correct.
