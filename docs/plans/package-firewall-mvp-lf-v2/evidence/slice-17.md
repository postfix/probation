## Behaviour notes (decisions inside the contracts)
- Codec: hand written instead of the pinned marshal-rs. Reason: marshal-rs is a git dependency with a WTFPL licence and its Reader neither tracks the object table nor counts nodes; LS-F13 needs a link table, per-class payload kinds, nested streams with cumulative depth and shared budgets, and a typed re-render, all of which the wrapper would have to implement anyway. The probe's schema (a one-element `Gem::Version` payload, UTF-8/US-ASCII encoding ivar) is what the tuple filter accepts, as the spec lists. This is a deviation from "pinned marshal-rs" in 03 and needs the user's yes or an explicit instruction to switch; no new dependency was added for it.
- Memory budget accounting: a retained typed value costs 64 B plus its bytes, a link-table slot with no typed value 32 B, a symbol its name plus 64 B, and the output buffer its length; parsed-and-dropped nodes are bounded by the node cap instead (the first draft charged every node permanently and refused the real full index at 512 MiB: that is why the rule above exists, see rubygems-corpus.md).
- Dates: `created_at:` in a compact-index line is authoritative for exactly that version AND platform; a line without it takes the committed first-seen time of that reference; there is no cache-age or build-time substitute. The reference id of a gem is the registry-scoped hash of name, version, `{name}-{version}[-{platform}].gem`, `{origin}/gems/{file}` and the line's `checksum:` sha256, so a changed checksum is a new reference.
- Policy version for a blocklist or OSV rule is the version without the platform; `Gem::Version` equality (`1.0` equals `1.0.0`, `1.0.a` equals `1.a`) is in `canonical_version`.
- `/versions` passes through unchanged. Bundler 2.5 requires its third column (the MD5 of upstream's unfiltered info file) and uses it only to decide whether its cached info needs re-downloading, so a filtered info file costs a re-download, never a failure (the native Bundler test is the witness).
- The tuple indexes are filtered per tuple: a gem whose compact index this instance already holds is judged completely (age, blocks, pins, OSV) so the listing agrees with `/info/{gem}`; every other gem is judged by blocks only, because the legacy index carries no dates. Listing a version never delivers it: its quick gemspec and gem file are identity-gated by the same policy.
- Quick gemspecs: inflated within 4 MiB, validated, and the ORIGINAL bytes are served (a real fixture is byte-identical and Ruby loads it). A hostile class, also one placed only inside the nested Gem::Specification stream, answers 502.
- RubyGems through the shared service is read-only (GET and HEAD, no query string); `gem push` and `gem yank` are not forwarded by this family.

## Known gaps, stated plainly (decisions needed where marked)
1. The first `gem install` of a gem this instance has not indexed can fail: the legacy tuple index lists a gem's young latest version (no date to judge it by), the resolver chooses it, and its quick gemspec is then refused (404), where Bundler (compact index) is exact. Any `/info/{gem}` request, or a first failed attempt, makes the next listing agree. DECISION NEEDED (this is the "global indexes with missing-date candidates" design point of 03): either a batch first-seen store for index tuples (held until first-seen plus cooldown, the literal reading of 03), or an operator-visible bulk date source such as rubygems.org's `timeframe_versions` API. # Recheck fix round (2026-11-19, N1-N8 of reviews/slice-17/recheck-1.md)

Live check (one read-only GET of rubygems.org, 2026-11-19): `GET /api/v1/timeframe_versions.json?from=<iso>&to=<iso>&page=N` answers a JSON array of **30 rows per page**, newest first; the row has `name`, `version` (not `number`), `version_created_at` (ISO 8601 with milliseconds, e.g. `2026-11-18T23:05:30.165Z`), `platform`, and many ignored fields (`info`, `licenses`, `sha`, ...). The code accepts `number` and `created_at` as spellings too. (The first request of this check wrote no file because the scratch directory was missing, so a second identical read was made; two GETs in all.)

- **N1** `fetch_recent` pages every window until an empty page. Hard caps: 2,000 page requests, 60,000 rows and 300 s per list; hitting any returns `None`, so every unindexed tuple stays unlisted (fail closed, never listed) and a warning is logged. A real seven-day window is on the order of a thousand pages, so a 7-day cooldown against rubygems.org costs about that many sequential requests per list refresh (once per minute at most, one at a time per registry).
- **N2** File ids and names keep the client's spelling (`RedCloth-4.3.2.gem`); policy, blocklist and OSV keys, `ArtifactReference.name` and the stored project row are lower-case. The artifact membership check now passes the reference's file name to `ensure_fresh_project_in`, which derives the spelling from it and builds the advertised set for that spelling (the snapshot keeps the first spelling's set; another spelling rebuilds per call).
- **N3** The recent list has one cell per (registry, window, origin) (single flight), no global lock, and is fetched before the heavy permit is taken, so no lock is held across an upstream fetch while a permit is held. A failed or absent list is remembered 15 s (a list 60 s).
- **N4** One page is at most 2 MiB (or `max_metadata_bytes` if smaller) and is parsed into a typed `Vec<RecentRow>` that skips every other field unparsed; rows are capped as in N1.
- **N5** The recent cache is read and written only when `credential_read::cache_token` allows (shareable reads), keyed by origin too; a credential-bearing read fetches its own list uncached.
- **N6** The filtered index has a per-key flight lock and re-checks the cache after taking it: N cold concurrent requests cost one fetch, one recent list and one filter pass.
- **N7** A cooldown over 42 days (more than 6 weekly windows) deliberately stays fail-closed: unindexed tuples are not listed (a warning names the window) and the API is not asked. Choice: the API caps one call at seven days and the date of a version older than the horizon cannot be proved, so no date is invented. `Rack` and `rack` now share one stored project row (lower-case key, row name and reference names); the references of each spelling are committed on its first request in this process (a revalidation, conditional when validators exist). Residual: a client can still make one set of reference rows per spelling it invents (bounded by the per-project entry cap per spelling, as before; the project row itself is shared). Needs the user's note if that bound is not enough.
- **N8** `gem push` and `gem yank` forward the caller's `OTP` header (non-empty, at most 64 bytes) in a new `ActionRequest.otp`; `Content-Type` was already forwarded (now asserted). No other header is forwarded.

Page format the E2E fake should imitate: `GET /api/v1/timeframe_versions.json?from=2026-11-12T00:00:00.000000Z&to=...&page=1` (from, to are ISO 8601; page starts at 1, no `page` is page 1). Answer a JSON array of rows `{"name":"rgcase","version":"1.0.0","platform":"ruby","version_created_at":"2026-11-18T23:05:30.165Z", ...ignored fields}` of at most 30 per page, and `[]` for every page past the last (including page 1 of an empty window). The firewall keeps requesting `page=N+1` until it sees `[]`, so a fake that returns the same non-empty array for every page makes the list fail closed (all unindexed tuples unlisted).

# Recheck-2 fix round (2026-11-19, R1-R7 of reviews/slice-17/recheck-2.md)

- **R1** At most 4 case spellings of one gem are committed per registry (`MAX_SPELLINGS`, in-memory per (registry, lower name)); a further spelling answers 404 before any upstream fetch, an already committed one keeps working. This also bounds R6 (pins and first-seen rows are keyed by reference id, which includes the spelling: at most 4 id sets per gem, so a changed-bytes registry can be delivered under at most 4 spellings, each pinned on first delivery). Ceiling (marked `ponytail:`): the count is forgotten after a restart, when 4096 gems are tracked, and is not shared between instances, so the bound is 4 per gem per process lifetime; a persisted per-gem count if that matters.
- **R2** The crawl runs in a task that owns the cell's lock, so a disconnecting client does not drop it and the next request finds the finished list; the cache stamp is taken when the crawl ends. While a crawl runs, other builds of the same registry wait on the cell (single flight, bounded by the crawl deadline); none of them lists an undated tuple. The real page count and latency of rubygems.org were not measured in this round (a 7-day window is estimated at about a thousand pages; the 2,000-page / 60,000-row / 300 s caps are the margin); if a real crawl exceeds 300 s the list stays unavailable and unindexed tuples stay unlisted.
- **R3** A credential-bearing index read still never reads or fills the shared caches, and now takes one of two per-(registry, origin) slots around its crawl and build, so N concurrent such reads crawl two at a time.
- **R4** Documented, not changed: `to` is the request start and the list is cached for 60 s while the tuple index is fetched afterwards, so a version published in that gap is dated as older than the cooldown and listed in the legacy tuple index for up to the crawl time plus 60 s. Only the listing is affected: info, the quick gemspec and the gem file stay gated by their own dates (403/404), so this is the F1 symptom for brand-new versions, not artifact delivery.
- **R5** Tests added for the 60,000-row cap, the crawl deadline (shortened through `App::set_rubygems_recent_deadline`, compiled only under `test-support`; no real sleep of minutes), and the OTP bounds (64 bytes forwarded, 65 and empty dropped).
- **R6** Bounded by R1 (above).
- **R7** NOT done: the E2E-rubygems assertions (young java file `404 || 403`, lowercase file `!== 200`, the young mixed-case 1.1.0 file never requested) are unchanged, because tightening them cannot be verified without rebuilding the two release images and re-running the scenario, which this round did not do. Only the E2E-003 header comment was corrected (comment text, no behaviour change; the scenario was not re-run for it).
