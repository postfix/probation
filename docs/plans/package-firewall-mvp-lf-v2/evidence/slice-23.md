## Measured against the real registry and the real client (ConanCenter, 2026-11-19, and conan 2.21.0)
- `GET /v1/ping` answers `x-conan-server-capabilities: complex_search,checksum_deploy,revisions,matrix_params` and `x-conan-server-version`; `/v2/ping` is a 404 there. The real client probes `v1/ping` (before an upload and on a first read), so it is the one `v1` path routed; this firewall advertises only `revisions` (it serves no checksum deploy, no complex search and no matrix parameters).
- A revision list is `{"reference": "zlib/1.3.1@_/_", "revisions": [{"revision": "...", "time": "2025-12-09T12:51:39.337+0000"}, ...]}`, newest first; a package list is the same with `packageReference`; `latest` is `{"revision", "time"}` of the first; a file list is `{"files": {"conanfile.py": {}, ...}}` with empty values; a binary search is `{pkgid: {settings, options, content, requires}}`; a reference search is `{"results": ["zlib/1.2.11@_/_", ...]}` (`_/_` printed for no user and channel). A file carries `Last-Modified` equal to its revision's time and `x-checksum-md5/sha1/sha256`.
- Largest real inputs: `search?q=*` 222,081 bytes; the binaries of boost/1.86.0 31,998 bytes (9 package ids) and of openssl/3.3.2 30,996 bytes (10); a revision list of zlib/1.3.1 about 700 bytes (4 revisions). Nothing is compressed on the wire in these answers.
- The real client (conan 2.21.0) sends on a plain read exactly `accept`, `accept-encoding`, `connection`, `host`, `user-agent` and `x-client-anonymous-id` (measured with a tap, `conan_native_client_sends_only_allow_listed_headers`): all common but the last, a non-secret random id, so Conan adds `x-client-anonymous-id` (and `x-client-id`, which a logged-in client may add, not seen) to the allow-list of LS-F4 and the query keys `q` and `ignorecase`. File downloads carry only `Accept`. A logged-in client sends `Authorization: Bearer <token>` on every request, a login `Basic` to `v2/users/authenticate`, which answers the token as text.
- The real client's read flow for `conan install --requires='hello/[>=1.0]'`: `v1/ping`, `v2/conans/search?q=hello%2F%2A`, `.../latest`, `.../revisions/{rrev}/files`, then each file; `.../packages/{pkgid}/latest`, `.../revisions/{prev}/files` and each file. Its upload flow: `authenticate`, `v1/ping`, `.../revisions`, `.../packages/{pkgid}/revisions`, `check_credentials`, then a `PUT` of each file with an `X-Checksum-Sha1` header (not forwarded: the registry computes it).

## Behaviour notes (decisions inside the contracts)
- Identity. A reference is `name/version@user/channel` (`_/_` in the URL for none; user and channel both or neither). Policy, the blocklist, the OSV key and the project name of the reference rows are the package NAME and the recipe VERSION verbatim (case is identity; `[A-Za-z0-9_][A-Za-z0-9_+.-]*`, what the Conan 2 client accepts, at most 200 bytes: wider than the 03 table's `[a-z0-9_.+-]`, which would refuse a valid Conan name). A reference row's `filename` is the path below `{name}/{version}/` (`{user}/{channel}/revisions/{rrev}/files/{file}` or `.../packages/{pkgid}/revisions/{prev}/files/{file}`), which is everything that tells two files of two revisions of one version apart; every upstream URL is rebuilt from the parsed identity. A path that is not exactly one canonical spelling (a dot or empty segment, a revision or package id off `[A-Za-z0-9_-]`, one of user and channel `_`, a file of more than four segments, a query on a layout route, anything of the Conan 1 tree but `v1/ping`) is a 404 before any admission or upstream call.
- Units and dates. The thing that has a publication time is a revision (a recipe revision, or a package revision of one package id of one recipe revision). Its time is the `time` of the remote's own revision list (`+0000`, `+00:00`, `Z` or none are read; absent or unparseable is no date), committed on the revision's anchor row (its `conanmanifest.txt`) only ever later (the later of what this process saw, what the row holds and what the remote says now); a revision with none waits on the committed first-seen time (held for a whole cooldown). Dating costs no call beyond the list. A new binary of an old recipe is its own package revision with its own time and age: no recipe date ever ages a binary, no binary date a recipe, and the latest recipe's date substitutes for nothing.
- Revision lists. `revisions` and `latest` of a recipe or a package id list only the revisions that pass (age, block, OSV, pinned digest); `latest` is the newest allowed (greatest time, the remote's order on a tie), built from the list rather than relayed; with none left the answer is the decision of the first revision (403 with the hold's deadline, or the block); the document's string head (`reference`, `packageReference`) is kept. A list the strict reader cannot read as one document (not an object, `revisions` not an array, an entry without a valid `revision`, a repeated revision, a `time` that is not a string) is a 502.
- Searches. `v2/conans/search?q=`: a reference that the layout cannot carry, one a block names (name or name and version), and a repeat are not listed; each remaining reference is listed only while a revision of it passes (its revision list is read: every one, 16 at a time, as a shared background job whose verdicts are remembered; see "Fix round"). `revisions/{rrev}/search` is gated by its recipe revision and lists a package id only while a package revision of it passes (same bounds); an entry is served as the remote wrote it. A blocked package is never asked about.
- File lists and files. A file list is gated by its revision and rebuilt as `{"files": {name: {}}}` for the names the layout can carry (a remote that returns locations, or members other than `files`, reaches no client through it). Every file is gated by the decision of its revision, delivered exactly and pinned on first verified download; a held revision's files and file list are never fetched; a file the remote does not have is confirmed by a one-byte read after the decision and makes no row.
- The client's own credential. A read that carries `Authorization` goes to the registry's origin with it (never anywhere else), is request-scoped (reads and fills nothing shared: no shared list, no unit table, no stored file) and is shared with nothing; `v2/users/authenticate` and `check_credentials` are asked of the registry with the caller's credential and its answer is relayed as text. A certificate-managed firewall (the key route) answers the login itself: the key presented as the Basic password (or Bearer) comes back as the token, so the client sends `Authorization: Bearer <key>` from then on and the managed admission accepts it; the certificate script says so on stderr and writes no Conan configuration (unit test `conan_setup_points_at_the_key_route`), as for Cargo, Go, NuGet and Maven. Authentication is by the installed client's own key or token, not certificates.
- Writes (class W). Through the shared service only: `PUT` of a file of a recipe or package revision and `DELETE` of a file or of a recipe, revision, packages or package(-revision) directory, with the caller's own `Authorization` (never the service key) to the registry's own origin (its `target_url`, path included) or, for the public registry, to `conan_publish_url` (no default: ConanCenter takes no uploads, so there the answer is 404). A write without a credential is answered `401` with `WWW-Authenticate: Bearer realm="conan"` before anything is read or asked, a declared body over twice the artifact cap is 413 before the registry is asked, a path that is not a layout path (a `PUT` of a directory, `latest`, `revisions`, `v2/users/...`, a Conan 1 route) is 404, and the answer is relayed only with a status an upload endpoint gives, as `text/plain` with `nosniff`. All through the shared spool (src/http/spool.rs, owner by `spool::owner_of`). A standalone or managed firewall has no upload route (405).
- Ping. `v1/ping` and `v2/ping` are answered locally (200, `x-conan-server-capabilities: revisions`); the registry is not asked.

## LS-F7: the family's inputs and caps
- A revision list, a file list, a binary search and a reference search are read to `max(max_metadata_bytes, 16 MiB)` (70 times the largest real one, 222 KB); a login answer or credential check 64 KiB. The transport decodes `Content-Encoding: gzip` and counts the decoded bytes against the cap. No valid input is refused before those caps: `a_large_listing_is_not_refused_before_its_cap_and_dates_cost_no_extra_call` serves a 2,100-revision list in one call.
- Entries per document are at most 500,000 (the JSON must fit the byte cap first); a revision, a package id and a file name have byte bounds in coords.rs; nesting is bounded by `serde_json`'s own 128.
- Bounded tables: 128 package cells, 256 refresh-place and gate entries, 1,024 row gates, 32 shared lists of at most 4 MiB (5 s), 16,384 units and 4,096 lists per cell; fetches at most 16 in the process and 4 per registry (a wait over 30 s is a 504); a document request has a 120 s deadline; a project holds at most five times `max_references_per_project` reference rows (the bound is hard and atomic: the project's row gate is held from the count to the commit, in `list_units`, `resolve` and `reference_for_file`; past it a revision's anchor is withheld and a file of one more revision or one more file is a 503 and commits nothing; files that have rows are still served).

## Not done, limits and decisions
- The Conan 1 API (`v1/conans/...`, `download_urls`, `upload_urls`) and the Conan 2 `checksum_deploy`, `complex_search` and `matrix_params` capabilities are not served or advertised; the client falls back to plain uploads and the simple search.
- Searches judge every result (see "Fix round"): the earlier 512-list cap was a permanent loss of results and is gone.
- A mirror's revision `time` is the mirror's. Artifactory may stamp a revision with the time it cached it: later than the truth, so it can only hold a revision longer, never release one early; a remote that gives no time waits on first-seen. A hosted remote that lets a depositor choose a revision's time can back-date it (the same accepted residual as Maven's U1, Go's first list and NuGet's `published`; a block or an exception entry is the way through).
- The package id of a binary and the recipe revision are the remote's text and are not recomputed: the manifest (`conanmanifest.txt`) and the remote's `x-checksum-*` headers are not compared with the files (the first verified download pins the digests, SPEC §9; the Conan client verifies its own manifests).
- A recipe whose newest revision is held and whose older revisions the remote no longer lists has nothing to offer: `revisions` and `latest` are 403 with the hold (an older revision is downloadable by its exact name).
- A held recipe revision does not hold the package revisions built from it: a package revision has its own age (that is the contract: "a new binary on an old recipe gets its own age"; the converse, an old binary of a young recipe, is unreachable through a client, which asks for the recipe first, and is its own decision when asked for directly).
- Duplicate JSON object keys in a remote's document: the last one wins (as in the Python client), because `serde_json` reads into a map; every document served is rebuilt from what was understood, so the client never sees an ambiguity the firewall did not.
- Conditional requests: `If-None-Match` and `If-Modified-Since` on a document are answered with the full document.
- Old binaries. No prior-release enforcer or server was built. Compatibility is witnessed at the wire level only: `Upstreams.conan` is additive both ways (`conan_reachability_is_additive_in_both_directions`), the `Conan` descriptor tag is the explicit unknown-tag path of LS-F3 for an enforcer that predates it, and `archive_origin` is ignored by an older reader.
- Gradle-style multi-remote use (a client with two remotes) is the client's decision to make: the documented set-up removes ConanCenter, because a second remote would offer what this one refuses.
- The client image installs Conan from PyPI at IMAGE BUILD time (not at test time); the stack itself stays offline. The native lane (tests/conan_native.rs) and E2E need that image and skip loudly without it.
- The portal's coverage view for Conan is row 27's.

## Decisions for the user
None: every choice above is settled by the product rule (full parity, no backlog, no 400/withhold of valid input) or by what Conan itself does.

### M1: the latency measurement and the redesign

The earlier 565 verdicts/s had no network. The fake registry now answers after an injected delay (`FakeRegistry::set_delay_ms`). |---|---|---|---|
| 0 ms | 200 | 8.2 | 1,098 |
| 50 ms | 200 | 37.2 | 242 |
| 100 ms | 200 | 65.6 | 137 |
| 200 ms | (120 s harness limit) 504, 8,840 verdicts made | 120.0 | 74 |

Redesign (decision recorded):
- Judging has its own lanes: a registry judges 16 lists at once (`JUDGE_PLACES`), the process at most half of `max_upstream_requests` (16 at the default of 32; `Shared::new`), a search 16 at a time (`JUDGE_AHEAD`).
