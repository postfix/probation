## Behaviour notes (decisions inside the contracts)
- The server relays only `MAL-*` vuln refs (at most 32). The endpoint's verdict has always been a `MAL-*` match; other advisories are stored and returned as no-match so the answer stays small. The wire shape is osv.dev's.
- Credential admission: a `fwt_` token (live, firewall not retired, caller inside its `allowed_source_cidrs`, same address derivation as /sync) or a live service-kind `prb_` key. Everything else, including a firewall token from a disallowed source (403 on /sync), is 401 on this route. A pre-auth failure throttle of 10 per minute per peer address answers 429.
- Rate: token bucket per credential, 600 cache-missing keys per minute (config `[server] osv_key_rate_per_minute`), burst 1000, charged once per distinct key that becomes a leader; empty at admission is 429, keys beyond the remaining budget are degraded. Cache hits and followers are never charged. The OSV budget is separate from /sync's window (test `osv_flood_does_not_429_sync_routes`).
- Credential lookups use the app pool through their own gate of 4 (`auth_concurrency`) so an OSV flood cannot take the `/sync` pool (`osv_saturating_load_leaves_sync_latency_within_bound`).
- Server cache: two LRUs (matched, clean), 200,000 entries and 64 MiB, clean entries are evicted first; match TTL 3600 s, no-match 30 s.
- Endpoint: only a non-degraded 2xx answer with the envelope and `upstream_ok: true` counts as OSV reached; 401, 403, 404, 413, 429, 5xx, a redirect (redirects are disabled), a missing envelope, a duplicate key or an oversize answer are unreached, counted in `osv_server_unreached`, and fail open (a retained match is still refused through the stale window). Matches in an `upstream_ok:false` answer are honoured, no-matches in it are not stored.
- Readiness detail (shared-service listener, admitted peers only): `osv_degraded_warning`, `osv_results_total`, `osv_results_degraded`, `osv_server_unreached`, `osv_matches_file_degraded`, `osv_stale_matches_expired`, `osv_matches_records_skipped`. Status code unchanged.

## Measurement gate (LS-F7): real api.osv.dev latency, from this host (curl, one manual run, not a test)
256 npm keys per `querybatch`, 20 runs, each with a fresh connection: min 0.609 s, median 0.655 s, p95 0.862 s, max 0.868 s (connect+TLS about 0.06 to 0.14 s of that). With a reused connection: median about 0.62 s, p95 about 0.75 s. Smaller batches (reused connection, time to first byte): 1 key median 0.25 s p95 0.31 s; 10 keys median 0.30 s p95 0.325 s; 64 keys median 0.335 s p95 0.375 s.
**Consequence (needs a user decision, see the report):** the spec rule is "if p95 exceeds 250 ms the row must raise the deadlines (client strictly above server by at least 100 ms, 400 ms floor consistent) and re-confirm with the user". The measured p95 is far above 250 ms for every batch size, so the provisional numbers (server deadline 300 ms, client default 500 ms, floor 400 ms) would answer every cold lookup degraded (fail-open, matched entries kept, but no new protection). The implementation uses the approved numbers unchanged (`OsvLimits::deadline`, `DEFAULT_OSV_REQUEST_TIMEOUT_MS`, `MIN_MANAGED_OSV_REQUEST_TIMEOUT_MS` are single constants); I did not change them without the user. Steady-state and cold-start key-rate estimates against the 600 per minute budget are not measured here (no fleet to measure); the budget is a configurable key.

## Second review round (2026-11-18)

Fixed: SEC-2 (a follower that has waited half its deadline fires its own single-key call, charged to its credential, bypassing the in-flight table; a slow chunk it cannot influence no longer decides its answer), NEW-1 (a source that keeps failing is turned away before any lookup unless the request carries a credential that authenticated before, so a bad-token flood cannot occupy the 4-permit auth gate; revocation is unaffected because a known credential still goes through full authentication), NEW-2 (the body is read first with a 2 s timeout and no permit; the parse permit covers only the parse; a late body is 408), SEC-5 (the shared 12000 per minute budget gives each tenant, the place a key belongs to, at most 25% of burst and refill, and keeps 20% of the burst as a reserve for tenants that have used under 10% of theirs), hardening (a drop guard removes a dying fetch task's keys from the in-flight table; one key's page error degrades that key only), SEC-1 comment (osv_key.rs), N3 (literal old-shape report fixture), F3 residual (the fleet health text shows `Healthy; OSV warning: ...` for the degraded ratio, refused keys and matches-file or stale-window problems; row 27 names OSV identities and coverage and the registry scope view, not this health text, so it is built here and the healthy flag is unchanged).

Body cap against batch cap (coordinator's question): the server refuses a body over 1 MiB with 413 for the whole envelope before any per-key work, whatever the key count, and refuses more than 1000 queries the same way. A maximum-size legal client batch (256 keys at 1024 bytes of name and of version) is about 0.55 MB and is accepted (test, plus a unit test in batcher.rs on the client's own serialised body). 1000 maximum-size keys are about 2.1 MB and get 413 with zero upstream calls (test). So the count cap of 1000 can legally exceed the byte cap; the byte cap wins and the refusal is the envelope path (413). For the spec author: 03 LS-F7 states both bounds; state that the byte cap is the binding one for large keys. Neither bound was changed.

PyPI real limits (SEC-1 residual): not verified here (no authoritative source reachable in this session; PyPI project names are validated by a regex with no length limit I could confirm, versions likewise). The outcome for a key over 1024 bytes is visible, not silent: never sent, counted as `osv_keys_refused`, reported in the sync report (`keys_refused`), the readiness detail and the fleet health warning. A policy-controlled hold (refuse the install on a too-long key) was NOT built: it would change which packages are allowed and is a decision for the spec author.

Unchanged by decision: `osv_scope` default Public, `osv_stale_match_seconds` pushable, the standalone 2000 ms default timeout question (pending with the user; nothing changed here).

## Third review round (2026-11-18)

Fixed: NEW-1 (a failed authentication pops the credential from the "authenticated before" set and remembers the failed tag for 10 s so repeated attempts cost no lookup; a per-credential lookup limit runs before the 4-permit auth gate, so a valid or revoked credential cannot occupy it; blocked requests are not recorded and each source window is capped at twice the limit; the sticky-block behaviour is documented in the test and below), SEC-2 (one rescue slot per key shared by all followers of that key, a reserved pair of upstream permits for rescue calls), SEC-5 (tenant share applies per organisation: org, group and user keys collapse to their organisation, a firewall token is its own tenant; below the shared reserve every tenant keeps its own floor), drop guard (cleans a poisoned in-flight table; unit test), PyPI comment (verified wording).

Documented behaviour (pre-auth throttle): a source with 10 or more real authentication failures in a minute is turned away without a lookup, unless the request carries a credential that authenticated before. A first-time credential from such a source is turned away until 60 s after the last real failure. Behind a proxy that is not listed in `[server] trusted_proxies` every client shares the proxy's address, so one client's failures block first-time credentials of the whole fleet for that minute; list the proxy in `trusted_proxies` so the throttle sees the real client address. Blocked requests do not extend the block.

Still with the user: the PyPI over-1024-byte hold and the standalone default timeout; nothing changed for either.
