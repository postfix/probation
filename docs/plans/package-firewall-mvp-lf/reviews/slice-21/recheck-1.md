## Findings

R1 - Medium - BLOCKING - spool fairness regressed: one service key can now take all 8 places (F2 not closed)
Location: src/http/spool.rs:29-41 (`owner_of`), src/http/limits.rs:30-32 and 162-170 (`SPOOLS`, `SPOOLS_PER_OWNER`, `spool_seat`); the comment at limits.rs:32 still promises "one valid key cannot take them all".
Failure: `owner_of` hashes the service key id together with the presented credential headers, and those header values are never validated. A caller with ONE valid service key sends 8 uploads with 8 different junk `Authorization` values: 8 distinct owners, each under the 4-per-owner cap, so all 8 global seats are taken and every deploy of every tenant and family gets 503. Before the round the cap was per key id (4 of 8), so a second key was needed. The new floor does not release the seats: a body at 1 KiB/s passes `MIN_RATE` and the 15 s idle limit, and holds its seat for the whole `BODY_DEADLINE` (15 min). The evidence line "a trickle ends in about 35 s" holds only below the floor. Attack cost: 8 sockets, about 1 KiB/s each, junk credentials. No test covers distinct credentials from one key against the global bound (tests/maven_service_write.rs:270-302 checks only that credential B still deploys while A holds its 4).
Correction: keep a per-key-id cap (the old 4) in addition to the per-credential cap (or count both and refuse on either), and either raise MIN_RATE well above 1 KiB/s or shorten the deadline for bodies with no declared length. Cost: one more counter map in `spool_seat`, one more test (8 junk credentials under one key leave places for a second key).
Closure check: a test with 8 distinct junk `Authorization` values on one key, then a deploy under another key must return 201, not 503.

R2 - Low - PLAUSIBLE - first-download `.sha1` check fails closed on a 403 for an absent sidecar
Location: src/artifacts/download.rs:699-741 (`Err(error) => return Err(...)`).
Scenario: a registry that answers 403 (not 404) for a key that does not exist (S3-style bucket without list permission) and publishes no `.sha1`: every first download of a file fails. 404 is handled and is the Central/Nexus/Artifactory case. Redirects are not a concern: the small-file rule keeps sidecars off the archive redirect, and `fetch_metadata` follows only same-origin hops. Decision for the product owner: treat 403 like 404 for the sidecar only, or document the requirement that the registry publish or 404 its checksum files.

R3 - Low - CONFIRMED - existing-row path rewrites the row on every request when a file's own date is later than its unit's
Location: src/maven/serve.rs:420-424 (`reference_for_file`, the `else if dated.is_none_or(...)` arm compares the row with the UNIT date, not the file's later date).
Effect: a classifier or sidecar whose stored date (max of unit and file) differs from the unit date triggers `commit_request_references_in` on each GET (a DB write per read, no semantic change since the store keeps the max). Efficiency only; compare against `max(unit, stored)` to skip.

R4 - Low - PLAUSIBLE - credentialed catalog reads hold the process-wide catalog slot for a whole fetch
Location: src/maven/serve.rs:914-919. A caller of a slow selected registry holds the one slot up to the document deadline (120 s); other registries' catalog requests wait 30 s then 504. No deadlock (the slot is always taken before a refresh place, no path takes them in the other order). Availability of one document type only.

R5 - Low - PLAUSIBLE - idle limit 15 s (was 60 s) applies also to the wait for the first chunk
Location: src/http/spool.rs:95. A client that sends headers and then stalls longer than 15 s mid-upload (flaky mobile link, TCP retransmit stall) is cut and must retry the whole upload. Unchanged: BODY_DEADLINE 15 min, so a 1 GiB jar needs about 1.2 MiB/s on average to finish; the 1 KiB/s floor itself breaks no legitimate upload.
