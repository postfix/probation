## Closed from recheck-2
- N1 closed for the cases it named. Certificate mode now counts `principal.account` (an `Org` PlaceRef built from the certificate, never `None`: `PlaceRef` is not optional, managed/mod.rs:296-299), hashed with a mode tag; `key_id` is no longer used. Service mode counts the client address. All six forwarders call `spool::owner_of(app, principal, headers)` (pypi:358, maven:161, cargo:322, nuget:246, rubygems:196, registry_action:87-89). The cert-mode unit test builds a `Principal` by hand, but `owner_of` reads only `principal.account` and `app.config.service_policy` (None in certificate mode: `management` and `service_policy` are mutually exclusive, config.rs:742), so the unit test exercises the same function the forwarders call. The source-scan test pins the call text in each file (mutation: reverting one forwarder to `key_id.0` fails it; replacing the account by a constant inside `owner_in` fails the two-tenant unit test).
- N2 closed: `grow` refuses past `total/2` per owner dimension; a burst cannot hold the budget.
- N3 closed: the rate clock starts at the first chunk; windowed floor cuts burst-then-trickle (test with 1 MiB burst then 300 ms trickle).
- Seat and byte release: `SpoolSeat` and `SpoolReservation` are fields of the returned `Spool` or locals of `spool_paced`; every `?`/return path, timeout, cancelled future and panic drops them; `release` runs under a poison-tolerant lock and removes an entry only at 0 seats and 0 bytes; `grow_waiting` enables the `Notified` before `grow` (no lost wake-up). No leak found.
- Header handling in service mode: `X-Forwarded-For` is read only when the peer is inside a listed range (`TrustedProxies::client`, canonicalised, so IPv4-mapped peers match IPv4 ranges); the rightmost entry that is not itself a listed proxy is taken, every header line is read, `ip`, `ip:port`, `[v6]`, `[v6]:port` parse; a non-UTF-8 line or an entry that is not an address falls back to the proxy's own address (shared, never free); a forged left-hand entry is never reached when the proxy appends. Header size is bounded by hyper's header limits, and the scan is O(entries). `trusted_proxies` is validated as CIDRs (config.rs:990-995; an invalid range fails startup) and is documented in docs/configuration.md:46 and docs/operations.md. Peer is read for `service_policy` (logging.rs:243, lib.rs:511), so `peer()` is `Some` for every TCP request in service mode; the owner is computed inline in the handler (task-local still in scope). The server listens on TCP only (no unix socket path in lib.rs), so there is no peer-less case in production.

## Findings

R3-1 - Medium - not blocking - CONFIRMED by code - an attacker needs only two identities to take every place and all the bytes; the IPv6 case needs one /64
Location: src/http/spool.rs:61-64 (the full 128-bit address is hashed), src/http/limits.rs:30 (`SPOOLS_PER_OWNER = 4` of `SPOOLS = 8`), docs/operations.md "Limits" bullet.
Scenario: in service mode the owner is the address. Two source addresses, each with a different junk credential, hold 4 seats each (2 x 4 = 8 = all places) and, by two bursts, `2 x total/2` = the whole budget. At the 16 KiB/s floor a declared length of about 7.2 MiB earns the whole 15 minute deadline (undeclared: 5 minutes), so every legitimate publish is 503 for that time, repeatedly. With IPv6 an ordinary /64 gives 2^64 distinct "addresses", so one machine is many owners. The half-share rule stops ONE identity; it does not bound a caller that controls two. The documentation says the damage is "seconds of one trickle per address": that is true only for a body BELOW the floor (cut in about 35 s); a body AT the floor holds its seat for the deadline. Only publishes are affected (reads and integrity are not).
Correction: count IPv6 clients by /64 (mask the low 64 bits before hashing; cost: one line, and callers in one /64 share a share, as NAT callers already do). Correct the documentation sentence ("seconds") to the 5 and 15 minute figures. A stronger fix (a higher floor for a seat, or admitting only a validated key first) is a product choice: the credential is not validated in service mode.
Blocking: no. Inherent to unauthenticated per-address counting; fail-closed; only the /64 mask and the wording are cheap and should be done.

R3-2 - Medium - not blocking - plausible - the default `trusted_proxies = []` behind a reverse proxy makes service mode one owner for the whole deployment
Location: src/http/spool.rs:55-65, config default (config.rs:420-424, `#[serde(default)]`), docs/operations.md.
Scenario: service-mode firewalls normally sit behind a load balancer. With the default empty list every caller has the proxy's address, so the whole deployment holds 4 places and half the bytes, and one caller with a junk credential and a trickle at the floor pins those 4 for 5 to 15 minutes; the other 4 places are unreachable. That is recheck-2 N1 again, by configuration. The documentation tells the operator to list the proxy, but nothing at startup or in the logs says that the firewall is behind one (the peer is private or loopback and `X-Forwarded-For` is present from an unlisted peer).
Correction: a startup or first-request warning when an unlisted peer sends `X-Forwarded-For` (once per process), and say so in config.sample.toml (it has no `[service_policy]` section at all; only docs/configuration.md lists the key). Cost: one `AtomicBool` and one log line. Decision for the coordinator whether this belongs in this slice.
Blocking: no (documented, operator-controlled).

R3-3 - Low - CONFIRMED - the spool cap is lowered to one artifact for the three envelope forwarders (regression of slices 18, 20, 21)
Location: src/http/spool.rs:131 (`cap.min(spool_total / 2)`), cargo_routes.rs:270, nuget_routes.rs:235, maven_routes.rs:150 (they pass `2 x max_artifact_bytes`), pypi_routes.rs:351.
Scenario: `spool_total = 2 x max_artifact_bytes` (or the 64 MiB floor), so the effective cap is exactly `max_artifact_bytes`. A `cargo publish` or NuGet push body is the artifact plus its envelope (JSON metadata, multipart framing), so an artifact within a few KiB of `max_artifact_bytes` that was accepted by slices 18-20 is now a 413 before the artifact check. Exactly `max_artifact_bytes` of body does pass (`grow` allows equality). Practical size: only artifacts in the last envelope-sized sliver below the limit (and only for non-trivial `max_artifact_bytes` above 32 MiB, where the floor does not lift it).
Correction: give the budget `2 x max + envelope`, or pass the real cap and size the owner share to `cap` (`share = max(total/2, cap)`); closure: a test with a body of `max_artifact_bytes + 1 KiB` for cargo.
Blocking: no.

R3-4 - Low - CONFIRMED - one owner running two concurrent uploads that together exceed its half waits 30 s and one of them is 503
Location: src/http/limits.rs `grow_waiting`, `share = total/2`.
Scenario: a sole tenant (certificate account) starts two uploads of 0.6 x max each. Each reserves while it streams until their sum reaches `max`; both then wait 30 s for the other to free bytes, and one is refused (its drop releases and the other continues). One upload of exactly `max_artifact_bytes` passes; two sequential ones pass. The cost appears only for artifacts above half the (default 5 GiB) cap and two at once from one account. Accept and document, or let `share` be `max(total/2, cap)` as in R3-3.
Blocking: no.

R3-5 - Low - plausible - the rate test counts our own budget wait against the client
Location: src/http/spool.rs:146-177. `grow_waiting` may block up to 30 s inside the read loop; the next chunk then sees a long `elapsed` and a window with few bytes, so a client that is fine but whose owner was waiting for its own bytes can be cut "too slow". Only with R3-4 or a contended budget. Fix: measure the rate over time spent receiving (subtract the wait). Not blocking.

R3-6 - Low - documentation - docs/operations.md still says, in the recheck-1 paragraph (about line 1806), "per service key (at most four of the eight) AND per credential": contradicted by the recheck-2 paragraph below it (account or address, key id counts nothing). The owner hash uses `format!("{:?}", principal.account)`; a change of the `Debug` output of `PlaceRef` would silently re-key owners (harmless, but a test pins nothing). The unit tests do not exercise the credential dimension (every assertion is blocked first by the key dimension); a mutation that drops the credential hash would not fail `spool.rs` tests (the junk-credential integration test in maven_service_write.rs covers it for service mode).
