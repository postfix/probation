## Findings

### F1  Medium  confirmed (mechanism by source trace; not measured)  src/maven/serve.rs:914-919 `serve_catalog`, 176-191 `refresh_places`
Attacker: any caller that can reach `/maven/archetype-catalog.xml` (login-free common route, or any admitted client); no credential needed against the public registry.
Path: `serve_catalog` takes a refresh place first (`refresh_places`: one of 4 per registry and one of 16 process-wide, serve.rs:71-72) and only then waits up to 30 s for the single process-wide catalog slot (`app.maven.catalog`, 919). The catalog is never cached (18.6 MB decoded per request on Central, parsed and re-serialised). N concurrent catalog requests therefore hold N places while queueing for one slot.
Ineffective defense: the per-registry limit (4) bounds the number of builds, but the same places also serve every `maven-metadata.xml` (serve.rs:833) of that registry, and the waiting requests hold them idle. Tokio semaphores are FIFO, so once the attacker keeps a queue longer than about 30 s / (time of one catalog fetch) legitimate metadata requests wait the whole `REFRESH_WAIT` and answer 504, and every waiter also holds one of `max_active_requests` permits.
Effect: a handful of anonymous connections keep every `maven-metadata.xml` of the public registry (and, in service mode, of the shared registry of an organisation) failing with 504 (version ranges, plugin prefix and snapshot resolution break), while each catalog hit also costs about 440 KB of Central egress and an 18 MB parse. A second, weaker form: the same places are held for the whole dating of a 2,000-version artifact (DB reads of every row, 2,000 OSV evaluations, serve.rs:560-637), so a flood of metadata requests for one heavy artifact queues the rest the same way.
Smallest correction: take the catalog slot before `refresh_places` (waiting costs nothing then), and cache the catalog and its filtered result for a few seconds for credential-free reads in the existing `raw` table (it is capped at 16 MiB per entry, so allow one larger entry or store the filtered edit list). Cost: one reorder and one cache entry. Closure: unauthorized-action check: 32 parallel catalog requests against a slow upstream fake leave `maven-metadata.xml` of the same registry answering within its normal time and upstream catalog fetches stay at one per TTL; legitimate check: `tests/maven_registry.rs` catalog cases (blocked archetype removed, `<repository>` removed) still pass.

### F2  Medium (shared class, residual of slice 20 F2)  confirmed (source)  src/http/maven_routes.rs:154, src/http/spool.rs:55-60, src/http/limits.rs:30-32 and 162-169, src/managed/service_policy.rs:480
Attacker: anyone who can reach the service route; needs only a header `Authorization: Basic x` (admission checks the shape, not the value, registry_read.rs:175-185, and the credential is never validated before the body is spooled). A registry that has a target, or a configured `maven_publish_url`, is needed for the request to get past `publish_target` (serve.rs:971-987).
Path: in shared-service mode the spool owner is `principal.key_id`, which is the service snapshot's one `key_id` for every caller, so `SPOOLS_PER_OWNER` (4) is a limit on the whole service, not on a caller. Four `PUT`s with chunked bodies and one byte every 59 s hold four seats for `BODY_DEADLINE` (15 min) each, at almost no bandwidth; all other seats up to `SPOOLS` (8) are one more such request away.
Effect: with 4 to 8 trickling connections, `spool_seat` returns `Overloaded` for every deploy of every family (Maven, NuGet, Cargo, RubyGems, PyPI) of every tenant of the service for as long as the attacker keeps reconnecting. Disk fill (slice 20 F2) is closed; this is the starvation side of the same mechanism. A related smaller effect: a deployed `PUT`/`DELETE` with a junk credential is relayed to the registry's deploy endpoint, so the firewall can be used as a credential-guessing relay and its egress IP can be locked out by the registry for all users.
Smallest correction: key seats by the presented credential (hash of the `Authorization` value) instead of `key_id`, and shorten the idle limit for a body that has sent less than a few KiB; optionally forward the first request headers upstream with `Expect: 100-continue` so a refused credential never spools. Cost: a hashed owner key and one constant. Closure: unauthorized-action check: 8 trickling uploads with distinct junk credentials from one source do not stop a legitimate deploy with a fifth credential; legitimate check: `tests/maven_service_write.rs` deploy and 413 cases.

### F3  Low  confirmed (source), exploitable only with a publisher-controlled `maven-metadata.xml` and a lenient client  src/maven/meta.rs:107-130 and 115-121, src/maven/serve.rs:860-868
The reader takes a `<version>`, `<latest>` or `<release>` only when it is a leaf (`leaf()` is `None` if the element has a child element). A `<version>2.0<x/></version>` is therefore neither judged nor cut, and a non-leaf `<latest>` is neither checked nor replaced; a repeated `<latest>` or `<release>` keeps only the last one in `meta.latest` (assignment, line 118-119), so the first still names a held version after filtering. Separately `meta.has_plugins` is tested before the artifact branch (serve.rs:860), so a document that has both `<plugins>` and `<versioning><versions>` at an artifact path is only plugin-filtered and its versions, `latest` and `release` pass unfiltered (the evidence says a document of the wrong kind is a 502; this combination is not refused).
Exploit scenario: a tenant that can deploy `maven-metadata.xml` to a hosted registry whose server stores it verbatim, or a compromised upstream, lists a held version so that a client which reads the first duplicate, or tolerates child elements (Maven's xpp3 does not: `nextText` fails on a child element and strict duplicates fail; the last duplicate wins in the non-strict resolver, which is what the firewall edits; Gradle's parser was not checked), resolves it. The held version's files are still refused by the file gate, so the effect is the names leaking and a resolution that fails late, not delivery of a held artifact.
Smallest correction: make `meta::read` return an error (502) for a non-leaf `version`, `latest`, `release`, `snapshot*` leaves, for a repeated singleton (`latest`, `release`, `lastUpdated`, `snapshot`, `timestamp`, `buildNumber`) and for `has_plugins && (has_versions || !versions.is_empty())`; also refuse element names containing `:` (a prefixed `m:versions` is not recognised by the firewall but is `versions` to a namespace-aware reader that binds the prefix to the default namespace). Cost: about 15 lines and one test per case. Closure: unauthorized: each of those documents is a 502 and never served; legitimate: the Central documents of the evidence and `a_large_listing...` still pass.

### F4  Low  plausible  `.module`/`.pom` pass-through (serve.rs:314-331 deliver the file unmodified), src/maven/meta.rs:162-166
URL completeness: the archetype `<repository>` is removed and the settings line uses `mirrorOf *`, which covers Maven POM `<repositories>`. Gradle Module Metadata files (`.module`) are delivered unmodified and may contain absolute `url` values (`files[].url`, `available-at.url`); a Gradle build resolving through this repository can be pointed at another host by a dependency's own publisher, so the blocklist, cooldown and OSV decisions of this firewall do not apply to the file fetched there. Whether Gradle follows an absolute `url` outside the repository was not verified here, so this stays plausible. Correction: parse `.module` as JSON (bounded, 16 MiB already), refuse or rewrite any absolute `url` or `available-at.url` that is not below this firewall, and add a test; if that is judged out of scope for the feature, record the limit in docs/operations.md next to the POM `<repositories>` note. Smaller point: `archetype_repositories` stops recording after `max_entries` (meta.rs:163-165) while `archetypes` over the bound is an error, so one archetype with more than 500,000 `<repository>` children would keep the later ones; make that `too_many` as well.

### F5  Low  plausible (depends on the registry)  src/maven/serve.rs:491-495, 457-458
A unit's age is the `Last-Modified` of its POM and every file of the unit inherits it. The file's own `Last-Modified` is ignored (the existence probe discards headers, serve.rs:272-300). On a hosted registry that allows redeploy or adding classifiers to a published version (Nexus hosted with redeploy allowed, Artifactory), a new `lib-1.0-natives.jar` or `.module` added to a months-old version is served at once under the old POM date; the pin only catches a changed existing file, not a new one. Central itself is immutable, so the public registry is not affected. Correction: take the maximum of the POM date and the file's own `Last-Modified` when a file row is first created (the validators are already returned by `fetch_metadata`; the probe can use the same call with a 1-byte cap and keep them). Cost: one `max` and keeping validators in `exists`. Closure: a file whose own date is young is held although its POM is old; an old file is unaffected.

### F6  Low (hardening)  confirmed (source)  src/maven/serve.rs:326-328
`expected` is empty, so the first download of a file is pinned unverified. Maven Central and every Maven repository publish `.sha1`/`.sha256` next to each file and send `x-checksum-sha1` (measured, evidence). The first-seen bytes could be compared with that sidecar before pinning, which would turn a transport-level corruption or a poisoned cache in a mirror (`maven_upstream_url` is a mirror) into a refusal instead of a permanent pin. Not exploitable against Central over TLS.

### U1  Unknown (inherited class)  src/maven/serve.rs:304-310
Evidence says a hosted repository stamps the upload time and the publisher cannot choose it. That holds for Central and for Nexus. For Artifactory and GitHub Packages-style feeds, whether a publisher can set the stored modification time (deploy with a chosen last-modified, import, checksum deploy) was not established here. A back-dated POM `Last-Modified` there skips the cooldown for the whole unit exactly as slice 19 F1. Decision/check for the user: which hosted repositories organisations register, and whether any lets the depositor set the stored time.
