## Findings

### S28-1 Medium, confirmed (spec conformance), impact plausible: classify_read result is advisory; metadata/project/refusal caches and CacheToken are not gated
Location: src/http/service_registry.rs:46-57, src/http/logging.rs:176-184, src/http/credential_read.rs:8-12; only consumer src/artifacts/mod.rs:360.
Path: a GET/HEAD carrying any non-allow-listed header or query (Authorization, Cookie, ?token=, X-JFrog-Art-Api, unknown header) is classed RequestScoped, which only sets a task-local flag. The sole reader of that flag is the artifact body path (open_or_download). npm/pypi packument and simple-index handling (src/npm/mod.rs, src/pypi/mod.rs), the project/snapshot caches and the render caches never read it. `CacheToken` is constructed by classify_read but no cache accepts it (grep: no other use), so the 03 requirement "the shared content, metadata and snapshot caches accept a write only through a value that type cannot produce" (LS-F4, C1028, T5) is not implemented. The `absent` refusal cache is skipped in service mode wholesale (npm/mod.rs:752, pypi/mod.rs:601), which is safe but not the specified mechanism.
Effect: today caller headers are not forwarded upstream on reads (upstream auth is the registry-held registry_read_authorization, pypi/mod.rs:542, artifacts/mod.rs:133), so I found no live leak of a caller credential through the metadata cache; the exposure is that the invariant rests on that wiring, not on the type seam. Any family row (17-24) that forwards a caller credential on a metadata read will populate the shared cache. Also, registry-held credential metadata is cached and shared across principals of that registry (intended, keyed by registry_id).
Smallest correction: make the shared cache insert APIs (projects, absent, rendered/metadata) take `&CacheToken`; thread `ReadClass` from respond into adapters instead of a bool metric. Closure checks: `credential_bearing_read_never_enters_shared_caches` for packument/simple routes per carrier (Authorization, Cookie, ?token=, unknown header) asserting cache miss afterwards; control that an allow-list-only request populates the cache.

### S28-2 Medium, confirmed: own-listener denial is activation-time and IP-literal only
Location: src/http/service_connector.rs:73-87 (`denies` ignores `listener`), :121-141 (`check_target` is the only place `listener` is used), src/upstream/resolver.rs:67-72 (connect-time check uses `denies` only), src/upstream/origins.rs:203-206.
Path: an org admin (or whoever controls a registry target) sets target_url to https://attacker-host.example/ whose DNS resolves to the enforcer's own non-loopback address (pod IP, e.g. 10.x, not in control_plane_cidrs) and the listener port. At activation the host is a Domain, so check_target returns Ok. At connect, GuardedResolver/check_connected_peer call `Denylist::denies`, which does not consider the listener address or port, and private addresses are allowed only if an approved private CIDR exists (or `allow_private_addresses`), so exposure needs an operator-approved private CIDR covering the pod range; the denylist was designed to override exactly that ("its own private CIDRs cannot unlock") and does not for the listener. Same gap when the listener is wildcard (0.0.0.0/::): check_target compares the literal to 0.0.0.0, which never equals a real interface address.
Effect: SSRF back into the enforcer's own listener (loopback-exempt admission paths, management/health surfaces), limited by TLS on the target (selected registries require https) so the enforcer must present a hostname-valid cert; impact bounded but the D5 property "own listener is absolutely denied" is not met for hostnames.
Smallest correction: carry the listener port into Denylist and, in the connect-time check, reject any answer whose (ip, port) equals the listener, plus resolve wildcard listen to the host's interface addresses. Closure: test with a fake resolver returning the listener's IP and a descriptor hostname on the listener port (must refuse) and a legitimate private registry on another port (must pass).

### S28-3 Low, confirmed: credential temp parent not tightened when pre-existing
Location: src/http/credential_temp.rs:98-113 (check_owner compares uid with data_dir only; mode of an existing `credential-reads` is not checked or fixed), :132-143 (sweep).
Path: if the parent already exists group/other-writable (operator error, restored backup), a local user can plant a symlinked or crafted `<pid>-<nonce>` entry. sweep skips symlinked directories (is_symlink) and Rust's remove_dir_all does not follow a swapped symlink, so no arbitrary deletion was found; but a planted real directory whose `lock` is a symlink makes sweep open the target read+write (no truncate) and lock it, and the nonce (pid + subsec nanos + counter, :104-110) is predictable so a pre-created child dir may be reused path-wise (create_dir would then fail: availability only). The created dirs are chmod 0700 after create_dir (brief 0755 window, :111-112, harmless since files are created afterwards inside).
Smallest correction: refuse (UnsafeParent) or chmod when an existing parent has mode & 0o077 != 0; use `mkdir` with mode 0700 atomically (DirBuilderExt). Check: pre-create the parent 0777 and assert open() refuses or tightens.

### S28-4 Low, confirmed: no per-request/total byte cap by default
Location: src/http/credential_temp.rs:61-64, src/artifacts/download.rs:477-510 (bounded only by `max_artifact_bytes` and download permits).
Effect: credential-bearing reads of large artifacts fill the data volume; bounded per request by max_artifact_bytes and by permit count, so it is a documented availability trade-off (spec: no default cap). 503 NoSpace has no Retry-After. Informational hardening: ship a default total cap or alert on the readiness gauge.

### S28-5 Low, plausible: loopback peers skip Host validation (documented deviation) and selected_upload ordering
Location: src/http/service_registry.rs:35 (`!peer.is_loopback() && ...`), src/http/pypi_routes.rs:341-345.
(a) A reverse proxy or sidecar on the same host presents a loopback peer, so every external request bypasses LS-F10 Host binding; admission is by actual TCP peer only (X-Forwarded-For is correctly never read, listener_admission.rs:44-47). Deployment must not front the enforcer from loopback; the evidence file flags this deviation for a decision. Host canonicalisation itself is sound (single Host required, userinfo/path/query rejected, backslash form rejected by `Url`, non-UTF-8 rejected); url strips tabs/newlines so `exa<TAB>mple.com` compares equal, which is harmless.
(b) selected_upload now checks the Authorization form before origin/registry shape (the intended fix), but `admit_pypi` still runs first (:340) and takes a permit and can answer registry-specific errors before the 401, so "peer trust and registry shape never decide it" holds only for the origin/registry-origin checks. Minor information exposure to an admitted peer; move the header check above admit_pypi if the spec means strictly first.

### S28-6 Unknown: snapshot replay at equal revision
Location: crates/probation-policy/src/api.rs:101-104 (digest excludes registries and rate fields, "latest-wins at equal revision"), src/managed/service_policy.rs ActiveRevision::admits.
A replayed older response at the same revision can restore an old registry set (trust flag, osv_scope Public, target_url). Needs a network position against server_url; I did not verify that server_url is required to be https with certificate validation in config (only that it must be an origin). Check config validation; if http is accepted, this is a medium. Lower revisions and equal-revision digest changes in the policy body are rejected structurally (closed).
