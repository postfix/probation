## 2. New findings (fix round code)

R1 medium, resource (needs the user's explicit acceptance or a cap): per-spelling reference-row growth is not bounded enough for the shared service. Location: src/rubygems/serve.rs `refresh` / `current_project` (`spellings`), `reference_of`. A reference id includes the file name, so each case spelling of one gem (`rails`, `Rails`, `rAils`, 2^n for an n-letter name) is one upstream info fetch plus one commit of up to `max_references_per_project` rows. rubygems.org answers any spelling, so any admitted client can mint them; there is no pruning in the store (grep: none). `commit_request_references_in` (service mode) persists references too. The project row is shared, so only reference rows (and first-seen/pin rows) grow. The in-memory `spellings` set clears at 4096, which makes every spelling revalidate once more (extra upstream load, not a leak). Judgement: for standalone with trusted clients acceptable; for a multi-tenant service it is an unbounded amplifier (one request, hundreds of rows, never reclaimed). Correction: cap committed spellings per (registry, gem) (for example 4; refuse or serve the client's spelling uncommitted beyond it) and test with 10 spellings; or record the user's acceptance in the ledger. Blocking: no (admitted client, storage not auth), but record the decision.

R2 low-medium, correctness/availability: the recent-list cache stamp is taken before the crawl. `at` is read before `fetch_recent`, so a crawl longer than 60 s (INDEX_TTL) is stale when stored and the next index build re-crawls the whole list (single flight then serialises them). Also the crawl runs inside the request future: a client that disconnects (gem/bundler read timeouts are about 60 s) drops the future, nothing is stored, and the next request starts over, so a real registry whose list takes more than the client timeout never completes for such clients. Evidence estimates about a thousand pages per 7-day window; at 0.1 to 0.3 s per page that is 100 to 300 s, near the 300 s deadline. PLAUSIBLE for rubygems.org (page count and latency not measured; the E2E fake pages two rows per page). Correction: stamp after the fetch (one line), and run the crawl in a spawned task owned by the cell so a cancelled caller still fills it; measure the real page count once and size the caps with margin. Blocking: no (fails closed or slow, never lists a young version).

R3 low, resource: credential-bearing (non-shareable) index reads have no cell and no flight, so N concurrent such requests each crawl up to 2,000 pages before the heavy permit is taken. Bounded only by admission permits. Correction: a small per-registry semaphore (1 or 2) on the crawl for non-shareable reads. Blocking: no.

R4 low, freshness: `to` is the request start and the list is cached 60 s, but the tuple index is fetched later. A version published after `to` is absent from the list, so it is dated `bound` (older than the cooldown) and listed in the legacy index for up to crawl time plus 60 s. Only the listing is affected: info, gemspec and gem file stay gated by their own dates (403/404), so the result is the F1 symptom for brand-new versions, not artifact delivery. Correction: fetch the tuple index first and use its fetch time as `to`, or accept and document. Blocking: no.

R5 low, test gaps: no test for the 60,000-row cap, the 300 s deadline, the OTP 64-byte cap, or that OTP is never sent by the other four ActionRequest sites (they pass `otp: None`, verified by reading; no Debug derive on ActionRequest, no logging of it). Add one table-driven test each if cheap.

R6 low, PLAUSIBLE: pins and first-seen rows are keyed by reference id, which includes the spelling, so a pin recorded under `RedCloth` does not apply to `redcloth-...gem`. A registry that changes the bytes of an existing version (only private registries can) could be delivered under a new spelling. Needs a malicious or buggy upstream plus a client choosing the spelling. Correction: key pins by lower-case (name, version, filename-lower) or cap spellings (R1 fixes both).

## 3. E2E-003 rewrite (tests/e2e/scenarios/e2e-003-osv.mjs)

Contract (03 LS-F2, item (h), LS-F7): a managed firewall asks the management server; the server answers per result `probation_degraded` at its 1500 ms deadline; the firewall fails open, counts degraded lookups in the sync report, and the fleet page shows the warning; readiness is unchanged. The firewall logs nothing for a slow or refused OSV (consistent with the old log assertions being obsolete, as the baseline run at e3226bf showed).
- Fail-open outcome: kept. Still 200 and an `npm install` that works for a MAL package nobody asked about; still under 4 s. Delay raised to 20 s so the server's late answer cannot land mid-step. Sound, and the switch to a fresh package is justified by the remembered-answer premise (a listing asks about every version).
- Timeout and refused-connection evidence: replaced, not dropped. Old log greps become (a) only the management server's address ever reached api.osv.dev, (b) a fake row with fault `delay`, (c) a fake row with fault `reset`, plus the unchanged fleet-page `cannot reach OSV`. This is at least as strong on what happens at OSV, and a stronger check that a firewall never talks to OSV directly. Not covered any more by this scenario: the firewall-side client timeout against a hanging management server (the old WARN could only come from that path); the spec lists unit tests for it (`managed_osv_fails_open_within_timeout_when_server_down`, `osv_slow_upstream_and_coalesced_follower_answer_degraded_before_client_timeout`). Not a weakening of the contract, a changed observation point.
- Healthy relaxation: accepted. fleet.rs `healthy_text` returns `Healthy; OSV warning: more than 5% of OSV lookups degraded` while the five-minute alert window holds, and LS-F7 says readiness is unchanged with the warning shown beside it. The new regex allows exactly "Healthy" or that single warning text, so any other suffix still fails. Residual: it no longer proves the outage raises the warning or that the warning clears; the first is optional extra, the second is a five-minute wait and is covered by unit tests.
- Nit: the header comment (lines 17 to 19) still says "firewall-2 logs the failures"; update it.
