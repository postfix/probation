## Findings

### SR17-1 Medium, confirmed. src/rubygems/serve.rs `reference_for_file`, info.rs `filename_candidates`
Prerequisite: any admitted client (standalone) or any tenant (shared service). Entry: `GET /rubygems/gems/{file}` or `/quick/Marshal.4.8/{file}` with a name such as `a-1-a-1-a-1-...gem` (up to 128 chars of prefix). `filename_candidates` yields one candidate per `-<digit>` split (up to about 60), and the loop calls `current_project` for each, so each distinct bogus name causes an upstream `/info/{name}` fetch before any policy decision. In service mode (`app.service_policy().is_some()`) the absent-cache is skipped entirely and every call refreshes. Effect: about 60x upstream request amplification per client request, unauthenticated-name probing of rubygems.org from the proxy's IP (rate-limit or ban risk for all users), and tenant-controlled upstreams are hit as well. Ambiguity refusal is correct, but the fan-out happens first.
Smallest fix: bound candidates (for example at most 4 splits, or resolve only splits whose left side is already in the stored project table or absent cache first), and apply the absent cache in service mode. Closure checks: a 60-split name issues at most N upstream calls (counting fake upstream); `foo-1-2.0.gem` ambiguity and legitimate platform gems (`nokogiri-1.16.0-x86_64-linux.gem`) still resolve.

### SR17-2 Medium (High if the shared service lets tenants choose an upstream), confirmed by static trace. serve.rs `serve_index`, marshal.rs `Budget`/`value`
Prerequisite: a client who can request `specs.4.8.gz`/`latest_specs`/`prerelease_specs`; to control content, a compromised upstream or a tenant-selected registry origin. Two parts.
(a) No caching or single-flight: every request re-downloads up to `max_metadata_bytes` (64 MiB), inflates up to 128 MiB, runs the full filter on a spawn_blocking thread (about 1 s CPU for the real full index per the corpus record), and first loads every known project payload and runs `evaluate_scoped` over all entries of all known gems. Concurrency is bounded only by `max_active_requests` (1024); there is no limiter for this heavy path.
(b) The memory budget under-counts. Only retained link-table slots, string bytes and symbols are charged (64 B per retained node). In-flight values are not: in keep mode `[`/`{` push every parsed child into a `Vec<V>` (`V` is 32 B) until the container ends. A single array declared with millions of 2-byte `i` items is bounded only by the 20,000,000 node cap, so about 640 MB (about 1 GB with Vec doubling) is allocated while the charged total is near zero, and only after parsing does `tuple_parts` reject it. Separately the nominal charge under-estimates real size (measured: nominal 107 MB, process peak 283 MB for the real index; per retained string the real cost is roughly 140 B plus data against 64 B plus data charged), so the 512 MiB budget can resident-grow to about 1.3 GB per request. Many concurrent hostile requests multiply this; earlyoom-style OOM kills the whole proxy.
Smallest fix: in tuple mode reject any value whose shape is outside `[String, Gem::Version, String]` before collecting children (parse the tuple with a typed 3-slot reader; allow containers only inside the Gem::Version payload with a tiny cap), or charge `size_of::<V>()` per in-flight child; charge about 150 B per retained node; add a global semaphore (1 to 2) around index filtering and a short-lived cache of the filtered output keyed by (registry, file, policy fingerprint, upstream validators). Closure checks: a stream `[` + 10M `i` items is refused with Memory/Nodes while RSS stays under the budget; the real 1.76M-tuple index still filters; N concurrent requests produce at most the semaphore's worth of RSS.

### SR17-3 Low, confirmed (executed witness). src/rubygems/inflate.rs zlib branch
`flate2::read::ZlibDecoder::new(&[u8])` wraps the input in a 32 KiB BufReader, so `reader.get_ref()` is the slice after the BufReader drained it. Witness (flate2 1.1.10, scratch crate, since deleted): zlib stream plus 16 trailing bytes leaves `get_ref().len() == 0`, so "bytes after the last member are refused" does not hold for zlib; the gzip branch (bufread, exact slice) does refuse (witness: error, 6 bytes left). `consumed` for the ratio check is also overstated by up to 32 KiB (lenient only; the size cap still holds). Effect: a quick gemspec with up to about 32 KiB of unvalidated trailing bytes is served byte-for-byte. Ruby's `Zlib::Inflate.inflate` ignores trailing bytes (checked with local ruby 3.3), so the bytes are not interpreted by the stock client and impact is hardening only. Fix: use `flate2::bufread::ZlibDecoder::new(input)` (as the gzip branch does). Check: zlib plus trailing byte is `Malformed`; a plain real gemspec still passes.

### SR17-4 plausible, severity Medium if confirmed, UNKNOWN. serve.rs `gem_name`, names.rs canonical_name
Gem names are kept case-sensitive end to end (cache key, candidate name, policy/blocklist/OSV name, upstream URL). If rubygems.org (or a private mirror) resolves `/info/Rack` to the `rack` index case-insensitively, a client asking for `Rack` is judged as the distinct name `Rack`, so blocklist entries and OSV matches for `rack` do not apply; the returned lines and `gems/Rack-x.gem` fetch would be those of rack. No code checks upstream-returned identity against the request. Deciding check: one read-only request of `info/<mixed-case existing gem>` and `gems/<MixedCase>-<ver>.gem` against the real upstream (needs authorization; not run), or add the real corpus witness. If upstream answers a different case, fix by canonicalising by the registry's answer (for rubygems.org: refuse any name that is not the exact case listed in `/names`, or lower-case for the public registry) and add a regression test.

### SR17-5 Low. serve.rs `serve_index` listing of unjudged and not-yet-cached tuples
Tuples of gems with no stored compact index are judged by block rules only (publication forced to `Upstream(0)`, no OSV, no age); a version newer than the stored info of a judged gem is also kept (only `refused` is subtracted). So `specs.4.8.gz` advertises versions that `/info` would hide (fresh releases, OSV-malicious versions of never-seen gems). Delivery stays identity-gated (gemspec and gem route through the index), so no artifact is delivered; the effect is disclosure of the name/version only and client resolver confusion (a listed version that then 404s). Already documented in the function comment; recorded as an accepted residual needing user acknowledgement. Platform keying is by `entry.platform` or `"ruby"`; a spelling mismatch between info and tuple platform would also fail open in the listing only.

### SR17-6 Low. names.rs `gem_segments`
A segment of more than 38 digits fails `u128` parse, so such a version has no canonical form and only matches by identical spelling; a block on `1.<40 digits>` does not match the entry `1.<40 digits>.0` (Gem::Version treats them equal). Needs a hostile registry plus a block on such a version; negligible. Fix: compare numeric segments as trimmed digit strings instead of u128.

### Observation (not a finding): migration and UnknownEcosystem
0014 only widens four CHECKs (names match the 0001/0007 inline auto-names); old rows satisfy the widened checks. `ecosystem_of` no longer maps an unknown tag to npm (good, fail closed). Consequence: any stored `conan`/`oci` row makes `load_layer` fail, so a binary older than the data fails every policy load for that place rather than skipping the rule (LS-F3's "skip only the affected rule" default concerns the snapshot parse; this is the server store). Safe direction; rollback is documented as unsupported. The migration comment says "ten ecosystems" but lists nine (comment only).

## Codec assessment (deviation from pinned marshal-rs)
Acceptable security-wise, and arguably stronger than wrapping marshal-rs, because LS-F13 requires an object table, node count, per-class payload kinds, cumulative depth over nested streams and typed re-render, none of which marshal-rs's Reader offers (confirmed by the evidence's reasoning; I did not re-audit marshal-rs). Reasons: single allow-list dispatch with a closed tag set (0 T F i l f(spec only) " I : ; [ { @ U o u); every other tag, including `e`, `C`, `S`, `c`, `m`, `d`, `/`, `}` and `M`, refuses; class names compared after lossy UTF-8 so a match implies exact bytes; payload kind enforced per class; depth is checked at every `value` entry and nested streams add one level on the shared budget (outer plus inner at most 32; recursion cannot exceed it); nodes and memory budgets are shared with nested parsers; each nested stream has its own symbol and object tables; length prefixes never preallocate and are checked against remaining bytes; negative or oversized lengths and bignums over 64 bits refuse; typed re-render writes only typed fields (name, version string, platform with encoding ivar) so no input bytes are spliced, and link numbering in the output is generated from the writer's own counters; object links to containers refuse in keep mode so no typed aliasing; trailing data refuses. Residual caveats: (1) the memory accounting gap in SR17-2; (2) the user decision that the deviation needs an explicit yes is outstanding (slice-17.md says so); (3) no fuzz or property test is part of the evidence, only hostile fixtures. I recommend a cargo-fuzz or proptest target on `filter_tuple_index` and `validate_gemspec` (run under the capped systemd-run scope) as a closure check before a CLEAR; (4) `string_ivars` accepts an arbitrary `encoding` name that is re-rendered, which can make Ruby raise on load, an upstream-trust DoS of the client only.
