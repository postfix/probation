## Findings

### Medium

**M1. "About four times the worst measured run" is false for most bounds (invented round numbers).**
benches/transport_hot_paths.rs:6-9 and :32-37, tests/transport_rated_load.rs:3-4, docs/operations.md section 22 ("each about four times the worst value over five runs"), evidence/slice-27.md runbook ("a runner within a quarter of this host's speed passes").
Using the bench's own worst values: cheap read p95 worst 0.042 ms vs bound 1 ms (24x); refusal p95 worst 0.018 ms vs 0.5 ms (28x); cheap throughput worst 30,000/s vs floor 3,000/s (10x); npm p95 worst 42 ms vs 250 ms (6x); only npm throughput (16/s vs 5/s, 3.2x) and the debug read/refusal/rps bounds (about 4 to 5x) match. The file header says "three runs", the constant block says "five runs", the debug test says "three runs". Consequence: the bounds are round numbers, not measured multiples. They will not flake, but they also will not catch a 20x regression of the eight cheap transports, and the runbook sentence tells a release manager the opposite. Scenario: admission cost grows 20x (0.8 ms p95), `--assert` still prints PASS. Fix: state the real ratios, or tighten to about 4x of the worst measured and say which runs.

**M2. The bench and the debug test never assert what the read answered, so the "hot path" can be a miss path and still pass.**
benches/transport_hot_paths.rs:72-85 (statuses printed, never judged); tests/transport_rated_load.rs:47 (`*status < 500 || 502 || 503` accepts every status except 500, 501 and 504 and above, so effectively nothing) and the debug test reads npm at `/registry/npm/3/left-pad`, not the warm fixture (`hot_read(surface, false)`), so even npm is a miss there. Concurrent phases (`concurrent`, tests/common/transport_load.rs:161-185) count any response. Scenario: the npm warm fixture path breaks and answers 404 in 50 microseconds: the npm p95 bound (250 ms) and the 5/s floor pass trivially and the "npm warm 100-version document" row of section 22 is no longer what is measured. Only 2 of 9 families (npm in the bench, Conan ping) are served at all; docs section 22 says so honestly. Fix: assert npm status is exactly 200 and Conan 200 in the bench and in the test; assert the miss families answer one stable status.

**M4. `osv_coverage_view_matches_mapping` does not fail when a new `Ecosystem::ALL` member lacks a mapping; it is partly tautological.**
crates/probation-server/tests/osv_coverage_view.rs:13-36. `coverage()` is built from `Ecosystem::ALL` with `osv_ecosystem(e)`, and the test compares the view to `osv_ecosystem(e)`: same function on both sides. A new variant without an arm does not compile (exhaustive `match` in `osv_ecosystem`), so the real guard is the compiler, not this test. A new variant WITH an arm passes without any oracle edit: the hand table (:27-31) is iterated over its own nine rows, not over `ALL`, so a tenth family with a wrong spelling is accepted. The comment at :10-12 states the first half correctly; the evidence row 25 ("every `Ecosystem::ALL` member covered; probes P1 killed it") overstates. P1 (dropping OCI from `coverage()`) is a real kill, but it mutates the view, not the mapping. A plausible mutation of the mapping spelling (`Some("PyPI")` to `Some("pypi")`) is killed by the oracle table; a mutation of `ALL` (omit Conan) is killed by `rows.len()`. The one case in the review question (a new member with no mapping) is killed by the compiler only. Fix: iterate the oracle over `ALL` and fail on a member with no oracle row (cross_plan_acceptance.rs:114 already does this), and say in the doc that the compiler is the first guard.
Related: the add-registry form's family `<select>` is hand-written (registries.rs template), so a tenth family appears in the coverage table "without an edit" (docs/operations.md section 22) but not in the add form.

### Low

**L1. Debug floors in `tests/transport_rated_load.rs` are wall-clock bounds with no retry.** Bounds are about 4 to 5.5x over a 32-core, load 15 host: read p95 2 ms vs 0.36 ms worst (5.5x), refusal 1.5 ms vs 0.31, 800/s vs 3,298/s, RSS 64 MiB vs 6.3. It passed here at load 95 to 108, which is good evidence it is not fragile on a loaded host; the worker count is fixed at 4 so a 4-vCPU runner has comparable parallelism. Residual risk: p95 of 100 samples fails with 6 samples over 2 ms (one preemption burst). It is part of `cargo test --workspace` in the release gate, so a flake blocks a release. Consider asserting p95 of 100 samples only against the median times a factor, or run the sequential phase twice and take the better. The debug test is deterministic in its functional asserts (403 every time, 401 every time).
**L2. `cargo bench ... -- --assert` semantics are correct** (cargo passes `--bench` plus the trailing arguments to a `harness = false` main; `args().any(== "--assert")` finds it; a panic exits 101; verdict failure exits 1). Two caveats: the bench uses a default multi-thread runtime (all cores) so numbers scale with the runner, the npm floor (5/s vs 16/s worst, 3.2x) is the tightest bound and rests on a store commit under 32 clients: a 4-vCPU hosted runner with slow disk could be near it and nothing was run on one (stated in the ledger). `rss_kib()` returns 0 off Linux, which makes the RSS bound vacuous there (Linux only in CI).
**L3. Doc sentence duplicated.** docs/usage.md (new paragraph): "A client may reuse packages already in its own cache without contacting Probation." appears twice in a row.

Also `registry_line` calls `effective_scope` twice (second call with `Some(Private)`) to detect the rule that decided; clear enough, but it is an inference about internals, so a future change to `effective_scope` (for example Private beating a fixed source) would turn the label wrong silently.
