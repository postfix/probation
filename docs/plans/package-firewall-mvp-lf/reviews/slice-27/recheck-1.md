# Slice 27 recheck 1 (security lens, product-code delta after fix rounds 1 to 3)

Read-only review at 182f7f3 plus the uncommitted tree. Nothing was built or run (no E2E, compose or bench); every statement below comes from reading the code and the evidence file. Not executed: `cargo test --test service_metadata_share`.

## Outcome: NOT PASS (1 blocking finding, F1; 1 finding that needs an owner decision, F2)

## Blocking

### F1 (Medium, blocking) The shared project cell is bounded by count only, never by bytes, and never expires entries
src/service_share.rs:14-35 (`MAX = 256`, `put`, `get`).
- `get` ignores an expired cell but nothing removes it. `put` clears the table only when it holds 256 cells. An expired document stays in memory until the table fills or the same key is overwritten.
- The unit is a whole `CachedProject`: the raw upstream payload (`Arc<[u8]>`), `first_seen`, `pins`. The per-document cap is `max_metadata_bytes`, whose shipped default is 64 MiB (docs/plans/package-firewall-mvp/03-program-design.md:377). The bound is therefore 256 x 64 MiB = 16 GiB in theory. With real large npm and PyPI documents (several to tens of MiB) it is a few GiB in practice.
- Failure scenario: in shared-service mode any admitted peer can send credential-free GETs for 256 distinct large public packages (names are public). Every request passes, none needs a credential, and the cells stay for the life of the process (the cell never expires unless the table fills). The service holds several GiB and is OOM-killed, or the node is starved. The old service-mode path kept nothing: this memory is new in this slice.
- Fix (small): count bytes with `CachedProject::approximate_bytes()` (src/store/cache.rs:212) against a byte budget (for example 64 MiB total), drop expired cells in `put`, and refuse to share a document above a per-cell size. Add a test that fills the cell with large documents and asserts the byte bound.

## Needs an owner decision

### F2 (Medium, accepted by the evidence, not yet accepted by the owner) Credential-free reads, including ARTIFACT requests, now trust upstream state up to 5 s old
src/npm/mod.rs:246-259, src/pypi/mod.rs:232-245; artifact path src/artifacts/mod.rs:247-250 and src/http/registry_routes.rs:362 (both reach `current_project`).
- C1028 and SPEC section 9 say every artifact request confirms its reference against a sufficiently fresh upstream snapshot, and "a removed reference is unavailable even if its bytes remain cached". For a credential-free read the share now answers that question. An upstream takedown or yank (the malware case) stays advertised and downloadable for up to 5 s per hot project. The evidence lists this under "Spec changes needed" item (a), so it is declared. It is a security-relevant relaxation, so the owner should state "this relaxes C1028 for credential-free reads" explicitly (rule: no silent weakening).
- The cached `pins` and `digest_generation` are also frozen for 5 s. A digest this instance pinned in the last 5 s (a first download) and then blocked is not seen by the listing until the cell expires. Cooldown and first-seen: the dating uses upstream publish times against the current `now`, so a stale document cannot release a version earlier than a fresh one, except if upstream rewrites a publish time inside 5 s (npm does not allow it). Verified: no path found where a stale document releases something a fresh one holds, other than the removed/pinned cases above. Policy is judged per request on the shared document (resolve, src/npm/mod.rs:463-504), so a publication governs the next read (tests/service_metadata_share.rs:120-135 shows it).
- The two changed tests (tests/managed_delivery_authority.rs:~515-522, tests/shared_service.rs:~431-477) now advance the test clock 10 s so the artifact request leaves the share and revalidates. They still test what they were written for (the race window while an upstream revalidation is held, and the generation refusal after it). They no longer cover "an artifact request revalidates upstream" for a credential-free caller, and no test covers the opposite: nothing asserts that a credential-bearing artifact request inside the 5 s window still goes upstream (tests/service_metadata_share.rs checks metadata GETs only), nor that a credential-free artifact request inside the window is the accepted stale case. Add both, so the contract is pinned either way.

## Findings that do not block

### F3 (Low) PyPI decides "credentialed" from the request classification only
src/pypi/mod.rs:232 `shareable = cache_token(app).is_some()`. npm also tests `read_authorization.is_none()` (src/npm/mod.rs:249). PyPI never looks at `principal.registry_read_authorization`. Today this is safe: `cache_token` is None for any GET or HEAD carrying `Authorization`, a cookie or an unlisted query key (classify_read is an allow-list, src/http/credential_read.rs:100-121; the allow-list covers userinfo, repeated headers and pseudo-headers), and no non-GET route reaches the PyPI `current_project` (grep of callers). `record_request_scoped` is only called for GET or HEAD (src/http/service_registry.rs:48-72), so a future non-GET PyPI route that reads a project with an `Authorization` header would fill and read the share. Add `&& principal.is_none_or(|p| p.registry_read_authorization.is_none())` for symmetry.

Checked and sound:
- Key (family, registry id, selected origin, normalised name): complete for the data the cell holds (the fetched project). The origin comes from the principal (npm and PyPI), so a registry whose target a publication moved is not answered from the old origin (tests/service_metadata_share.rs:146-175). Registry ids are unique, so two tenants can only meet on one registry id, which is the intended sharing. The stored per-registry read credential (`read_authorization_enc`) is not delivered to the service (src/managed/service_policy.rs:508 sets `registry_read_authorization: None`); in service mode a read credential is only what the client sends, so a registry that needs its credential cannot fill the cell (the credential-free fetch fails upstream and `put` runs only after `Ok`). Names: PackageName and ProjectName are normalised before the key.
- Errors are never cached (`put` only after a successful `refresh`; `Missing` writes no absent mark in service mode, src/npm/mod.rs:767).
- Cancellation: a dropped fetch never reaches `put`; there is no waiter state to poison. A poisoned mutex disables the share (get returns None, put is skipped), which fails safe.
- Time: the stamp is the request's start `monotonic`, taken before the fetch, so a cell lives at most 5 s from the request start. A slow older request can overwrite a newer cell with an older document, but its age is still under 5 s of its own stamp.
- mTLS/cookies/query tokens: service mode has no mTLS admission for reads; cookies and non-allow-listed query keys make the read request-scoped.

### F4 (Low) No single-flight on the first fetch
Concurrent first reads of one project each fetch upstream and each commit (`commit_request_references_in`); the share helps only after the first put. No hang or poisoning, but the doc comment "a burst costs one upstream fetch" is true only for a burst that starts after the first completes. A cold burst on a hot package is N fetches of up to `max_metadata_bytes` each at once (memory, not only requests).

### F5 (Low) Audit rows `registry.*`: pre-image is not locked
crates/probation-server/src/portal/registries.rs:~175-190 and the setters. `registry_state` (before) is a plain SELECT in a READ COMMITTED transaction, followed by the UPDATE. Two admins editing one registry at once can produce an audit `before` that is not the row the UPDATE replaced. Use `SELECT ... FOR UPDATE` in `registry_state` for the "before" read. Checked and sound: the row is written in the same transaction (a failed audit insert rolls the change back, and an early `Ok(false)` drops the transaction, so a not-found writes nothing); the actor comes from `admin_on`, org comes from the path and every query filters by `org_id`; the content holds only name, ecosystem, target_url (the Add form rejects userinfo, query and fragment), flags, scope, origins, prefix and the boolean `read_credential_configured`, never the sealed credential. The form select is rendered from `Ecosystem::ALL` (9 tags, the same nine the `add` handler accepts); Askama `ext = "html"` escapes the values. The privacy warning text is static.

### F6 (Low) The hot-path bench and rated-load snapshot switch OSV off
tests/common/transport_load.rs:45 `osv: Some(OsvSetting::Off)` for all nine registries. The transport figures therefore exclude the OSV batch and its cost (and cannot show the +23 ms outage cost). Fine for a transport floor, but the doc comment at the top should say OSV is excluded, and docs/operations.md section 10 should not cite those figures as end-to-end. By contrast the two benches changed here (benches/artifact_throughput.rs:271, benches/warm_metadata.rs:244) use the real OSV client against a reachable mock that answers "no match" (`osv_flagging(&[])` + `start_with_upstream_and_osv`), so the client, the batch window and the negative cache are the product's. They do hide the outage cost, openly and with the number in the comment; the operator doc must keep the +23 ms and 14 to 36 percent figures (the evidence says it does). The warm_metadata assertion now allows `passes = elapsed / INTERVAL + 2` database commands: a request that writes once per request would still exceed it.

### F7 (Low) E2E harness changes that can hide a product failure
- tests/e2e/harness/stack.mjs `up()` retries (3 attempts) on a regex that includes `ECONNREFUSED`, `socket hang up`, `ECONNRESET`, `pool timed out` and `cannot connect with PROBATION_SERVER_DATABASE_URL`, not only IPAM or route errors. A product that intermittently fails to start (portal not listening, pool exhaustion at boot) would be retried and pass. The retry goes to stderr only. Record the attempt count in the run result and fail CI when an attempt other than an IPAM or route failure was retried.
- tests/e2e/harness/net.mjs:69-79 resends once on a reused keep-alive socket for any method. "Never read" does not prove the server did not process a POST or DELETE before the connection died. A product that drops idle connections early, or a crash after processing, is invisible and a duplicate side effect is possible. Limit the resend to idempotent methods or log it as a counted event the scenario can assert on.
- stack.mjs `purgeStaleDns` (about line 340): safe for networks the same engine lists, and a file younger than 120 s is skipped. The mtime test is not a liveness test: the aardvark file's mtime is the last container add or remove on that network, so a live stack older than 2 minutes is protected only by `network ls`. Another podman root, `--network-config-dir` or storage of the same user shares `$XDG_RUNTIME_DIR/containers/networks/aardvark-dns` but is not in this session's `network ls`; its live stack's file would be deleted and its DNS lost at the next aardvark reload. Not reachable on a single-session host (the one used here) but possible on a shared developer host. Skip the purge unless a lock or the project prefix says the file is this harness's (for example only `probation-e2e*` and `probation-f27*`-style names).
- tests/e2e/scenarios/publishing-certificate-scale.mjs:77-79: first refusals are retried once for any non-200 status, and the first-refusal ceiling is `max(3, limit / 100)`, that is 100 of 10,000. The measured rate in the comment is about 1 in 1,400 (about 7 of 10,000), so the ceiling is about 14 times the measurement; a regression to a 0.9 percent refusal rate passes. Use roughly `max(3, limit / 500)` (20) and retry only on 401, so a 5xx fails at once. The pace calibration lets the probe run at the slowest of 20 to 320 ms and asserts only "at least 3 identities per second" (line ~118): a product that became 16 times slower still passes, the pace is only logged. State that floor as the SPEC bound or fail above the pace the plan promised.
- publishing-npm-actions.mjs login-rate probe: the repeat (at most 3, 65 s apart) is justified (a probe longer than 45 s does not fit one 60 s window) and the final assertion requires `ms <= 45000` and the exact 117 x 200 then 429, so it fails closed. No weakening. publishing-npm-read.mjs now compares the client-side `ms` (stricter than the earlier exec-inclusive time) and prints both. publishing-full-matrix.mjs: `E2E_MATRIX_ONLY` is reported by the final witness check, so an accidentally set variable fails the run, not passes it.
- issuer.mjs: `respond` is async with at most 4 openssl children; `this.statusMode` is read again after the `await` (`bad-signature`), so a control call that changes the mode while an answer is being signed gives an answer under the new mode. Fixture only; capture `const mode = this.statusMode` at entry.
