## Findings

**M1 (Medium, security) Any later `systemctl restart|reload nftables` removes both tables and nothing puts them back.**
`probation-node-firewall.service:7` (`After=nftables.service` only), `:16-17`. The unit orders itself after `nftables.service` at boot, but is not `PartOf=`, `ReloadPropagatedFrom=` or `BindsTo=` it and has no re-assert path. Debian's `/etc/nftables.conf` starts with `flush ruleset`. Reproduced in the namespace: after the install the unapproved source is CLOSED; after `nft flush ruleset` (what a restart or reload of `nftables.service` does) `nft list tables` shows 0 tables and the same unapproved source is OPEN. Scenario: an operator applies a change to `/etc/nftables.conf` and reloads the service; the node egress rule (the "no upstream fallback" and the NodePort backstop) is silently gone until the next boot, and `verify-node.sh --firewall` is not run by anything periodic. Also `ExecStop=` lacks the `-` prefix, so stopping the unit after such a flush fails ("failed" state). Fix: add `PartOf=nftables.service` (stop/restart propagation) plus `ExecStop=-...` so the restart re-runs the loads, and document that a reload of `nftables.service` needs `systemctl restart probation-node-firewall` (or `ReloadPropagatedFrom=nftables.service` with an `ExecReload`); state it in operations.md (the sentence at 2118 covers only the boot).

**M2 (Medium, security claim) `verify-node.sh` proves the drop-in FILE, not the environment of the running containerd.**
`verify-node.sh:140-148`. It greps its own `probation-ca.conf` and the empty directory. Reproduced: with a second drop-in `zz-corp.conf` (`Environment="SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt"`, the usual corporate-CA drop-in; systemd applies drop-ins in file-name order and the last assignment of a variable wins) the verifier still prints `verify-node: ok`. The same blind spot: containerd not restarted after install, not run by `containerd.service` (k3s, RKE2, a custom unit), or an `EnvironmentFile`. This is the second half of the original F1 complaint (the verifier green while the pin is off). `--prove-pin` does not help: it runs `ctr` with the variables taken from the arguments (`verify-node.sh:166-168`), so it proves Go's behaviour, not the daemon's environment (with the drop-in's `SSL_CERT_DIR` line deleted, `--prove-pin` still passed and only the text check failed; reproduced). Fix: add a check of the effective values, `systemctl show containerd -p Environment` (requires both values, last assignment wins) and, when the daemon runs, `tr '\0' '\n' < /proc/$(systemctl show -p MainPID --value containerd)/environ`.

**M3 (Medium, lane) `run-kind-lane.sh` cannot pass as authored; two of its checks are vacuous.** All of these fail closed (red) except where noted; none can go green falsely on its own. The cluster lane has never run, so none of this was observable by the author.
- `run-kind-lane.sh:199` "D1 restored: the outsider is refused by the service again" runs `refused_by_service` (needs the body `NETWORK_NOT_ALLOWED`) right after `kubectl apply -k` at `:196`, which re-creates `probation-ingress`. With the policy back in force an enforcing CNI drops the outsider (timeout, empty body): the assertion is red, and it contradicts the lane's own phase B and the doc ("restore the policy afterwards"). Use `dropped_or_refused` there, or check the object is back and the body only with the policy lifted.
- `:194` the negative control assumes kube-proxy's Cluster-mode SNAT puts the approved node's INTERNAL address (IP2) as the source. With Calico's tunnel encapsulation the masquerade source is the node's tunnel interface address (`tunl0`/`vxlan.calico`, a pod-CIDR address), which is not in `allowed_peer_cidrs`: the control stays red. Unverified either way; the doc (`operations.md:2106`) states the SNAT address as fact.
- `:204-212` the RWOP step applies a `second` pod with no `securityContext` into the `probation` namespace, which enforces `restricted`: it is rejected at admission, no event ever exists, and the 120 s loop exits 1. And if it were admitted, the regex also accepts `FailedScheduling` for any reason, so a taint mismatch (the pod does not tolerate the pool taint) would satisfy it: the check cannot discriminate RWOP. Use a restricted-compliant pod that tolerates the taint and select the RWOP message only.
- `:225-232` the fence check is vacuous: the Deployment's `nodeSelector` admits only the pool node (worker 1), which `docker network disconnect` makes NotReady/unreachable-tainted; the replacement is Pending for that reason alone, whatever the claim does. It cannot show the RWOP fence. Add a second schedulable pool node (a second labelled worker) or accept that this lane does not test the fence.
- `:105-111` `csi-driver-host-path` deploys its plugin as a single-replica StatefulSet on an untainted node; its volumes are node-local to that node, while the pod is pinned to the tainted pool node: the claim will likely bind to a volume the pod cannot use and `rollout status` times out. Unverified.
- `cri` lane `:90` `! crictl images -q | grep -q .` asserts the node has NO image; a kind node is created with the control-plane images (kube-apiserver, etcd, coredns, kindnet) preloaded, so it is red. It should assert that the control image (`registry.k8s.io/pause:3.10`) is not listed. The two `until docker exec ... crictl info` loops (`:75`, `:87`) have no bound except the job timeout.
Severity: Medium because the evidence calls the lanes AUTHORED/NOT RUN and no check can turn green wrongly; but with `pull_request` path filters (`cluster.yml:13-22`) the `kind` and `cri-node` jobs will be red on every PR touching `deploy/kubernetes/**` until fixed.

**M4 (Medium, correctness of a security claim) Several-registries `ns` selection takes the FIRST match.**
`src/http/service_registry.rs:182-186` (`registries.find(...)`). The old behaviour for several registries was `NotFound` (ambiguity is not a guess); with `ns`, two OCI registries whose `target_url` has the same host (different path prefixes, or two default Docker Hub entries with `target_url = None`) both contain the `ns`, and the first in policy order silently serves it. `oci_hosts` compares host (and port) only, never the path. Whether the policy server can hold two registries of the same host was not found to be refused (no uniqueness check located). Scenario: `ghcr.io/org-a` and `ghcr.io/org-b` are two registries with different rules/credentials; a pull through the `_default` route (`ns=ghcr.io`) is judged under whichever is listed first. Fix: when more than one registry matches the `ns`, return `NotFound` (as `only_registry` does), and add a test.
