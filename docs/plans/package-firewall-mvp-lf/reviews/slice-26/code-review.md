### H2. `_default` + `server` serves exactly ONE registry, and the service ignores `?ns=`: other registries are mis-served or fail (parity gap)
- src/http/oci_routes.rs:247-249 ("`ns` ... is checked for its shape and read for nothing else"), operations.md:1938-1940 (unprefixed `/v2/` is served only "when its snapshot names exactly one OCI registry"; otherwise `/registry/oci/{registry}/v2/`), install-node.sh:33 (endpoint regex forbids a path) and verify-node.sh:46-47 (rejects `override_path` and per-registry servers other than the endpoint).
- Failure scenario A (several OCI registries): the org has Docker Hub and GHCR. `/v2/` is not served; every pull through `_default` is a 404. The only repair is a per-registry `certs.d/ghcr.io/hosts.toml` with `server = https://endpoint/registry/oci/2`, which install-node.sh cannot write and verify-node.sh reports as FAIL ("overrides the endpoint"), so the guide's own acceptance test rejects the one working layout.
- Failure scenario B (exactly one OCI registry, Docker Hub): `registry.k8s.io/pause`, `quay.io/cilium/...`, `ghcr.io/org/app` all go to `/v2/` and are looked up in Docker Hub under the same path. Kubelet, CNI and system images break (404 or a different image of the same path name: a registry-confusion hazard, an attacker who owns `org/app` on Docker Hub is served to nodes that asked GHCR).
- The evidence's e2e (service-cluster.mjs) only ever pulls `docker.io/team/...`. Operations.md:2097 says the service becomes "the only server of every registry", which is true only of the transport, not of the content.
- Full parity (no backlog) requires: installer takes a registry-to-route map and writes one `certs.d/<registry>/hosts.toml` per registry (`server` = `endpoint/registry/oci/<id>`, `capabilities`, `ca`; `override_path` only if the route needs it), keeps `_default` as a fail-closed sink (or documents that unmapped registries fail); verifier checks each per-registry file names the endpoint path; the service answers a `ns` it does not serve with an error instead of ignoring it; e2e pulls from two registries, one unmapped (must fail, no origin connection), and one with a same-path repository on the other registry (must not cross).

### H3. D1 is configured, not closed; the guide's "verify D1" commands cannot show it
- Row 26 acceptance (04 row 26, 03 D1/T1/T8): "a pod on an unapproved node and an external host hitting a NodePort refused". No such test ran: Lanes 12, 14, 15 are AUTHORED-NOT-EXECUTED in the evidence and honestly so. cluster_peer.rs proves only the service's half (a forwarder on an approved address IS admitted, the same host direct is refused). service.yaml:14 `externalTrafficPolicy: Local` is a setting; whether kube-proxy/Cilium keeps the source is the open fact. Do not mark D1 closed (00-status, 03 D1 row, CHANGELOG wording) until a cluster lane passes.
- operations.md:2087-2090 (the "verify D1" block): `curl --cacert ca.pem ... https://<service-pool-node>:30443/v2/` and "both must be refused with `403 NETWORK_NOT_ALLOWED`". The certificate names the endpoint DNS name (operations.md:2074), so a request to a node address fails TLS verification and curl prints `000`; and a request with Host = node address is refused by the Host check even from an approved node. Failure scenario: an operator with `externalTrafficPolicy: Cluster` (D1 broken) runs the command from an external host, gets `000` or a Host-check 403, and believes D1 holds. The command prints only the status code, not the `NETWORK_NOT_ALLOWED` body that distinguishes the two refusals.
- Fix: `curl --resolve <endpoint-name>:30443:<node-ip> --cacert ca.pem -s https://<endpoint-name>:30443/v2/` and require the body `NETWORK_NOT_ALLOWED` for the unapproved sources and `200|401` for an approved one; add the negative control (flip to `Cluster`, the external host must then be admitted) so the check is shown to discriminate.
- Other D1 conditions the guide does not state (operations.md:2074, 2084-2093): (a) an operator-owned L4 balancer that SNATs shows the balancer address to the service: either every node is refused or, if the balancer is listed, every host is admitted; the guide only says "health-check"; require source preservation (DSR / client-IP preservation) explicitly; (b) the source address the service sees is the kernel's route-chosen source, not the Node's registered InternalIP: multi-homed or secondary-address nodes must list the address they connect from; (c) dual-stack: the Service is `SingleStack` (service.yaml:16) and all ipBlocks are IPv4; an IPv6 node address is neither admitted nor policy-allowed, silently.

### M8. Node scripts: IPv6 endpoint, egress rule, check weaknesses
- install-node.sh:33 accepts a bracketed IPv6 endpoint; verify-node.sh:36 `host=${host%%:*}` turns `[2001:db8::1]:30443` into `[2001`, so `--online` fails on `getent` for a valid install; egress.nft:25 opens the endpoint port only for `service4` (no `service6`), so an IPv6 endpoint is reset by the final rule unless inside `cluster6`. Either drop IPv6 from the accepted regex or implement it both places.
- verify-node.sh:83 `--check-egress` treats any curl failure (DNS failure, proxy variables, timeout) as "origin unreachable": it can pass for the wrong reason. Use `curl --noproxy '*' -sS` and accept only a connection-level refusal/reset (exit 7/35/56) as proof; check the resolved address, not just the exit code.
- egress.nft: loopback, established/related, the endpoint port on the pool addresses, cluster ranges and an extra set are accepted; every other new outbound TCP (v4 and v6) is reset; UDP and ICMP are untouched (stated in the file). Idempotent (`table ...` then `delete table` then create) and `nft -c` clean. Accepting all of 10/8, 172.16/12, 192.168/16 on every port means a private-network registry origin stays reachable by the runtime (hosts.toml has no fallback to it, but the egress layer does not close it); documented as the operator's `define`. No persistence unit is shipped (the guide says "keep it in the node's boot configuration"); host-network pods are filtered by it (output hook), so cloud controllers need `extra4`.
- No rollback or uninstall path for install-node.sh (only overwrite and a refusal of a foreign hosts file; `mv -f` of the drop-in is atomic).

## No-upstream-fallback property (containerd), as asked

- `server` set with no `[host]` entry: containerd's host list is `[server]`; the implicit origin host is only added when the last entry has an empty host, which a `server` entry never is (that is also the `docker.io` case). The evidence's recording proxy (containerd-node.mjs `recordingProxy`: refuses and counts any CONNECT that is not the service) plus the control layout without `server` that DOES reach the origin (service-cluster.mjs step 6) is a sound demonstration for the `ctr` resolver of the pinned 2.2.0. Not demonstrated: the CRI/kubelet path (Lane 13), which uses the same `_default` host-dir resolution but also image-credential handling (M5) and `registry.configs`, and the per-registry routing of H2. `config_path` single directory plus the verifier's `containerd config dump` read (verify-node.sh:70-73) is the right check and closes the `/etc/docker/certs.d` second-directory route.
- Pause/service-down: paused container gives a hang, the scenario asserts failure "by itself and not by the timer" (service-cluster.mjs step 5); a refused connection (service process gone, port closed) is not run but the single-host list gives the same outcome.
