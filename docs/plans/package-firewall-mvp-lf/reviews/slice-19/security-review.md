## Findings

### F1  Medium  confirmed (mechanism), src/go_modules/serve.rs `parse_info`, `Known::publication`, `record`
Attacker: the author or a compromised maintainer of a Go module (the threat the freeze exists for). Value path: the cooldown date of a Go version is the `Time` field of `.info` (serve.rs:187-202, header comment "a version's real publication time is the Time of its own .info"). For a VCS-backed module the proxy fills `Time` with the commit time of the tagged revision (and a pseudo-version embeds the commit time in its own name). Both are chosen by the publisher: `GIT_COMMITTER_DATE=2020-01-01 git commit ...; git tag v1.0.9`, or tagging an old commit. Ineffective defense: the firewall accepts that date as "upstream publication time", merges it with `max` only against its own earlier observations, and uses first-seen only when `Time` is absent or zero. Effect: a brand-new malicious version carrying an old `Time` is listed, served by `@latest` and downloaded with no hold; the freeze (and the "young version" tests, which use fake `Time` values) never applies. Evidence: source trace; the fixtures publish `ageSeconds` directly in `Time`, so no test models a back-dated commit. Not a Go-proxy bug: the proxy protocol has no publication-time field. `go.sum`/sumdb do not help (the sumdb records whatever the first fetch saw).
Smallest correction (needs a user decision, since it changes freeze semantics for Go; keep every feature): date = max(upstream `Time`, firewall first-seen) for any version that was NOT already in the first list the firewall observed for that module (a per-module baseline), so a version that appears later is always held for one cooldown from the day the firewall first saw it, while versions already present when the module was first seen keep their upstream dates. Cost: one baseline marker per module (a reference-row flag or a project row), and a new module is trusted on its dates at first sight (stated limit). Pseudo-versions requested directly have no list: apply first-seen the same way (hold from first `.info` request when `Time` is younger than first_seen - cooldown is not provable). Closure checks: unauthorized: a version appearing in a second list with `Time` 300 days old is still HELD (403) until first_seen + freeze; legitimate: versions present in the first list and old stay allowed; a module first seen with only old versions lists normally.

### F2  Low  confirmed (source), src/upstream/reqwest_transport.rs `open_artifact` (credentialed branch), src/upstream/origins.rs `admit_any`
Prerequisite: a selected (private) Go registry that answers a credentialed zip request with a 3xx (hostile or compromised private registry; its admin is trusted by the org, so this is hardening). The non-credentialed client refuses every cross-origin hop except the declared archive origin (`same_origin_policy`). The credentialed branch follows redirects by hand and checks each hop with `admitted()` = `admit_any`, which accepts a URL belonging to ANY origin of the set. A selected set is `OriginSet::production()` with the npm slot replaced, so `proxy.golang.org`, `sum.golang.org`, `registry.npmjs.org`, rubygems, crates hosts stay in the set. Effect: the private registry can redirect the zip to `https://proxy.golang.org/<same module path>/@v/<v>.zip` and the firewall stores and serves public bytes under the private module identity (dependency confusion at transport level) and the "redirect away is refused (502) unless declared" statement in evidence/slice-19.md is false for credentialed reads. The credential is not forwarded (taken on the first request). Same shape already exists for the other families (pre-existing), Go does not widen it except for sumdb/proxy hosts. Not covered by tests (origin_guard Go cases drive the non-credentialed policy only).
Smallest correction: in the manual loop admit the hop only if `origins.admit(&next, kind_of(&url))` succeeds or `origins.admits_archive_redirect(kind_of(&url), &next)`. Cost: one condition. Closure: credentialed Go zip whose upstream redirects to a production host is `RejectedRedirect`; credentialed redirect to the declared archive origin still works and carries no Authorization.

### F3  Low  plausible, availability, SPEC §9 pin applied to `.info` (decision 2 of evidence/slice-19.md)
`.info` is pinned on first verified download and a later different body is a 502 integrity failure; pins feed `pinned_digests` of the candidate, so a pin conflict hides the version. `go.sum` only covers `.mod` and `.zip`; the `.info` body is not content-addressed (`Origin` metadata and key order can change when a proxy re-resolves; Athens/Artifactory re-render it). Effect: a benign `.info` drift permanently refuses or hides a version whose zip is immutable and verified. Check needed: observe whether proxy.golang.org ever returns two byte-different `.info` for one version (the evidence only sampled once). Correction option: pin `.mod` and `.zip` only (cost: `.info` TOFU protection dropped; it protects nothing the client verifies). This removes a protection, so it needs the user's explicit "this removes X" before any change.

### F4  Low  confirmed (availability), src/go_modules/serve.rs:508-551 `judged_list`
`cell.list_gate` is held across up to 64 `.info` calls (8 parallel, each up to the 30 s metadata timeout, so up to about 4 minutes), and every waiter holds an `active_permit` (try-acquire; none free is an immediate 503 `Overloaded`). An attacker with any read access sends N lists of one slow or unseen module (a cold module on proxy.golang.org can take many seconds to resolve): all but the first block on the gate while holding permits, so `max_active_requests` (1024 by default; a smaller number in a constrained deployment) is consumed by one module's list and unrelated requests get 503. Credential-bearing reads skip the gate (each makes its own 64 calls: the amplification is then 64 upstream calls per request with no coalescing, bounded only by the permit count).
Correction: acquire the gate with a timeout (or try-lock and serve from the table, withholding undated versions) so a waiter returns quickly instead of pinning a permit. Cost: small. Closure: 1024 concurrent lists of one module against a 10 s upstream leave permits available for another module's `.info`.

### F5  Low (hardening)  confirmed, src/go_modules/serve.rs:133 `cell_for`
A poisoned `app.go.docs` mutex returns `InternalFailure` (503) for every later Go request in the process, while every other lock in the file uses the poison-tolerant `lock()` helper. A single panic while the map is held (none seen) is a permanent Go outage until restart. Correction: use `lock()`. Cost: none.

### Hardening notes (no finding)
- `judged_list` builds 3 URLs and 3 hashes for up to 6,666 versions per list request and evaluates every dated version through OSV on every list; a long module costs CPU per request (bounded by the list cap). Each distinct valid version or pseudo-version requested creates three reference rows (identity only), so a read-access attacker can grow the table with real commit hashes; same class as other families.
- A selected registry's archive origin may be a bare origin (`https://host/`), which admits any path of that host as redirect target; the registry admin chooses it (activation applies the LS-F9 denylist and shape rules).

## Intermittent 503 on a cold stack (not proven; ranked by Go-specific likelihood)
No log of the failing run exists, so none is confirmed. Reading the code, a 503 in the Go path can come from only these `ApiError`s: `Overloaded`, `PolicyUnavailable`, `NotReady`, `LookupBusy`, `StorageUnusable`, `CapacityExhausted`, `InternalFailure`.
1. Download permit exhaustion (`Limits::download_permit`: try, then wait at most `download_wait_seconds`=5 in one of 64 places, else 503). Go turns one `go get` into many tiny transfers (`.info` and `.mod` of every version, each through the artifact pipeline, plus the 20+ MB zips holding permits). Under a loaded host the 5 s wait expires first. Most likely for a `.info` on a cold stack.
2. `selected()` re-check after the response (go_routes.rs:127-136): any change of the principal's policy fingerprint, trust flag, origin, CIDRs, archive origin or read authorization between admit and re-check turns an already-computed answer into `PolicyUnavailable` 503. E2E-go changes platform and org policy and waits only for the list to show the freeze, so a snapshot refresh arriving mid-request on a cold stack hits exactly this branch (any family has it; Go's scenario edits policy right before the first `.info`).
3. `StoreError::Busy` (critical store queue full) from `record`'s 64 sequential `get_reference` calls plus the commit, when the writer is slow under host load.
4. `managed.ready()` / key lookup `LookupBusy` before the first sync (E2E waits on the list first, so less likely) and `StorageUnusable` when the store health flag flips under load.
5. F4 permit pinning (needs concurrent lists; E2E-go does not make them) and F5 poison (needs a panic): unlikely.
Deciding checks (not run, needs the stack): rerun E2E-go on a cold stack with the firewall log kept and read the `error_code` of the 503 (`OVERLOADED` vs `POLICY_UNAVAILABLE` vs `NOT_READY` vs `LOOKUP_BUSY`); that one field separates candidates 1/3, 2 and 4.
