## Findings

R5-1 - low - correctness - certificate-managed `legacy` search re-authentication charges the account's rate limit a second time
Location: src/http/conan_routes.rs:126 (`super::admit` -> `managed.authenticate` -> `self.admit` -> `rates.admit`, src/managed/mod.rs:519, 1187); contrast `selected` (:149) which uses `recheck_conan` -> `admit_certificate(..., charge_rate = false)` (src/http/registry_read.rs:182).
Failure: a key with `rate_limit = N/min` pays 2 tokens per search. When the bucket is empty after the search, the second admit answers 429 (`Refusal::RateLimited`) after up to 100 s of judging; the finished answer is discarded (the verdicts stay, so a retry converges, but it must wait for a refill). The same second admit also takes a new active-request permit (the first is already dropped, so no double hold), and can answer 503 `Overloaded` if the process is saturated at that moment. No credential leak (the refusal is the shared 503 with no body of the key), no effect on other routes or ecosystems (only `Parsed::Search | PackageSearch` with `Some(principal)`), same `readmit::refusal()` as `selected` on a fingerprint change; a key revoked mid-search is refused 401, which is the right answer.
Evidence: read; not exercised (the managed test uses no rate limit).
Correction: re-read the principal without charging (an `authenticate` variant or `admit_network` only), as `selected` does. Cost: one small parameter.
Blocking: no (search-only, self-limiting, fails closed).

R5-2 - low - security (availability/staleness) - the "unfinished" mark is per registry and set by any non-complete exit, including cheap early errors
Location: src/conan/serve.rs:1403-1415 (`Attempt::drop`), created at :1522 and :1611 before `locally_blocked`, `origins_for`, `resolve`, `refuse_unless_allowed` can fail; `get_verdict` :1276-1284.
Failure: any caller who can send a search (also a package search for a blocked or unknown recipe, which fails at once with 403/404 and no upstream work) re-arms the registry's mark for 120 s; while it is open every search of that registry (any tenant sharing the verdict key: same registry, origin, policy fingerprint) that reads a verdict renews it, to at most `born + 600 s`. Tenant A can therefore keep tenant B's verdicts up to 10 minutes instead of 2 (an OSV advisory or a cooldown that has just ended shows in a search listing up to 10 minutes late). Bounded and listing-only: a policy/name/version block changes the key or is re-applied at the end of `serve_search` (:1574-1583); files and revision lists are gated live (`refuse_unless_allowed`, artifact pipeline); a verdict never outlives 600 s whatever is done; A's mark does not extend verdicts of a different policy fingerprint or origin; any finished search of the registry clears the mark (`done`). Not an escalation of release, only of listing freshness.
Correction (optional): create `Attempt` after the first upstream fetch (or set `done = true` on a pre-judging error), so only a judging that was cut short arms renewal. Cost: move one line. Document the 10 minute bound as an accepted staleness (already in the VERDICT_TTL comment).
Blocking: no.

## Answers
- R4-1 closed. `Attempt` is a drop guard held across the whole search body: client abort, deadline, any `?` error and unwinding drop it without `done`, which marks the registry for 120 s; completion sets `done` before the final policy re-check, which clears the mark. Renewal never shrinks a verdict and is capped by `born + VERDICT_LIFE`.
- FIX-16-A: policy fingerprint is part of the verdict key (:1498); a policy change shows at once; a block published mid-search is re-applied at the end; credential-bearing reads have no key and keep nothing.
- L2 closed. The removed end-of-search check compared the principal's captured policy with itself (dead). The `legacy` re-admission compares the captured fingerprint with a fresh `admit`, refusal `readmit::refusal()` (GateRefused, re-admitted by the layer up to 3 times under the new layer), the same as `selected`. Only R5-1 is a defect in it.
- Undated listing rule (list_units :891-930): `judge_only` only; an undated revision uses the stored row's first-seen, or now when there is no row (so it is never listed before a list/file request wrote its row and the cooldown has passed); one `list_project_first_seen_in` query per project and only when the list has an undated entry; the same `candidate`/`evaluate_scoped` decision as the artifact pipeline is applied, so a held revision (cooldown, block, OSV) is not listed; pins are excluded in judging and enforced at delivery, as before. An attacker cannot back-date a row (first-seen is the server's clock).
- Slices 17-21: no regression found in this snapshot (download.rs/Maven arms read in recheck-4, unchanged here; managed_mode 21/21 incl. go/maven/conan tests).
