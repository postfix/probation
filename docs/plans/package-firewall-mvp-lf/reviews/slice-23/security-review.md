## Findings

### F1  Medium  confirmed (by source trace; not measured)  src/conan/serve.rs:49, 613-686, 531-538, 658-679, 693-705
Attacker: a depositor or owner of any registry the shared service (or a standalone firewall with a `conan_upstream_url` mirror) reads, or a compromised mirror. Needs only that the upstream answers a `.../revisions` list with up to the document cap (16 MiB, `DOC_FLOOR_CAP`, serve.rs:45) of `{"revision":"a"}` entries, about 500,000 of them (`MAX_ENTRIES`, serve.rs:49), which is the entry bound `read_revisions` enforces. The caller then needs one anonymous request for any reference of that registry.
Path: `list_units` parses the whole list into a `serde_json::Value` (559) outside any fetch place (the places are dropped at 623), then builds, per entry, a `UnitRef` (five Strings), an `ArtifactReference` with a rebuilt URL (635-636), a policy `Candidate` future (693-705) and a `lists` entry holding every unit key (681-685); `record` then does one sequential `get_reference` per item (484-487) and commits up to `row_limit` rows in one transaction under the project's row gate (663-678). `record` clears the unit table when `units.len() + items.len() > MAX_UNITS` (532-535) and then inserts every item anyway (536-538), so the evidence's "16,384 units per cell" is not a bound: one list leaves up to 500,000 `Known` entries in the cell, and the cell table is capped at 128 cells (MAX_CELLS) but not in size. `lists` (4,096 per cell) each keep a `Vec<String>` of all unit keys of their list (30 MB for 500k entries) and nothing ever reads `lists` (only the write at 681 exists), so it is pure memory.
Ineffective defense: row bound (`room`) limits rows, not the in-memory fan-out; per-registry places bound fetches, not parse and allocation; `max_active_requests` bounds requests but each request is up to 16 parallel list parses in a search (F2).
Effect: one request makes the process allocate roughly 0.5 GB transiently (Value tree, 500k UnitRefs and ArtifactReferences) and about 50 MB retained per package name; a few concurrent requests for 128 distinct names retain several GB and 500,000 sequential DB reads and a 500,000-row transaction per request (the 120 s deadline cancels the request but the memory and DB work have been spent). A tenant of the shared service can take down the service for every other tenant. Public ConanCenter lists (about 700 bytes) do not trigger it, so the public registry alone is not exposed.
Smallest correction: refuse a list above a real bound (a recipe with more than a few thousand revisions does not exist; the evidence's 2,100-entry case needs 4,096 at most) with 502 before parsing into units, never insert more than `MAX_UNITS` into the table (truncate instead of clear-then-insert), drop `lists` (unused) or cap its key count, and make the 8 MB-per-document parse bounded by the same constant. Cost: three constants and one test. Closure: unauthorized-action check: an upstream fake answering a 16 MiB list of 500,000 revisions yields 502 with process RSS growth under a few MB and zero rows; legitimate check: `a_large_listing_is_not_refused_before_its_cap_and_dates_cost_no_extra_call` (2,100 revisions) still passes.

### F2  Medium  confirmed (source)  src/conan/serve.rs:617-629, 945-968, 971-1007, 1010-1036, 709-728, 681, 862, 1046
Attacker: any caller that can reach the Conan search route (anonymous on a standalone firewall; on the shared service, anyone who can send an `Authorization: Bearer x` header, because admission checks only the shape, registry_read.rs:194-201).
Path and effects:
(a) One `v2/conans/search?q=...` costs 1 plus up to `JUDGE_CAP` = 512 upstream revision-list fetches (and the same for `revisions/{rrev}/search`), 16 at a time. `list_units` never consults `cell.units` or `cell.lists` to skip a list it has judged (the comment "the next request settles more" is not what the code does; only the 5 s `raw` table helps), so every search request refetches the same first 512 lists, and references 513 and beyond are never judged and so never listed at all (functional, fail closed; see non-security note). The `raw` table holds 32 entries (MAX_RAW) and clears itself when full (721-726), so a 512-list search never hits it.
(b) In service mode any read with `Authorization` is request-scoped (C1028), so the 5 s `raw` memo and the cells are disabled for exactly the requests an attacker can mark that way; the credential is also forwarded to the registry's origin (and for the public registry to center2.conan.io), so each search becomes 513 authenticated calls from the firewall's egress address.
(c) Per-registry fairness is 4 places and 16 process-wide (`REFRESHES_PER_REGISTRY`, `REFRESHES`), FIFO, 30 s wait. A caller holds as many as it has requests; 20 concurrent `search?q=<varied>` keep the 4 places of the registry busy (513 fetches at about 4 in flight is on the order of ten seconds per request) so every metadata request that needs a list (`revisions`, `latest`, first file of an unseen revision, `files`) answers 504 after 30 s. With four registries the 16 global places are exhausted (inherited note from slice 21).
(d) `probe` (862) for a made-up file name of an allowed unit and `serve_auth` (1046, a login or credential check) call upstream outside the places and are bounded only by `max_active_requests`; they have no negative cache, so one request is one upstream call (1:1, low).
Effect: availability of the metadata path of one registry or of the public registry for every client, plus a ban risk for the firewall's egress address at the public remote. Same class as 19 F4, 20 F1 and 21 F1.
Smallest correction: judge a reference from `cell.lists` when its list is younger than a few seconds (the table is already written) and keep judged results for credential-free reads; take a per-caller share of the registry's places (a caller may hold at most 1 of the 4 for searches); lower `JUDGE_CAP` or return the references that are judged and refuse the search with a retry hint once it would pass the cap per caller per minute; raise the `raw` table above 512 lists for one search or key it by search. Cost: one read of an existing table and one counter per owner. Closure: unauthorized-action check: 20 parallel searches with distinct `q` against a slow upstream fake leave `revisions` of the same registry answering inside its normal time and the upstream sees at most the judged lists per TTL; legitimate check: `search_lists_only_references_that_pass`-style cases and `a_narrow_pattern_is_judged_in_full_at_once` still pass.

### F3  Low (Medium when the registry holds exceptions and several publishers)  confirmed (source)  src/conan/serve.rs:406-412, 427-429, 697-703; crates/probation-policy/src/names.rs `canonical_name`
Attacker: a depositor on a hosted Conan registry who can create `name/version@user/channel` references (the typical Artifactory/Nexus repository) and a policy that holds an exception, or a pinned allow, for a name or a name and version.
Path: policy sees only the package name and recipe version (evidence, "Identity"); user and channel are in the row's `filename` but not in any policy key. An exception for `zlib` (or `zlib` 1.3.1), lifting cooldown or OSV for the trusted publisher's `zlib/1.3.1@_/_`, therefore also lifts it for `zlib/1.3.1@attacker/stable`, a different recipe from a different depositor on the same registry. A block is fail closed (it covers every channel), which is the safe direction; the exception direction is the bypass.
Effect: a recipe published a second ago under the trusted name is served at once. Mitigation: exceptions are a human act and the product treats name+version as the identity; but the identity is wider than one recipe on a hosted remote.
Smallest correction: either document that an exception on a Conan name covers every user/channel of it (docs/operations.md Conan section and the portal text), or key the policy name as `name` for `_/_` and `name@user/channel` for the rest, which also makes blocks per channel. Cost: a documented limit, or a key change touching names.rs, the blocklist and the OSV key (the OSV key must stay `name`). Closure: an exception for `zlib` does not release `zlib/1.3.1@attacker/stable`.

### F4  Low  confirmed (source)  src/conan/serve.rs:585-590, 784-791, 1031-1035
Mechanism: the revision list rebuild keeps every string member of the remote's document other than `revisions` (key at most 64 bytes, value at most 1,024) and relays it (`head`), and `revisions/{rrev}/search` relays each package entry "as the remote wrote it" as arbitrary JSON (up to the 16 MiB cap, nested to 128). Neither is an allow-list of the members the client reads (`reference`, `packageReference`; `settings`, `options`, `requires`, `recipe_hash`). The documented property "nothing of the remote's document but its string head and the entries that pass reaches a client" is therefore not "no location of the remote".
Exploit scenario: a hostile or compromised remote (a tenant's hosted registry) adds `"download_urls"`-style string members or an extra string `reference` that points at another recipe; a client that reads a member this review did not enumerate (an old or third-party client, a Conan 2 plugin or a future client) follows it. The reference client 2.21.0 ignores them (not run against such a document here).
Smallest correction: rebuild `reference` and `packageReference` from the parsed identity, drop every other member, and rebuild package-search entries from the four keys the client reads with the string/array shapes it expects. Cost: about 20 lines and one test with a hostile document. Closure: a document with extra members is served without them; the real client's flows (native lane) pass.

### F5  Low  plausible (depends on the registry)  src/conan/serve.rs:851-884, 862
A file's age is the unit's: `reference_for_file` gives every new file of a revision `unit_dated`, and a made-up or later-added name is confirmed by a one-byte probe and then served under the revision's old date. Pins catch a changed existing file, not a file added to an aged revision. Scenario: a depositor with write access (or a registry that allows re-upload of files into an existing revision, which the class W route itself makes possible) adds `conan_sources.tgz` or a package file to a revision that has aged; a client resolving that old revision downloads it immediately. Correction: take the later of the unit's date and the file's own `Last-Modified` when the row is first made (the probe can read it), and log the difference. Same cost and closure as 21 F5. Public ConanCenter is immutable and not affected.

### F6  Low  confirmed (source), documented decision made explicit  src/conan/serve.rs:795-813, 904-927, 818-839
`revisions`, `latest`, `files` and every file of a package revision are judged by the package revision's own time and by the name and version, not by whether its recipe revision passes (`serve_package_search` resolves and refuses on the recipe; the three siblings do not). So under a held recipe revision R the lists `.../revisions/R/packages/P/latest`, `.../revisions` and the files of package revisions that are old enough are served. A client that asks for the recipe first is stopped at R's files, and an old package revision under a young recipe cannot exist on a server that stamps upload time, so the bypass needs a back-dated or depositor-chosen package time (U1) and a client that downloads a binary without the recipe (`conan download` by exact reference still fetches the recipe first). The evidence calls this the contract; the asymmetry with the package search is the weakness. Correction: in `serve_revisions` (Package parent), `serve_files` and `reference_for_file` for a package revision, also `resolve` its recipe revision and `refuse_unless_allowed` on it (one more lookup in a hot table, no more upstream calls). Closure: a package file under a held recipe revision is 403 unfetched; a new binary of an old (allowed) recipe still gets its own age.

### F7  Low (hardening)  confirmed (source)  src/conan/serve.rs:388-391
`expected` is empty, so the first download of each file is pinned unverified. Every recipe and package revision has a `conanmanifest.txt` with the md5 of its files and the remote sends `x-checksum-sha1/sha256`; neither is compared before pinning, so a poisoned mirror cache is pinned permanently. Not exploitable against ConanCenter over TLS.

### U1  Unknown (inherited)  src/conan/serve.rs:264-272, 477-508
`time` is whatever the remote lists. A hosted remote that lets a depositor choose a revision's time back-dates it (the same residual as 19 F1, 21 U1); also `1970-01-01T00:00:01Z` is accepted as a real date (only the epoch itself is "undated"), so the cooldown is skipped for a remote that claims it. Decision for the user: which hosted Conan remotes organisations register, and whether any lets the depositor set `time`.

### U2  Unknown  src/conan/coords.rs:97-103
Name and version are case-sensitive identity (`Zlib` and `zlib` are two policy keys). On a case-insensitive backend (a Conan server on a case-insensitive file system, some Artifactory settings) a block on `zlib` does not cover `Zlib`. Environment dependent, not tested here.

## Verification and limits
- Run (inside `systemd-run --user --scope -q -p TasksMax=512 -p MemoryMax=16G -- timeout 900`, `CARGO_TARGET_DIR` under /home/john/go/src/github.com/postfix/.probation-scratch/s23sec, `--offline -j 8`): `cargo test --test conan_registry` 26 passed, `--test conan_service_read` 8 passed, `--test conan_service_write` 7 passed. Scratch deleted afterwards. Fingerprint of src/conan/*.rs + conan_routes.rs + spool.rs (md5 of md5 list) 8-byte check: identical before and after (unchanged: yes).
- Not run: tests/conan_native.rs, E2E, Postgres suites, probation-policy crate tests, a load or memory measurement of F1 or F2 (source trace only, no hostile upstream was built), dependency advisories, `cargo clippy`.
- No source, test or configuration was modified; only this file was written.
- Non-security observations: (1) search lists the first 512 references of the remote's answer forever (the same 512 are re-judged each request), so a pattern with more than 512 matches (`q=*` on ConanCenter, about 4,000) never lists the rest, contrary to the evidence's "the next request settles more". (2) `lists` in `Cell` is write-only. (3) A `HEAD` of a document route performs the full work.
- Newly identified surfaces absent from the threat model: the string members and package-search values relayed from the remote (F4); package revisions not gated by their recipe revision (F6).

## Next steps
1. F1: bound entries per list (a few thousand), never exceed `MAX_UNITS` in a cell, drop or cap `lists`.
2. F2: use `cell.lists` and the units table to skip refetching judged lists, per-caller share of fetch places, keep a search's lists in the raw memo.
3. F3: decision for the user: exceptions per name (documented) or per reference.
4. F4, F6: rebuild the head and package-search entries from allow-listed members; gate package lists and files by their recipe revision.
5. F5, F7: take the later of the file's own `Last-Modified` and compare first bytes with `conanmanifest.txt`/`x-checksum-*` (optional hardening).
6. User decisions (inherited): U1 which hosted remotes let a depositor set the time; U2 case-insensitive backends.
