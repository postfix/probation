## New findings
R1 - medium - blocking - the upload lane queue holds an active-request permit for up to 10 minutes, with no cap on waiters per owner, and covers requests that carry no big body
Location: src/http/oci_routes.rs `forward_write` (`_permit` from admit_oci, then `serve::upload_lane`), src/oci/serve.rs `upload_lane`, `UPLOAD_QUEUE_WAIT` 600 s.
Scenario A (DoS): one client address (shared service: the registry decides credentials, so a junk `Authorization: Bearer x` passes the firewall's own check) opens uploads. Two stall at the 16 KiB/s floor and hold the owner's two lanes; every further request of that owner waits in `lane.acquire_owned()` for 600 s holding one of `max_active_requests` (default 1024) and its connection. About 1000 connections from one address take the whole front door for 10 minutes, repeatable. Before the fix round the same flood got an immediate 503 from `spool_seat` (4 per owner).
Scenario B (valid push refused): the lane is taken for every request with `has_body` (not GET/DELETE), which includes the empty upload POST, the finishing PUT of a layer and the manifest PUT. A client pushing 3+ multi-GiB layers (docker pushes up to 5 in parallel) has two PATCHes holding both lanes for more than 10 minutes; the next layer's POST, a finished layer's PUT and the final manifest PUT queue behind them and answer 503 after 10 minutes.
Correction: take the lane only for a request whose body can be large (PATCH; PUT/POST with a declared length over a small threshold or undeclared), never for POST-start, empty PUT or manifest PUT (own 8 MiB cap); cap the waiters per owner (lane size + a few, the rest 503 at once) and do not hold the active permit while waiting. Closure: two stalled PATCHes, then POST-start, empty PUT and manifest PUT complete at once; 50 queued uploads of one owner leave active permits free.

R2 - medium - blocking (parity) - token_origin works in a shared service only
Location: src/managed/mod.rs:321 and :372 (the certificate principal sets `registry_token_origin: None`; `CertificateAdmission::Granted` has no such field); src/oci/serve.rs `origins_of` reads the snapshot (service only).

(archive_origin is None on the certificate route too, the same pre-existing pattern from slices 18-23.)
Correction: carry `token_origin` in the certificate admission, or record the limit in "Not done" and get the user's explicit yes (binding parity rule).

R3 - high (process) - blocking - U2: refusing manifests with layer `urls` is a feature loss decided without the user
Location: src/oci/serve.rs `read_children` (403 on any layer with non-empty `urls`); evidence slice-24.md U2 "stated here, not asked".
Rule: pass-product-goal.md: any removal needs the user's explicit "this removes X"; ruling 2026-11-09: build it, never defer. Windows base images that still carry foreign layers (and images built FROM them) are withheld.
Judgement: the client fetches `urls` itself (containerd and containers/image use them directly; I did not verify the order from their sources), the firewall cannot intercept that, and the manifest cannot be rewritten (its digest is its identity and signatures bind it). So "serve foreign layers through the firewall" only works where a client falls back to the registry blob route, which cannot be assumed. A safe full-parity design that can be built: (1) accept the manifest; each `urls` entry must be https, no userinfo, host in an operator/descriptor allow-list (default mcr.microsoft.com, go.microsoft.com, download.microsoft.com), with size and digest present; (2) check EVERY child digest, foreign ones included, against `blocked_anywhere` at manifest time and refuse the manifest if one is blocked (today a block is checked only on a blob request, which a foreign layer never makes); (3) the manifest's cooldown pins every layer digest and the client verifies the digest itself, so integrity holds; what is lost and must be stated: the firewall cannot refuse those bytes later; (4) optionally fetch each allow-listed URL itself (credentials dropped, redirects only to the allow-list, digest verified) and serve it at `/v2/<name>/blobs/<digest>` for clients that use the registry route. Cost: one allow-list and a child block check. Safe to build.
Blocking: yes until the user decides or the design above is built.

## Verified fixed and guarded
- S24-F1: `serve_token` returns `local_token` whenever service mode is off. The token is the constant text `probation-pull-only`: pull scopes only, blocked repositories left out, the registry is never asked. It is NOT unguessable, bound or expiring, and need not be: nothing validates it. Admission on every certificate request is the per-request client certificate (`admit_for` -> `admit_certificate`), the Authorization header is ignored there; the shared-service branch is exclusive (`service_policy().is_some()` is tested first). Routes traced: token (local_token), ping (stored credential makes `caller` Some, 200, no token needed), 401 challenge (firewall realm, no credential), Basic passthrough (ignored in cert mode; in a shared service the Basic is the caller's own and goes only to the registry origin or an allowed realm). A certificate holder gets no stored credential and no registry token by any route I traced; the token is accepted nowhere upstream. Guard a_firewall_that_is_not_a_shared_service_never_mints_or_echoes_a_registry_token (probe Q2); limit: the test calls `serve_token`, not the mTLS route, so the `Parsed::Token` arm of `run` in cert mode is untested (non-blocking).
- (b) places: owner 4 of 8, owner lane half of the process, credential 2, registry 8, global; taken in a fixed order inside one `timeout`; every permit is an owned guard dropped on every exit (timeout, error, cancel); `exchange`, `ping`, `serve_token` never nest `places`. Junk credentials and anonymous share the owner's 4. Two or more owners (two addresses or /64s) can still fill a registry's 8 places: inherent to per-address fairness, as in Conan. Token table 32 per owner with oldest-first eviction: OK.
- (c) undeclared body 2 h: worst case with per-owner caps is 2 lanes = 2 spool seats per owner, bytes reserved as they arrive (about 115 MiB per connection at the 16 KiB/s floor over 2 h), 8 seats in total (shared with every family's uploads): four addresses can hold every seat for 2 h per round. Multi-GiB chunked PATCH was not run with a real body (only the small chunked test and the computed bound).

A memoised HEAD cannot leak a young digest/length to an unauthorised caller. A credentialed HEAD (any Bearer/Basic) to a registry that challenges still learns a young digest/length only if the registry accepts the credential; information only, accepted.
- (f) token_origin: https only, no path/query/userinfo, absolute denylist `check_target`, `selected_npm_with_private` with the registry's own CIDRs, DB check constraint (oci with target only); the realm must equal the declared origin exactly; own-origin and table rules unchanged. A held manifest's descriptor (digest, size, artifactType, annotations bounded) can appear in a referrers list or fallback index: metadata only, low.
