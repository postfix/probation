# Security review
Verdict: CLEAR
Subject and scope: C-S16-1 only (a failed/degraded OSV lookup is no longer cached). Bounded review of src/osv/mod.rs (`check`, `OsvCache::put`, generation counter), src/osv/batcher.rs (`flush`, `run`) and their interaction with src/managed/publication_gate.rs (`authorize_current_policy`, `OsvStamp`) and callers (npm/mod.rs:472, pypi/mod.rs:356, artifacts/mod.rs:162,297, artifacts/download.rs:405). HEAD 6c4b7fc plus dirty slice-16 tree. Design-versus-implementation review of one hunk; not a full audit.
Summary: No property open. Two low observations (S1 load/latency amplification during an OSV outage, accepted by the user; S2 the would-block diagnostic re-queries). No unknowns that affect the verdict.

## Findings
S1, low (conditional medium on a shared server), confirmed by trace, src/osv/mod.rs `check` and src/osv/batcher.rs `run`/`flush`.
Prerequisite: OSV unreachable or slow, or an attacker who can make it so, plus any client able to request the proxy. Path: cache miss -> enqueue -> flush -> failure -> nothing cached -> the next request for the same key does it all again. Before, the 30 s negative entry capped repeat queries at one per key per 30 s. Now each request pays one batch interval (10 ms) plus up to `request_timeout` (shipped 500 ms) and each flush is an outbound call. Bounds still in force: enqueue timeout 50 ms, queue 1024, 256 per batch, one flush per 10 ms interval at most from a single batcher, and keys come from upstream metadata or artifact rows, so a client cannot invent keys (assumption: unknown packages fail upstream before OSV; not traced). `run` has no cap on concurrent flushes (ponytail comment in the code): with a hanging OSV about 50 flushes can be in flight (500 ms / 10 ms), each holding a connection. Impact: extra latency and connection use on the shared server during an OSV outage, and possible OSV rate limiting. Never a wrong verdict, because it fails open as before. The user accepted this cost (C-S16-1; code-review L1).
Smallest mitigation, if wanted (needs a user decision because it conflicts with "nothing is cached without a response"): a global "OSV unreachable until T" flag that is not a per-key verdict, or a semaphore on concurrent flushes. Closure check: with the stub at 500, N requests inside 30 s cause no more than about 100 outbound requests per second, and a legitimate lookup succeeds again once OSV recovers.

S2, low, confirmed, src/artifacts/mod.rs:297 `record_would_block`. It relies on "the answer evaluate just cached". After a failure nothing is cached, so it asks OSV again and may get a late real match; it then records a would-block for an artifact already served. This is a log-only diagnostic and fail-open, so the effect is an extra OSV round trip and an inconsistent diagnostic record. No security impact. The comment on line 278 is now inaccurate for the failure case.
