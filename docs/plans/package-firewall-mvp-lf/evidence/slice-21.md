## Measured against the real registry (Maven Central, 2026-11-19; the fixture shapes follow what was measured)
- A POM, a JAR, a `.sha1` and a `.asc` all carry `Last-Modified` (junit 4.13.2: 2021-02-13, the real release time); `x-checksum-md5` and `x-checksum-sha1` headers are sent too. A metadata document carries one (its last deploy), which is why the version's date is the POM's, never the metadata's.
- Largest real inputs: `maven-metadata.xml` of com.amazonaws:aws-java-sdk-s3 66,454 bytes (4,880 gzip, 13.6:1) for 1,956 versions; the plugin group's metadata (org.apache.maven.plugins) 10,258 bytes; `archetype-catalog.xml` 18,602,965 bytes (439,873 gzip, 42.3:1); a POM 27,018 bytes (junit). Directory listings are HTML and are not part of the protocol (never served).
- The real `mvn` 3.9.16 sends, on a plain read, exactly `accept-encoding`, `cache-control`, `connection`, `host`, `pragma` and `user-agent` (measured with a tap, `mvn_native_client_sends_only_allow_listed_headers`): all common headers, so Maven adds nothing to the allow-list of LS-F4 and has no query keys.

## Behaviour notes (decisions inside the contracts)
- Identity. A Maven coordinate is `groupId:artifactId` as the layout spells it and case is identity (Central is case-sensitive: `Foo` and `foo` are two artifacts); the version is the version directory verbatim. A group is its directories joined by `.` and a group directory never contains a `.` itself, so a group has exactly one path. The policy key, the blocklist, the OSV key, the project name of the reference rows and every upstream URL are rebuilt from the parsed identity; a path that is not exactly one canonical spelling (a file not of the directory's artifact and version, a dot in a group directory, an empty, dot or encoded segment, a query) is a 404 before any upstream call.
- Units and dates. The thing that has a publication time is a unit: a release version, or one snapshot build (`20260101.120000-3`) of a `-SNAPSHOT` version. A unit's date is the `Last-Modified` of its own POM (the anchor), committed on the anchor's row only ever later; a unit whose POM has none, or none that parses, waits on the committed first-seen time (held for a whole cooldown) and is never dated by a cache age, a build time or a directory listing. A file of a unit takes the unit's date on its own row; a made-up file name makes no row (it is confirmed to exist with a one-byte read before one is made, after the unit's decision, so a held unit's files are never probed). A bare jar with no POM exists when the file does and is undated. A snapshot file belongs to the directory version for policy (a block or exception on `1.0-SNAPSHOT` covers every build) and to its build for age.
- Metadata. Artifact level: only the versions that pass are listed, in the repository's order; `latest` and `release` name the newest allowed (the element goes when none is left); `lastUpdated` and every unknown element or comment are untouched. A snapshot directory is listed unless a block names it (its builds are judged one by one). Version level (`-SNAPSHOT`): each distinct build is a unit, the `snapshotVersions` entries of a withheld build are cut, the `snapshot` pointer moves to the newest build that remains, and with none left the answer is the decision of the newest build (403, with the hold's deadline). Plugin group (`{group}/maven-metadata.xml`): plugins whose package a block names are not listed. The document kind is the path's (a `-SNAPSHOT` last directory is version level, anything else is artifact or plugin group) and a document of the wrong kind is a 502 (a snapshot document smuggled into an artifact path would otherwise be passed unfiltered).
- Checksums and signatures. `.md5`, `.sha1`, `.sha256` and `.sha512` of a metadata document or the catalog are computed from what is served (never relayed). A `.asc` (or its checksum) of a metadata document is the repository's own only when nothing was removed (the signed bytes are what is served), else 404: a signature of other bytes would not verify. Checksums and signatures of FILES are files of their version: gated by the version's decision, delivered exactly, and pinned like any other (the first verified download pins it).
- Archetype catalog. Archetypes whose package or version a block names are removed; an entry's own `<repository>` URL is removed (the entry stays), so no URL of another repository reaches a client through this document. The catalog is read one at a time process-wide (18.6 MB on Central) and never cached.
- Writes (class W). Through the shared service only: `PUT` of any layout file, checksum, signature or metadata document and `DELETE`, with the caller's own `Authorization` (never the service key) to the registry's own origin (its `target_url`, path included) or, for the public registry, to `maven_publish_url` (no default: Maven Central has no deploy endpoint, so there the answer is 404). A write without a credential is answered `401` with `WWW-Authenticate: Basic` before anything is read or asked (Maven sends none until challenged), a declared body over twice the artifact cap is 413 before the registry is asked, a path that is not a layout path is 404, and the answer is relayed only with a status a deploy endpoint gives, as `text/plain` with `nosniff`. All through the shared spool (src/http/spool.rs). A standalone or managed firewall has no deploy route (405).
- Authentication is by the installed client's own key, not certificates: a managed firewall on the key route takes the key as the Basic password of a `<server>`; the certificate script says so on stderr and writes no Maven configuration (unit test `maven_setup_points_at_the_key_route`), exactly as Cargo, Go and NuGet.
- No resource path prefix. NuGet's `resource_path_prefix` confines resources a service index names. Maven has no service index: every URL is the registry's `target_url` (repository root, path included) plus the layout path, so the prefix is the target itself and the field has nothing to add. (`archive_origin` does apply, and is migration 0020.)

## LS-F7: the family's inputs and caps
- A metadata document is read to `max(max_metadata_bytes, 16 MiB)` (250 times the largest real one); the archetype catalog to `max(max_metadata_bytes, 128 MiB)` (6.9 times Central's); a POM to 16 MiB; a checksum or signature relayed from the repository 1 MiB. The transport decodes `Content-Encoding: gzip` and counts the decoded bytes against the cap. No valid input is refused before those caps: `a_large_listing_is_not_refused_before_its_cap...` serves a 2,100-version artifact.
- The scanner bounds nesting at 24 and never recurses; entries per document are at most five times `max_references_per_project` (and 500,000); a version, a file name, a path and a segment have byte bounds in coords.rs.
- Dating is bounded before the first call: at most 2,048 POMs per request (above the largest real artifact, 1,956 versions), sixteen at a time, newest first, and never more than the room the project's row bound leaves. A version still undated is withheld (fail closed) and the next request settles more; the dates are committed.
- Bounded tables: 128 artifact cells, 8 shared documents of at most 16 MiB (5 s), 256 gates; refreshes at most 16 in the process and 4 per registry (a wait over 30 s is a 504); a document request has a 120 s deadline; the archetype catalog one at a time; a project holds at most five times `max_references_per_project` reference rows (past it a file of one more unit is a 503 and the files that have rows are still served).

## Not done, limits and decisions
- Old binaries. No prior-release enforcer or server was built. Compatibility is witnessed at the wire level only: `Upstreams.maven` is additive both ways (`maven_reachability_is_additive_in_both_directions`), the `Maven` descriptor tag is the explicit unknown-tag path of LS-F3 for an enforcer that predates it, and `archive_origin` is ignored by an older reader.
- A mirror's `Last-Modified` is the mirror's. Artifactory and Nexus may stamp a proxied file with the time they cached it. That date is later than the truth, so it can only hold a version longer, never release one early; a repository that serves no `Last-Modified` waits on first-seen. A hosted repository stamps the upload time (the publisher cannot choose it).
- Legacy non-unique snapshots (a literal `lib-1.0-SNAPSHOT.jar` redeployed under one name) are pinned on first download like any other file; a redeploy under the same name is refused as changed bytes until its pin is cleared. Maven 3 deploys timestamped builds, which are immutable; the literal name exists only on old repositories.
- A snapshot whose newest build is held and whose older builds the repository's metadata no longer lists has nothing to offer: the version-level metadata is 403 with the hold (an older build is still downloadable by its exact name).
- The plugin group's metadata hides blocked plugins only; a plugin with no allowed version is listed and its version request is refused at the artifact level (judging every plugin of a group would be one listing per plugin).
- The archetype catalog and plugin metadata are filtered by blocks only (their entries name no per-version date, and the files of the version an entry names are gated when asked for).
- Gradle is not listed in the plan: no Gradle scenario was written. Its Maven repository protocol is this one (`maven { url ... }`, `.module` files are gated like any file of a version); its credentials are the same Basic or Bearer.
- Directory listings (Central serves HTML for a directory), `.index/` files and `maven-metadata-{id}.xml` local copies are not served: they are no part of the protocol a client resolves with.
- The client image fetches its two plugins from Maven Central at IMAGE BUILD time (not at test time); the stack itself stays offline. The native lane (tests/maven_native.rs) and E2E need that image and skip loudly without it.
- Conditional requests: a client's `If-None-Match` or `If-Modified-Since` on a metadata document is answered with the full document (always valid); the E2E fake's own ETag handling is the only 304 in the stack.

## Recheck-2 round (reviews/slice-21/recheck-2.md: N1 blocking, N2, N3; the spool designed once for all six forwarders)

The rule (src/http/spool.rs `owner_of`, src/http/limits.rs; docs/operations.md "who a spool share belongs to"): a place and bytes are counted against REAL identities only, never an unvalidated credential alone.

| Mode | Identity counted | Second count |
|---|---|---|
| Certificate / managed | the caller's account (`principal.account`; every principal there has key id 0, which counts nothing) | the presented credential (hash of `Authorization`, `X-NuGet-ApiKey`, cookies, ...) |
| Shared service | the client ADDRESS: the peer, or, when the peer is listed in the new optional `[service_policy] trusted_proxies`, the client the proxy names in `X-Forwarded-For` (the existing `TrustedProxies` reading: rightmost entry that is not a listed proxy; an unreadable entry falls back to the proxy's own address). The header from any other peer is never read | the presented credential |
