## Behaviour notes (decisions inside the contracts)
- Identity. A NuGet id is case-insensitive and every URL of the protocol spells it lower case, so the family has exactly one spelling: the policy key, the blocklist, the OSV key, the project row, the reference rows and every upstream URL carry the lower-cased id; an upper-case id, a version other than the normalised lower-case spelling (`1.0`, `1.0.0.0`, `1.0.0-Beta`), an unknown file name or a query on a read route is a 404 before any upstream call (tests `request_paths_parse_to_one_canonical_identity`, `invalid_spellings_are_404_before_any_upstream_call`). Because there is one spelling there is no spelling-count table (Cargo's four-spelling cap does not apply: nothing multiplies). A block written `Evil.Pkg` or with version `1.0.0.0` matches (`a_blocked_id_or_version_is_refused_before_any_upstream_call_and_the_block_is_case_insensitive`, and the managed key route test). OSV is asked with the lower-cased id and the normalised version: api.osv.dev answers `Newtonsoft.Json` and `newtonsoft.json` with the same advisory (GHSA-5crp-9r3c-p9vr for 12.0.3) and `12.0.3` and `12.0.3.0` alike (canary 2026-11-19), so the lower-cased key is safe.
- Dates. A version's publication time is the `published` of its registration leaf. The unlisted sentinel (1900-01-01), an absent value and an unparseable one are "no date": the version waits on the committed first-seen time (held for a whole cooldown), never dated from a cache age or a build time (`an_unlisted_sentinel_date_and_a_version_registration_does_not_name_wait_on_first_seen`). A version the flat container lists and registration does not yet name is held the same way. Two leaves for one version keep the later date.
- Project. The stored project is the firewall's own compact list (`{id, versions: [{v, p, l, f}]}`), built from the flat container (what can be downloaded, in the registry's order) and registration (dates, `listed`); no upstream document is stored (the persisted state is reference identity, first-seen and pins, as Go). The flat index and registration are fetched together; registration is always read fresh when it is the response (the project is refreshed from the same fetch).
- Four files per version. `.nupkg`, `.nuspec`, `readme` and `icon` are four references judged by the one decision of the version (digest pins and OSV follow the `.nupkg`), so a held version's four files are all refused and none is fetched (`flat_index_withholds_young_versions_and_the_four_files_of_a_young_version_are_all_refused`). The reference bound is four rows per version, so a project is refused above `max_references_per_project / 4` versions (5,000 by default; `a_project_with_more_versions_than_the_reference_bound_is_refused` pins the boundary exactly).
- Service index. Parsed strictly (a JSON object, `version` 3.x, at most 512 resources; a resource with no usable `@id` is skipped). Each resource is used only when it lies on an origin configured for its kind (the public registry: `nuget_upstream_url`, `nuget_search_url`, `nuget_publish_url`; a registry of its own: its own origin, any path, because Azure Artifacts, Artifactory and GitHub Packages name resources under paths unrelated to the index's); the first admitted resource of a family is used, so a registry listing two search hosts uses the configured one. No flat container: 502. A registry added by the public index URL (`https://api.nuget.org/v3/index.json`, how an organisation adds nuget.org) is the public registry (`selected_root`). The served index points every served resource at a route here and advertises nothing else (decision 3 below).
- Registration. Every page is rendered inline: a page the registry links is fetched (only under the registration's own directory, 256 pages at most, four at a time), the leaves that pass kept, `count`, `lower` and `upper` recomputed, a page with nothing left dropped, `@id`, `packageContent`, `registration` and a registry-own `iconUrl` rewritten (catalog `@id`s stay: they are identifiers no restore reads). The registry's semver1-only view is not offered separately: every `RegistrationsBaseUrl` type is served from one SemVer 2 view (decision 3). Pages could instead be re-linked to routes of this firewall; inline is valid protocol and needs no page route (the measured largest linked page is 670 kB).
- Search and autocomplete. Query keys are the protocol's own (`q`, `id`, `skip`, `take`, `prerelease`, `semVerLevel`, `packageType`), a repeated key keeps the first, a value over 256 bytes is dropped, `take` is clamped to 50 (default 20). Each result is judged against its project (bounded: eight at a time), shown with its allowed versions only, dropped when none remain or when it cannot be judged (fail closed), its headline `version` becomes the best allowed version when the original is held, and its links point here (`a_search_...`, `search_works_through_the_shared_service_with_its_query_keys`). Autocomplete by `id` lists allowed versions; by `q` it hides blocked ids.
- Vulnerability database and repository signatures. `VulnerabilityInfo/6.7.0` and `RepositorySignatures/{4.7.0,5.0.0}` are forwarded as documents: the index is rewritten (`@id` to `v3/vulnerabilities/{base|update}.json`, `contentUrl` to `v3/repository-signatures/certificates/{fingerprint}.crt`), and a file or certificate is served only when the registry's CURRENT index names it, from the origin of that index (nothing else of the host is reachable). The real client uses both: `NuGetAudit` reads the vulnerability index and `base` file through the firewall in the native lane (asserted), and `dotnet list package --vulnerable` in the E2E. Over plain http the signature resource is not advertised (the real client refuses an http one: NU1301, found by the native lane).
- Caches and C1028. The only memory is the per-registry service index (60 s, 15 s on failure, 64 registries, one fetch at a time) and, in the shared service, one fetched project per (registry, origin, id) for 5 s (256 at most); persisted state is reference identity, first-seen and pins. A request that carries the caller's credential (any non-allow-listed header) reads and fills NOTHING shared (`credential_bearing_read_never_enters_shared_caches_nuget_end_to_end`: the service index and the project are fetched again for it, its file never enters the content store, bytes fetched under a credential are never served without it, path-embedded credential forms reach nothing).
- Re-admission (FIX-16-A, `src/http/readmit.rs`) covers NuGet with no NuGet code: `a_publication_between_authorisation_and_release_is_admitted_again_for_every_family` now lists a NuGet document and a NuGet file. The selected route returns the marked refusal when the principal changed under it, as Go.
- Small-transfer pool. A `.nuspec`, readme and icon take one of the 64 small places and are read to 16 MiB (a 17 MiB nuspec is 502, 1 MiB served); they never queue behind large `.nupkg` transfers (`tiny_files_do_not_queue_behind_large_transfers_...`).
- Redirects and the archive origin. api.nuget.org answers a package directly (checked 2026-11-19: 200, no redirect, 2.4 MB). A registry of its own that redirects a `.nupkg` to storage declares an archive origin (the field and migration of rows 18 and 19, now NuGet too: portal field, activation validation, descriptor, transport); only a `.nupkg` transfer follows a redirect and only to that origin, the registry credential is never sent there; without one a redirect away is refused (502). Witnesses: tests/origin_guard.rs, tests/nuget_service_read.rs (`a_declared_nuget_archive_origin_travels_with_the_package_request_only`), the server's ecosystem_tags and portal_places tests, service_policy_cache.
- Writes (class W). Through the shared service only: `dotnet nuget push` (`PUT api/v2/package`, multipart, `X-NuGet-ApiKey`), the symbol package (`PUT api/v2/symbolpackage`), `dotnet nuget delete` (unlist, `DELETE api/v2/package/{id}/{version}`) and relist (`POST` of that URL), with the caller's own `X-NuGet-ApiKey` and `Authorization` to the publish endpoint the registry's own service index names (its origin; for the public registry `nuget_publish_url`), 401 before any lookup without a credential, 413 over the cap before the registry is asked anything, the id and version checked before any upstream call, the registry's status and body returned. The service key never leaves; an endpoint outside the allowed origin offers no route (404) and the key goes nowhere (`tests/nuget_service_write.rs`, the route table rows, `every_class_w_route_refuses_without_credential_and_makes_no_upstream_call`). A standalone or managed firewall has no write route (405 on `/nuget/`).
- LS-F4 allow-list. Real dotnet 8.0.416 sends `Accept-Encoding`, `Accept-Language`, `Host`, `User-Agent` (common) and `X-NuGet-Client-Version` and `X-NuGet-Session-Id` on a plain read (measured with a tap, `dotnet_native_client_sends_only_allow_listed_headers`); the two are the family's allow-list entries, with the search protocol's seven query keys. Credentials: `Authorization` (Basic from `packageSourceCredentials`, Bearer from a credential provider) and `X-NuGet-ApiKey` on writes, all request-scoped; no route takes a token in its path or query. The family's path-embedded and userinfo forms are in the family tests.
- Authentication is by the installed client's own key, not certificates: a managed firewall on the key route takes the key as the Basic password; NuGet has no client-certificate setting for a source, so the certificate script says so on stderr and writes no configuration (unit test `nuget_setup_points_at_the_key_route`), exactly as Cargo and Go.

## LS-F7: the family's inputs and caps (measured against the real registry, 2026-11-19)
- Documents are read to `max(max_metadata_bytes, 16 MiB)`; no NuGet input is inflated by the firewall beyond the transport's own decoding of the registry's `Content-Encoding: gzip` (api.nuget.org serves registration gzip; the transport decodes it and counts the decoded bytes against the cap).
- Largest real inputs: registration index of mongodb.driver (123 versions, two inline pages) 20,295 bytes gzip, 685,385 inflated; a linked registration page of awssdk.core (64 leaves) 14,627 gzip, 670,004 inflated (45.8:1, the highest ratio of 12 packages measured); a registration of newtonsoft.json 10,328 / 367,330; awssdk.core has 1,524 versions in 24 linked pages; the flat container index of awssdk.core 27,216 bytes; the service index 9,431 bytes; `vulnerability.base.json` 42,711 gzip / 842,176 inflated; the largest nupkg sampled newtonsoft.json 13.0.3 2,441,966 bytes. So the 16 MiB floor is 23x the largest document; the vulnerability file cap is 128 MiB, the service index cap 1 MiB, a certificate 256 KiB, a nuspec/readme/icon 16 MiB, a `.nupkg` `max_artifact_bytes`. No valid input is refused before those caps: `a_large_registration_is_not_refused_before_its_cap` serves a 4,000-version, 3 MB registration.

## Not done, limits and decisions
- Old binaries. No prior-release enforcer or server was built. Compatibility is witnessed at the wire level only: `Upstreams.nuget` is additive both ways (`nuget_reachability_is_additive_in_both_directions`), the `NuGet` descriptor tag is the explicit unknown-tag path of LS-F3 for an enforcer that predates it, and `archive_origin` is ignored by an older reader (the slice 18 test).
- Registration is served as one SemVer 2 view for every `RegistrationsBaseUrl` type. A client older than NuGet 4.3 (which cannot parse SemVer 2 versions) would see them; no such client is supported by .NET 8.
- Search costs up to 50 projects per request (two upstream documents each, cached per project TTL). A result that cannot be judged is dropped (fail closed), so a registry outage during a search shows fewer results, never an unfiltered one.
- Not served (nothing to protect or serve): the legacy gallery (`LegacyGallery`), package staging, the catalog, and the web-page URI templates; the registry's semver1-only registration view. A resource type this firewall does not name is not advertised, so a client falls back to what remains.
- The repository signature index is not advertised over http (client-side refusal).
- A registry of its own may serve its flat container only under a path the registry's origin allows: any path on its host is admitted (decision 2).

## Decisions for the user (defaults chosen; nothing here is a request to build or drop a feature)
1. Registration documents are always inline (decision of design above). Alternative: re-link large registrations to page routes of this firewall (more code, smaller documents). Default kept; the measured largest linked page is 670 kB.
2. A registry of its own may name its resources anywhere on its own host (not only under its index's path), because the three real feed families (Azure Artifacts, Artifactory, GitHub Packages) lay resources out beside, not below, the index. The cost: a feed host shared by many tenants (Azure DevOps, GitHub Packages) is trusted as one origin, and the caller's own credential is sent to it. Alternative: require a common path prefix (breaks Azure Artifacts). Default kept.
3. Resources the firewall does not serve are not advertised (LegacyGallery, staging, catalog, web templates, the semver1-only registration type) rather than passed through to the registry's origin. Passing them through would hand a client a direct upstream URL. Default kept.
4. `catalogEntry` and catalog `@id` URLs in registration are identifiers and are left as the registry wrote them (no restore reads them). Alternative: rewrite them to an unserved route. Default kept.
5. A standalone or managed firewall answers a write verb on `/nuget/` with 405 (the read-only route), not 404 as Cargo's absent `/cargo/api` route does. Default kept.

## Fix round (reviews/slice-20/code-review.md and security-review.md; every finding fixed, nothing dropped)
- **S20-1 / F1 amplification.** Registration documents are now kept as the bytes the registry sent (`RegRaw`) and shared for 5 s per (registry, origin, id) by credential-free reads (8 ids, 16 MiB each); the pages of one registration together are held to the document cap (an over-cap sum is 502; 256 pages is the bound, 257 refused before any page is fetched). One request at a time refreshes one project (`single_flight`, a per-key gate: 40 simultaneous reads cost one registration fetch and one flat read) and at most 16 refreshes run in the process (`REFRESHES`, a wait over 30 s is a 504), which bounds a search, a burst, and credential-bearing reads that share nothing. Search judges at most 100 results (`SEARCH_TAKE_CAP`; the rest are not shown), every document request has a 60 s deadline. The vulnerability index, vulnerability files, signature indexes and certificates go through `cached_document` (30 s, 16 entries of at most 8 MiB, credential-free reads only); the vulnerability file cap is 32 MiB (the real file is 0.84 MB) and `Rendered.body` is `bytes::Bytes`, so no document is copied again. C1028 holds: a credential-bearing read reads and fills none of the new cells (`a_credentialed_read_shares_neither_registration_nor_aux_documents`, shared service).
- **S20-2.** `allowed_for` refuses a blocked id before `current_project` (zero upstream calls for it); `?id=` autocomplete of a blocked id is 403 before the registry is asked (`blocked_ids_cost_search_and_autocomplete_no_upstream_call`).
- **F2 (all publish forwarders, fixed once).** src/http/spool.rs is the one place an upload is spooled: npm publish (`registry_action`), PyPI upload, `gem push`, `cargo publish` and `dotnet nuget push` all go through it. At most 8 spools at once (the ninth is 503, never queued), one byte budget for all of them together (`max(max_artifact_bytes, 64 MiB)`, reserved from the declared length or as chunks arrive), a 15-minute body deadline, a declared length over the cap is 413 before a byte is taken, and a write without a credential was already refused before anything is read. The key value is not validated (the registry does that), so a junk key can fill the places and the budget and no more. `Limits` owns the places and the budget (`SpoolReservation` returns bytes on drop). Tests: `uploads_past_the_spool_places_are_refused_not_queued` (nine open uploads, the ninth is 503, nothing forwarded), `the_spool_places_and_bytes_are_bounded_and_returned` (lib), and the existing publish suites for every family unchanged. Streaming without a spool would drop the recheck-after-body design, so the bound is the fix; decision for the user below.

- **S20-4.** `valid_name(NuGet, ..)` refuses `.`, `..` and any id that starts or ends with a dot.

## Decisions for the user (fix round)
1. F2 is fixed by bounding the spool (8 places, one budget, a deadline), not by streaming without a spool: streaming would drop the recheck of the policy snapshot after the body (the design of rows 17 and 18). Default kept; the alternative is a per-forwarder streaming path.
2. `take` over 100 is a 400 (not clamped, not forwarded). Alternative: forward any `take` and judge only the first 100 (results beyond would be skipped silently). Default kept.
3. Vulnerability data is not offered over plain http and there is no opt-in key. Alternative: a config key `nuget_allow_plain_http_audit`. Default kept (fail closed).
4. A project over 5,000 versions keeps its newest 5,000 (the oldest are withheld). Alternative: raise `max_references_per_project` for such feeds (a config key that exists).
