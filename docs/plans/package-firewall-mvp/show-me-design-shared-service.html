Package Firewall MVP: combined design approval

Topic: one shared enforcing service, nine package families, and the FIX-16-A current-authority release. This page is a digest of 02-architecture.md, 03-program-design.md and 04-slices.md. Nothing here is implemented or run yet.

What problem do we have?

Today: the firewall is built for one user at a time and two package families (npm and PyPI). Teams want one service for a whole machine or a whole cluster, with one shared policy, and protection for nine families.

A real defect, FIX-16-A: on the older managed route, the final "is this download still allowed?" check uses the policy as it was when the request arrived. If the policy server publishes a ban or refuses the service key while the request is still preparing, the file can still be sent. This applies to cached ("warm") files too. The source reading is in evidence/artifact-flow-correctness.md.

Consequence: a package that should be blocked could be delivered after the block was published. The new shared service would inherit the same gap unless it is fixed first.

How will we solve it?

1. Purpose and what the caller gets

  • One enforcing service per machine, or one per cluster (C1019).
  • One policy for everyone who uses it. The policy is chosen by one organisation service key held by the service (C1020).
  • No Probation login on package requests. Access is limited by host and network controls: loopback on a machine, approved nodes in a cluster (C1021, C1022).
  • Package-manager credentials stay where they are. The firewall stores no registry credentials. There is no public/private mode (C1015, C1024).
  • Either the exact verified artifact arrives, or it is refused with zero artifact bytes.

2. Behaviour flow, including the FIX-16-A release gate

The gate is a short synchronous lock in managed policy state. Publishing a policy, a refusal or a new config takes the write side and raises a generation number. The final check takes the read side, confirms the exact file, registry, config generation and OSV generation (the vulnerability-feed version, C1029) are still current, and hands the response over while still holding the lock. No waiting and no input/output happens inside it. A publication ordered before the final check governs the request, cold or warm. A publication after handoff does not cut a stream that was already accepted.

Reading the diagram in words: a snapshot is activated under the write side. A request prepares, then the gate checks it. Outcomes: exact bytes, refusal with zero bytes, or re-preparation (two tries at most, then 503). A later publication affects the next request, not the accepted stream. Source: 03-program-design.md "FIX-16-A" and its OSV generation contract.

// crates/probation-server/src/service_policy.rs   (proposed, slice 28)
// Snapshot route handler: GET /api/v1/policy/snapshot, read-only.
// Effects: one read transaction binds key standing, policy chain and registries.
// Errors: PolicyApiError (401 bad or wrong-kind key, 403 suspended, 429 budget, 503 storage).
pub async fn snapshot(/* existing request/server dependencies */) // no caller org or place selector accepted
    -> Result<ServicePolicySnapshot, PolicyApiError>;

// What the policy server returns for the service key's one organisation.
// It holds no upstream credentials. The enforcer validates it fully before use.
pub struct ServicePolicySnapshot {
    pub version: u32,                          // wire version; an unsupported version is a validation failure
    pub key_id: KeyId,                         // the service key this policy belongs to
    pub org: OrgId,                            // organisation derived server-side from the key
    pub place_chain: Vec<ChainLink>,          // inheritance chain for the key's group or organisation
    pub layers: Vec<PlaceLayer>,              // policy layers; must correspond to the chain
    pub revision: u64,                         // policy revision number
    pub account: PlaceRef,                     // place the policy is attached to
    pub rate_limit: Option<std::num::NonZeroU32>, // None means no rate limit is set
    pub rate_limit_source: LimitSource,        // where the limit came from
    pub registries: Vec<RegistryDescriptor>,   // every registry the organisation owns
}

// One registry the enforcer may reach. Carries no upstream credentials.
pub struct RegistryDescriptor {
    pub registry: RegistryId,                  // registry identity used in policy keys
    pub ecosystem: Ecosystem,                  // package family
    pub target_url: Option<String>,            // upstream address; can only narrow what the local denylist allows
    pub trusted: bool,                         // trust flag from the descriptor
    pub registry_private_cidrs: Vec<String>,   // can only narrow, never widen, the denylist (D5)
    pub deletion_scopes: Vec<RegistryDeletionScope>, // which deletions this registry permits
}

// src/managed/service_policy.rs   (proposed, slice 28)
// Validates a full reply, then activates it once, atomically.
// Effects: publishes policy and bumps generation; persists a refusal before acting on it.
// Errors: ServicePolicyError. Never changes mode on an outage.
async fn activate(&self, /* received reply + configured service identity */) // crate-private; ordering anchored at activation_order in src/managed/order_guards.rs
    -> Result<(), ServicePolicyError>;

// src/http/service_registry.rs   (proposed, slice 28)
// Owns the whole response lifetime: registry binding, dispatch, verified preparation,
// current-policy recheck, then release. Errors map to ApiError (refusal gives zero artifact bytes).
pub async fn respond(/* App + selected registry + native request */)
    -> Result<axum::response::Response, ApiError>;

Recommendation

Approve the design. Fix FIX-16-A first because it is an existing defect and the shared service would otherwise inherit it. The design is complete enough to build: Design QA is READY, the threat model is MODELED with no blocking finding, and no choice is left to Engineering. The limits below stay visible and are not hidden by approval.

Limits

  • Existing prototype code. Uncommitted prototype code for rows 16 and 28 was written on 2026-11-03, before this design was approved. Its author and review status are unrecorded. It is treated as an unreviewed draft to verify and complete. Nothing is deleted. Each new test runs fail-first against a baseline worktree on disk. Rows 16 and 28 review each diff, and a hunk that no row outcome needs is reset or deferred with a reason. You may overrule this default.
  • Source order checks are PENDING. They cannot run until the guard files exist: src/managed/publication_gate.rs (row 16), src/managed/order_guards.rs and crates/probation-server/src/order_guards.rs (row 28). Even then they prove only call order, not same-file, atomicity or concurrency. Those rest on the runtime tests.
  • Cluster routing is unverified. The containerd routing is a documented candidate, not runtime-verified (C1023). Row 29 probes it early. Cached images may not reach the service, so no revocation after a pull is claimed.
  • Execution mode. Protocol rows 17 to 24 run under version 1 serial execution. The parallel version 2 coordinator is not requested. Choose it only if you want it.
  • No proof yet. No builds or tests were run for this design. Native OS and cluster behaviour is design-level until rows 25, 26 and 29.
  • Model view. The flow model is version 1, so the generated domain view is unsupported (UnsupportedVersion). This page is grounded in the documents, not in a generated correspondence.
  • Accepted limits: delayed revocation under C19/C20, cached images, the local administrator (C30).
  • Render: not inspected. No tool here renders this page.
