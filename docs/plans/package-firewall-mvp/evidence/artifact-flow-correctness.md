## Five deciding findings

1. **All inspected artifact entry variants converge on the verified seam.** `src/http/mod.rs:49–116` explicitly registers legacy npm/PyPI reference routes, npm upstream-shaped/scoped/namespace tarball routes, and selected-registry npm/PyPI routes. Legacy reference requests call `artifact_routes::serve` → `deliver` → `artifacts::serve_artifact`; npm named requests first resolve an advertised reference (`src/http/artifact_routes.rs:25–173`). Selected npm calls `serve_admitted_artifact` → `serve_artifact_in` (`src/http/registry_routes.rs:111–172`); selected PyPI does the same (`src/http/pypi_routes.rs:303–327`). No inspected warm branch directly returns a file to the client.

2. **Reference identity and membership precede both cache outcomes.** `serve_artifact_in` loads a stored reference and rejects mismatched registry, ecosystem or filename before I/O (`src/artifacts/mod.rs:90–134`). `ReferenceId::compute` binds ecosystem/name/version/filename/upstream URL/expected digests; `compute_in_registry` additionally binds nonzero registry identity while preserving legacy IDs (`src/artifacts/reference.rs:34–82`). `ensure_membership` requires that a sufficiently fresh project snapshot still advertises that exact ID; cached bytes do not excuse removal (`src/artifacts/mod.rs:187–215`). A warm hit opens/pins the mapped content and checks its stored size; missing/wrong-size content loses its mapping and is fetched again without losing pins (`src/artifacts/mod.rs:337–388`; `src/artifacts/content.rs:357–422`). Warm content is deliberately not rehashed: the contract relies on private, immutable, previously verified storage, not detection of same-size local disk tampering.

3. **Cold completion is not downstream release or reusable authorization.** Download consumes the whole upstream body into a bounded temporary file, hashes it, validates advertised integrity/length, and durably pins computed digests; changed bytes conflict with original pins (`src/artifacts/download.rs:221–371`). Standalone download reevaluates current policy before publication; managed download intentionally publishes verified bytes independently of tenant policy so each waiter can decide separately (`:373–435`). Both warm and cold callers then reach the final policy evaluation with advertised AND pinned digests; cold callers also recheck membership (`src/artifacts/mod.rs:135–183,217–243`). Refusal/hold/unavailable returns an error instead of a witness. HEAD and Range use that same gate. `Authorized` is non-Clone/non-Copy, and response constructors consume it (`src/artifacts/stream.rs:40–66,152–238`). However its public constructor accepts any `Decision::Allow` and a revision; it is not bound to a reference, file, principal, policy generation or authority check. It prevents an accidentally omitted witness, not an independently proved correct decision.

4. **There is a concrete policy-source distinction the draft must not erase.** Standalone `App::policy_for(None)` loads the current published policy; `policy_for(Some(principal))` clones `principal.policy` (`src/lib.rs:200–205`). Legacy `http::admit` authenticates once (`src/http/mod.rs:145–180`), and legacy `artifact_routes::deliver` has no subsequent managed-authority recheck. Therefore a managed policy update or key refusal applied while an admitted legacy request awaits metadata/download does not replace the policy that its apparent “final reload” evaluates. This affects warm requests too if suspended during awaited preparation. By contrast selected-registry npm/PyPI performs an outer `registry_read::recheck*` after artifact preparation, propagates refusal with `?`, compares current fingerprint and registry authority fields, and drops the prepared response on change (`src/http/registry_routes.rs:143–171`; `src/http/pypi_routes.rs:315–326`; `src/http/registry_read.rs:78–107`). This is stronger than the legacy path, but is not a proof against every concurrent publication. Managed authentication explicitly permits matching stale state during server outages (`src/managed/mod.rs:415–435,477–526`), which must remain distinct from an explicit refusal. `check_delivery` is log/SIEM startup validation, not this artifact gate (`src/lib.rs:455–473`).

5. **The shared-service draft names the right obligations but does not implement them.** Active `03-program-design.md:90–110` requires identity-bound durable activation/refusal, current service policy at release, exact verified bytes, HEAD/range parity and an accepted non-retroactive streaming boundary. Existing inner delivery still awaits OSV evaluation after loading a snapshot and awaits `record_would_block` after obtaining `Authorized` (`src/artifacts/mod.rs:157–170,268–301`). Reusing that interface alone cannot satisfy the draft's proposed no-await final handoff. No-await narrows a scheduling window; another runtime thread can still publish concurrently, so it is not an atomicity proof. Define the linearization point: an authority/policy publication observed before final authorization must govern that request; a publication after accepted final authorization need not revoke an already accepted stream. Bind that final successful decision to the exact prepared reference/file and current service-authority/config generation, propagate refusal, then hand off synchronously. If asynchronous OSV/preparation is needed, finish it before the final generation check, retry/re-evaluate on generation change, and specify the publication/authorization synchronization rather than relying on call order.

## Branch outcomes and smallest required correction

| Scenario | Source-supported outcome / remaining obligation |
|---|---|
| Known warm artifact, current local deny/hold | Initial/final evaluation refuses; verified cache content is not permission. |
| Unknown reference, wrong filename/ecosystem/registry | Refuses before content delivery. No URL synthesis from arbitrary artifact request data. |
| Withdrawn reference | Fresh membership rejects even with cached bytes; metadata TTL remains the stated freshness boundary. |
| Cold truncated/integrity-changing artifact | Does not become verified content; original pins survive conflicts. |
| Standalone policy changes during preparation | Final policy load evaluates the new snapshot if publication precedes that load; accepted streams retain their old authorization boundary. |
| Legacy managed policy/refusal changes during preparation | Admission-time principal survives; no current-authority lookup at final seam. Treat as pending correction, not a cache exemption. |
| Selected-registry status/policy changes | Outer recheck failure/change discards the prepared response; synchronization after that check remains bounded by the accepted authorization boundary. |
| Managed outage versus explicit refusal | Matching remembered policy during outage is intentional. New service code must durably invalidate explicit refusal and prevent late activation/previous-file recovery from resurrecting it; existing draft statements are not source proof. |

Smallest correction is one owner of final managed authority and response release, reused by legacy and selected routes as appropriate to their existing authority model and by the future common-policy service. It must reload live local authority/policy state rather than reuse an admission principal, verify generation/registry binding, consume the successful result for this exact prepared file, and propagate failures. Do not add a new global credential mechanism or change publishing as part of this fix. The canonical npm token-packument metadata exception remains C35; `01-product.md:121` explicitly excludes artifact downloads and upstream write authority.
