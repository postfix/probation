# Local client and policy modes — existing seams

Verdict: PARTIAL. Existing code supplies standalone and managed policy engines, request enforcement, caches and upstream transports; local enrollment, API-key policy retrieval and safe mode transitions still need design.

Date: 2026-11-02. Scope: bounded structural inventory for the user's new direction: locally installed client; API-key authentication to a policy server; standalone TOML operation without that server. This replaces the proposed certificate bridge direction. No implementation or replacement mode semantics are approved here.

## Five decisive facts

1. **The executable is already a configurable package proxy, not a native-package-manager replacement.** Prior source inventory `src/main.rs:18,29,140` provides `serve --config PATH`, `check-config` and `check-blocklist`. `Config` (`src/config.rs:24`) carries a listen address, public URL, data directory, resource limits, origins, optional logs/SIEM and policy settings. A local installation could reuse that serving process, but the installer, lifecycle and native-client setup are new responsibilities. A per-user loopback listener versus a shared host daemon is not selected by the current code evidence.

2. **Mode choice already exists, and it is startup configuration rather than automatic outage fallback.** `Config.management: Option<ManagementConfig>` (`src/config.rs:101`) is present only in managed mode; its documented contract says a broken section refuses startup rather than running standalone. `App::start` (`src/lib.rs:323`) constructs `Managed` only when the section is present. At `src/lib.rs:354`, only the absent-management branch restores and polls the local blocklist. `App::policy_for` (`src/lib.rs:200`) selects the supplied principal's compiled policy or the standalone policy. Existing mode selection can support both local and shared deployment topologies, but neither topology is automatically a managed identity/enrollment mechanism.

3. **Standalone TOML policy is narrower than managed inheritance.** `CompiledPolicy::standalone` (`src/policy/effective.rs:29`) maps local cooldown and OSV mode into one platform layer and attaches the locally loaded blocklist snapshot, including expiry. The blocklist is a separate existing file, not an arbitrary inherited policy embedded in TOML. Managed policy uses the shared `probation_policy::resolve` layer model and compiles central blocks into a snapshot without local blocklist expiry (`effective.rs:51`). The preceding authentication inventory establishes platform→organisation→optional group→user policy selection. The local client must use the same resolver, identity-bound effective policy and artifact-time checks; accepting only the standalone TOML knobs would lose central layers, exceptions, blocks or constraints.

4. **Cached-policy outage behavior already has deliberate distinctions.** `src/managed/cache.rs:1,31,117` describes key/principal entries, shared layers/compiled policy, revisions and a restart snapshot. Live entries can expire or be invalidated by place changes; refused entries represent unknown/revoked/suspended keys; an unreachable server suppresses eviction of cached keys. `Managed::ask` (`src/managed/mod.rs:500`) reuses an expired cached policy when the server is unreachable. A busy server may reuse a normally expired entry, but not one invalidated by a place change; unknown keys do not acquire a policy through that branch. These decisions preserve remembered central policy, not a weaker TOML fallback. Snapshot serialization, loading and complete sync/reset/retirement wiring were outside this bounded pass; reuse their established contracts and tests rather than inventing replacements.

5. **Removing management is a policy change, not an outage.** The inspected startup path creates standalone policy after the management section is absent, using the local cooldown/OSV/blocklist instead of the former central effective policy. Those local settings can be less restrictive; the inspected seam does not compare the new policy with the old central one. Thus removal plus restart can relax policy even though malformed management does not fall back. No automatic “server unreachable → standalone TOML” behavior should be inferred or introduced. The proposed client needs an explicit managed/standalone choice and deliberate enrollment/removal transition whose weakening semantics are approved. Whether users may override a centrally managed local installation is a product/trust-boundary choice, not something API-key authentication alone solves.

## Caller-visible choices still open

- Is the client a per-user proxy service, a shared machine daemon, or a command wrapper? How do package tools address it and how is it kept running?
- Is standalone mode exactly today's cooldown/OSV TOML plus separate JSON blocklist, or does the user want richer Nora-style TOML policy? Current reuse proves the former only.
- What policy identity, scope and endpoint does a local API key authenticate; how do enrollment, group membership updates, expiry, rotation, revocation and removal work?
- Preserve the selected cached-policy outage behavior, including no policy for an unseen identity. Define first enrollment without a server and recovery after a revoked key explicitly; neither should silently choose standalone.
- Who may change managed mode to standalone, and is local enforcement a user-controlled tool or a mandatory organisational boundary? What happens to protected upstream credentials and network bypass when management is removed?

These are design inputs, not choices made by this evidence note. The management-server product decisions C8/C9/C12/C19 supplied by the main agent remain controlling inputs; this pass did not rewrite or independently reread them.
