Package Firewall MVP: combined design re-approval after the central OSV re-steer

Topic: C1030, C1031, C1021 amendment, new Slice 30 (row 30). Approval target: design.

What problem do we have?

Today every running endpoint builds its own OsvClient (src/lib.rs App::start) and calls https://api.osv.dev/v1/querybatch itself. A fleet of thousands of managed endpoints would each hit api.osv.dev with cold caches (osv-intel C2001/C13, management-server C110/C83: "managed mode adds no OSV traffic" meant no extra calls, not fewer). A second risk surfaced in Red Team (C1031): once OSV goes through the policy server, a server outage must not silently remove the OSV protection endpoints have today.

How will we solve it?

Purpose and caller outcome

In managed and shared-service mode the policy server is the only caller of api.osv.dev. It exposes an osv.dev-compatible POST /osv/v1/querybatch (same request and response shape) with one upstream client and one shared cache. A managed endpoint keeps its whole OsvClient and changes only its OSV base URL (server URL plus /osv), sending the credential it already uses for that server (firewall token or service key). Standalone is unchanged and still calls api.osv.dev directly. Managed mode never selects direct OSV: no configuration key, environment variable or retry does.

Caller journey: a managed endpoint evaluates an OSV-blind Allow for npm left-pad@1.3.0; its batcher POSTs the osv.dev-shaped body to <server>/osv/v1/querybatch; the server answers from its cache or one coalesced upstream call; the endpoint stores the answer, and if the verdict newly matched, its osv_generation advances (C1029) and an in-flight response is re-evaluated or refused.

C1029 stays client-side (the endpoint counts verdict changes it stores, now from server answers), so Slice 16 and Slice 28 are not delayed or changed.

Behaviour flow

Slice 30 owns the whole route (C1030). The OSV route is not in the molecule model: molecule-flow.json and molecule-contracts.json model the snapshot/activate/respond order guards and are unchanged. The route is a single-owner request/response contract whose witnesses are the named runtime tests below and security row T9. This is a stated model gap, not a proof.

Recommendation: approve the design. It removes the per-endpoint api.osv.dev fan-out without touching standalone, Slice 16 or Slice 28, and keeps known malicious matches through a server outage. Both accepted reductions are bounded and stated.

Limits:

  • Accepted reduction 1: packages never queried before a server outage are unchecked (fail open, C3/C14) until the server returns.
  • Accepted reduction 2: an outage longer than the stale window (24 h default, 7 d maximum) ends protection for matched entries until the server returns. No direct api.osv.dev fallback in managed mode.
  • Docker/OCI is not OSV-covered (no generic OSV image ecosystem); this is not a loss.
  • The OSV route is outside the molecule model; the named runtime tests are its witnesses, not a model proof. All new tests are planned, none observed. Slice 28 source obligations are PENDING (order_guards.rs files do not exist yet). molecule-verify not run.
  • Research evidence is fragment-based (scoped npm name form inferred); a live canary per ecosystem is an opt-in lane, not hermetic. Numeric budgets, TTLs and caps are set by the row 30 implementer (D-OSV3) and approved with the row. The domain view is version 1 (UnsupportedVersion), so this digest is document-grounded, with no generated correspondence claim.
  • Rendering: render: not inspected.
