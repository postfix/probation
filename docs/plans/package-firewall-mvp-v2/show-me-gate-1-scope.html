Gate 1 scope: Package Firewall MVP (version 2 successor)

What you are approving: the same 13 remaining slices carried over from the version 1 plan. No scope change. Approving Gate 1 does not start implementation; design approval (Gate 2) comes next.

What problem do we have?

Teams install packages from public registries and cannot refuse a held or blocked release before it reaches a build. Version 1 delivered this for npm and PyPI. The remaining work extends protection to the other selected registries and a shared service, and closes a gap where cached or downloaded artifacts could be released after authority was revoked.

How will we solve it?

User action to outcome (product language of 01-product.md):

  • An operator installs one shared enforcer for the whole machine or one logical service for a Kubernetes/other orchestration cluster, and it selects one common effective policy from its configured policy key (C1019, C1020).
  • Admitted package tools and node-runtime requests use that policy with no separate Probation login and no per-request policy choice (C1021).
  • A request from an unapproved host or node is refused. Cluster access trusts approved nodes and every workload on them (C1022).
  • A held, blocked or still-waiting release is refused before any bytes are released, including from the cache. An exact request is never swapped for other bytes (non-goals).
  • Registry credentials stay in the package managers, never on the firewall. Publishing keeps the existing upstream authorization path (C1015, C1024, C1028).
  • Standalone operation without a policy server keeps working (C1008). Clients run on Linux, macOS and Windows; the policy server is Linux only (C1016, C1017).

Scope: nine families (C1013, C1027): npm, PyPI, Maven, Go modules, Cargo, NuGet, RubyGems, Conan, Docker/OCI. CPAN, Terraform, Ansible Galaxy, APT, RPM, Hugging Face, Raw and Dart/Pub stay outside this release. No UI.
